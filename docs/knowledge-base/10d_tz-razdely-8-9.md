# ТЗ сайта КП УЗН Деснянського району — разделы 8–9

Часть ТЗ. Версия ТЗ, состав частей и последние правки — `claude/10_tz-sait.md` (оглавление).

## 8. API бэкенда

Бэкенд версии 2 — API и интерфейс админки. Интерфейс админки отдаёт сам сервис на Render, с того же адреса, что и API (решение Заказчика 20.11.2026, `docs/decisions/036-admin-on-render-single-owner.md`). Причина: GitHub Pages и Render — разные сайты, и cookie сессии из 8.2 в запросах со страницы на Pages к API либо не отправляется (`SameSite=Lax`), либо становится сторонней (`SameSite=None`) — такие Safari блокирует, и вход на iPhone не работал бы. На Pages по адресу `/admin` остаётся страница-будильник (4.14, 8.7). Отсюда два следствия: запросы админки к API не межсайтовые (8.1, п. 5), а в собранном коде админки по-прежнему нет и не может быть секретов — ни токенов, ни строки подключения к БД.

### 8.1. Общие правила: база, формат ошибок и кодов, CORS, ограничение частоты

1. **База:** `https://uzn-desna-api.onrender.com/api/v1` (сервис создан 20.11.2026). Номер версии в пути обязателен: он позволит менять формат, не ломая уже собранную админку.
2. **Формат.** Запрос и ответ — JSON, UTF-8. Успех: тело ответа — объект сущности или `{ "items": [...], "total": n }`. Пустой успех — 204 без тела.
3. **Формат ошибки** один для всех эндпоинтов:

```
{ "error": { "code": "VALIDATION_FAILED",
             "message": "Телефон має бути у форматі +380XXXXXXXXX",
             "fields": { "phone": "Невірний формат" } } }
```

`code` — из закрытого перечня, `message` — готовый к показу текст на украинском, без кодов и жаргона (2.3, требование 5). Коды: `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_FAILED`, `CONFLICT`, `FILE_TOO_LARGE`, `UNSUPPORTED_FILE_TYPE`, `RATE_LIMITED`, `PUBLISH_IN_PROGRESS`, `GITHUB_UNAVAILABLE`, `DB_UNAVAILABLE`, `INTERNAL`.
4. **Коды HTTP.** 200, 201, 204; 400 — неразбираемое тело; 401 — нет или истекла сессия; 403 — роли не хватает; 404; 409 — конфликт (занятый `slug`, идущая публикация); 413 — файл больше предела; 422 — не прошло проверку схемой; 429 — ограничение частоты; 500; 503 — БД недоступна.
5. **CORS.** Админка обращается к API со своего же адреса на Render (8, вступление), и CORS этим запросам не нужен. Межсайтовый запрос один — `GET /health` со страницы-будильника на Pages (8.7). Для него разрешён единственный источник — адрес сайта на Pages, плюс `http://localhost:4321` в режиме разработки; список методов и заголовков закрытый. Подстановочного `*` нет ни в одном окружении: с `credentials` он и не работает, и открывает API любому сайту.
6. **Ограничение частоты.** 60 запросов в минуту на сессию; 10 попыток входа за 15 минут на пару «логин + адрес»; 5 публикаций в час. Ответ 429 с заголовком `Retry-After` и сообщением «Занадто багато спроб. Спробуйте за хвилину».
7. **Размеры.** Тело JSON — до 1 МБ; загрузка файла — до 2 МБ для изображений и до 10 МБ для документов (8.4).
8. **Публичных эндпоинтов чтения контента нет.** Публичные страницы читают JSON из сборки (6.6) и к API не обращаются. Без авторизации доступны только `GET /health` и `GET /robots.txt` (8.6).
9. **Идемпотентность.** `PATCH` и `PUT` по идентификатору можно повторять безопасно. Состояние не меняется методом `GET` ни в одном эндпоинте.
10. **Часовой пояс и форматы** — по 6.1, п. 3: в API ходят только даты UTC в ISO 8601.

### 8.2. Аутентификация и сессии

| Эндпоинт | Метод | Кто | Что делает |
|---|---|---|---|
| `/auth/login` | POST | Все | Принимает `{ login, password }`; при успехе ставит cookie сессии и отдаёт `{ login, displayName, role, mustChangePassword }` |
| `/auth/logout` | POST | Вошедшие | Удаляет сессию на сервере и гасит cookie |
| `/auth/me` | GET | Вошедшие | Отдаёт текущего пользователя; админка вызывает первым делом при открытии |
| `/auth/password` | POST | Вошедшие | Смена своего пароля: `{ currentPassword, newPassword }` |

1. **Cookie сессии:** `HttpOnly`, `Secure`, `SameSite=Lax`, срок 12 часов. Cookie своя для сайта, на котором открыта админка: интерфейс и API на одном адресе Render (8, вступление). Токен в cookie — случайные 32 байта; в БД хранится только его хэш (6.4). В `localStorage` и `sessionStorage` не хранится ничего (бриф, раздел 6: «не берём хранение в localStorage»).
2. **Защита от подделки запросов:** `SameSite=Lax` плюс обязательный заголовок `X-Requested-With: uzn-admin` на всех изменяющих запросах; изменяющий запрос с заголовком `Origin` не своего адреса отклоняется; изменяющих `GET`-запросов нет (8.1, п. 9).
3. **Сообщение при неудаче** одно и то же для неверного логина и неверного пароля: «Невірний логін або пароль» — чтобы перебор не подсказывал, какие логины существуют.
4. **Пароль:** не короче 12 символов, проверка по короткому списку очевидных паролей; требований «заглавная, цифра, символ» нет — они не усиливают пароль, а усложняют жизнь редактору. Хэш — bcrypt, cost 12 (6.4).
5. **Восстановления пароля по почте нет:** с бесплатного Render почта не отправляется (отчёт 06, раздел 1, п. 5). Порядок возврата доступа — 9.2.
6. **`mustChangePassword`** закрывает всё, кроме `/auth/me` и `/auth/password`: редактор, которому владелец выдал временный пароль, обязан сменить его до первой правки.

### 8.3. Эндпоинты контента по сущностям 6.2

Единый набор для каждой списочной сущности (`contacts`, `leaders`, `services`, `vacancies`, `public-docs`, `static-blocks`; с версией 3 — `green-zones`, `equipment`, вместе с их схемами):

| Эндпоинт | Метод | Что делает |
|---|---|---|
| `/{сущность}` | GET | Список, включая черновики; с параметром `trashed=1` — только «Кошик» |
| `/{сущность}` | POST | Создание; `status` по умолчанию `draft` |
| `/{сущность}/{id}` | GET, PATCH | Чтение и частичная правка |
| `/{сущность}/{id}` | DELETE | Мягкое удаление: ставит `deletedAt` |
| `/{сущность}/{id}?permanent=1` | DELETE | Окончательное удаление из «Кошика»: только владелец (9.1) и только запись с `deletedAt` |
| `/{сущность}/{id}/restore` | POST | Возврат из «Кошика» |
| `/{сущность}/{id}/status` | POST | `{ "status": "published" | "draft" }` |
| `/{сущность}/order` | PATCH | `{ "ids": [...] }` — новый порядок целиком: все записи вне «Кошика», `order` — позиция с 1. Только у сущностей с полем `order` (6.1, п. 6); у `static-blocks` его нет |

Синглтоны (`enterprise`, `feed-rules`) имеют только `GET` и `PATCH`; черновика у них нет. Модерация внешних карточек:

| Эндпоинт | Метод | Что делает |
|---|---|---|
| `/feed` | GET | Карточки ленты из `data/sync/feed.json` ветки `sync-data`, у каждой — скрыта ли она и где окажется после публикации; `state` — `data`, `empty` или `unknown` (6.5), если файл ленты прочитать не удалось |
| `/feed/hidden` | POST | `{ "urlKey": "…", "hidden": true | false }`; ответ — `{ hidden, changed, pendingChanges }` |

Ключ записи ленты — `urlKey` с косыми чертами, поэтому он передаётся в теле, а не в адресе (решение 043). Повтор того же решения ничего не меняет и в журнал не пишется. Скрыть можно только карточку, которая есть в ленте (иначе 404); вернуть — всегда.

Правила для всех эндпоинтов контента:
1. **Проверка.** Тело — поля сущности; оно проверяется той же схемой Zod из `shared/`, что применяется при сборке (6.1, п. 8), и проверяется вся запись: при `PATCH` присланные поля накладываются на текущую запись (`null` убирает поле — RFC 7386), проверяется результат. Непрошедшее — 422 с перечнем полей. Служебные поля (`status`, `deletedAt`, `createdAt`, `updatedAt`, `firstPublishedAt`) ставит сервер; из тела они не принимаются.
2. **Ответ.** Запись — `{ id, status, createdAt, updatedAt, deletedAt, firstPublishedAt, data }`, где `data` — поля сущности по схеме. Ответ на изменение — `{ item, pendingChanges }` и заголовок `ETag`, на окончательное удаление — `{ pendingChanges }`, список — `{ items, total, pendingChanges }`.
3. **`slug`.** Не прислан — формируется из украинского названия по таблице транслитерации постанови КМУ № 55 від 27.01.2010 (https://zakon.rada.gov.ua/laws/show/55-2010-%D0%BF); занятый получает суффикс `-2`, `-3`. Задавать и менять `slug` может только владелец; после первой публикации — с параметром `confirmSlugChange=1`, иначе 409; смена пишется в журнал действий (3.2, п. 8). У `static-blocks` вместо `slug` — `blockKey` из закрытого перечня, он не меняется.
4. **Ссылки.** `contactId` в `Service` и `Vacancy` указывает на `slug` существующего контакта вне «Кошика», иначе 422. Контакт, на который ссылаются, не удаляется и не меняет `slug`: 409 с сообщением, где он используется.
5. **Публикация.** В `published` переводится запись, прошедшая правила 1 и 4. Отдельного запрета для руководителя без `confirmedAt` нет: до отметки карточка публикуется по 5.4, п. 3 (решение Заказчика 20.11.2026; сущность `Scenario`, к которой относился второй снятый запрет, удалена 26.11.2026). У `Vacancy` поле `status` данных — тот же статус записи (решение 026); `publishedAt` проставляется при первом переводе в `published`.
6. **Права** — по 9.1: `confirmedAt` и `confirmedBy` у `Leader`, весь `FeedRule`, окончательное удаление и `slug` — только владелец. Отказ — 403 и запись в журнал.
7. **Одновременная правка.** Изменяющий запрос может нести заголовок `If-Match` со значением `updatedAt` записи; не совпало — 409 «Запис змінився або вже існує. Оновіть сторінку». Без заголовка правка проходит.
8. **`pendingChanges`** — сколько записей изменено после последней публикации, плюс окончательно удалённые, чьё удаление ещё не опубликовано. Публикация (8.5) сбрасывает счёт. Правка на сайт сама не попадает: нужна публикация.
9. **Журнал действий** (6.4): каждое изменение и каждый отказ 403 — запись с действием, сущностью, `id`, результатом и именами изменённых полей; значения полей в журнал не пишутся.
10. **Начальные данные.** При первом запуске с пустой БД сервер один раз загружает `data/*.json` версии 1: записи получают `published` (у вакансий — свой `status`), время загрузки считается последней публикацией — данные совпадают с сайтом. Отметка загрузки хранится в БД; повторно данные не загружаются, даже если записи потом удалены.

### 8.4. Загрузка изображений и документов

| Эндпоинт | Метод | Что делает |
|---|---|---|
| `/uploads` | POST | `multipart/form-data`: файл, `entity`, `slug`, `alt`. Отдаёт `{ path, bytes, width, height }` |
| `/uploads` | GET | Список загруженных файлов с указанием, кто и где их использует, и состояния: «ще не на сайті», «на сайті», «зникне з наступною публікацією» |
| `/uploads/{path}` | GET | Просмотр файла в админке: неопубликованный — из БД, опубликованный — переадресация на ветку `content-data` публичного репозитория |
| `/uploads/{path}` | DELETE | Только владелец (9.1). Удаление неиспользуемого файла; используемый — 409. Неопубликованный удаляется сразу, опубликованный уходит из ветки со следующей публикацией |

1. **Допустимые типы:** `image/jpeg`, `image/png`, `image/webp` — всем, для фото `Leader`; `application/pdf` и Word `.docx` — для `PublicDoc` версии 2 (пункт `own`). Старый формат `.doc` не принимается: по сигнатуре его не отличить от таблицы Excel. `image/svg+xml` (только владельцу, после очистки разметки) отложен: ни у одной сущности нет поля, куда нужен SVG, а надёжная очистка — тяжёлая библиотека на бесплатном экземпляре Render (решение 042).
2. **Пределы:** изображение до 2 МБ, документ до 10 МБ. Сообщение об отказе — действием: «Файл більший за 2 МБ. Зменшіть зображення й спробуйте ще раз» (2.3, требование 5).
3. **Проверка на сервере** — по фактическому содержимому (сигнатуре файла), а не по расширению и не по заголовку `Content-Type`.
4. **Метаданные EXIF удаляются** при приёме: в снимках с телефона могут быть координаты и имя автора, которые незачем публиковать. Удаляются блоками, без перекодирования изображения (п. 7): у JPEG — Exif, XMP, IPTC и комментарии, у PNG — текст, Exif и время, у WebP — Exif и XMP. От метаданных JPEG остаётся один тег ориентации: без него снимок с телефона ляжет боком, а сборка поворачивает по нему. Ориентация PNG и WebP не сохраняется (решение 042).
5. **Имя файла задаёт сервер:** `media/{entity}/{slug}-{8 знаков хэша}.{расширение}`. Исходное имя не используется: в нём бывают кириллица, пробелы и даты. У записи, которая ещё не сохранена, `slug` имени файла — транслитерация её названия, той же функцией, что строит `slug` записи: иначе пункт `own`, которому файл обязателен, нельзя было бы ни сохранить без файла, ни добавить файл до сохранения. С итоговым `slug` записи имя файла совпадать не обязано.
6. **Хранение — репозиторий** (решение 7.6), ветка `content-data` рядом с `data/*.json` (решение 041). До публикации файл лежит в БД (6.1, п. 9); рабочий процесс `publish-content` забирает его вместе с выгрузкой (8.5) и коммитит в ветку тем же коммитом, что и данные; после успеха прогона содержимое из БД убирается, остаётся путь. Токен GitHub на Render прав на содержимое репозитория не получает: владелец обходит защиту `main` (решение 006), и токен с правом записи при утечке писал бы прямо в `main`. До публикации файл не виден ни на сайте, ни в публичном репозитории (решение 042).
7. **Приведение к форматам и размерам (5.3) выполняется при сборке, а не на Render:** память и процессор бесплатного экземпляра в документации не указаны и не проверены (отчёт 06, «Что не проверено»), а обработка изображений — самая тяжёлая операция в проекте. В репозиторий кладётся оригинал, в сборку идут производные WebP в двух плотностях.
8. **Неиспользуемые файлы.** Раздел админки «Файли» показывает, где используется каждый файл; автоматического удаления нет — удаляет владелец вручную (9.1).
9. **В выгрузку идут** опубликованные файлы и неопубликованные, на которые ссылается опубликованная запись. Загруженный и брошенный файл на сайт и в публичный репозиторий не попадает. Запись, чей файл не найден, публикацию останавливает с перечнем (8.5, п. 2; решение 042).

### 8.5. Публикация: как правка редактора попадает в статическую сборку

| Эндпоинт | Метод | Кто | Что делает |
|---|---|---|---|
| `/publish` | POST | Владелец, редактор | Проверяет все `published` записи схемами; запускает рабочий процесс `publish-content` в GitHub; отдаёт `{ runId, startedAt }` |
| `/publish/status` | GET | Владелец, редактор | Последняя публикация: время, результат, кто запустил, ссылка на прогон; число неопубликованных правок. Сведения о прогоне — с 5д; прогон, который закончился, сверяется с GitHub при запросе, с кэшем 60 с (7.5, п. 4; решения 040, 041) |
| `/export` | GET | Только по токену | Отдаёт полный набор редактируемых данных (только `published`), модерацию и словарь — в формате конверта 6.6 — и перечень файлов `media/` с хэшем SHA-256 (8.4, п. 9) |
| `/export/media` | GET | Только по токену | Содержимое неопубликованного файла по пути из перечня; рабочий процесс сверяет его с хэшем (решение 042) |

**Порядок.**
1. Редактор правит данные — они ложатся в БД и на сайте пока не видны. Индикатор в админке показывает число неопубликованных правок.
2. Редактор нажимает «Опублікувати зміни». Бэкенд проверяет данные схемами и отказывает с перечнем проблемных записей, если что-то не проходит: неверные данные не должны доходить до сборки, где они обрушат её (6.6, п. 3).
3. Бэкенд вызывает `workflow_dispatch` рабочего процесса `publish-content`. Токен GitHub — в переменных окружения Render, с правом запуска рабочих процессов только этого репозитория; в репозиторий, в код админки и в чат он не попадает.
4. Рабочий процесс запрашивает `GET /export` с токеном выгрузки (общий секрет между Render и Actions) и номером своего прогона, проверяет файлы шагом `data:check`, при наличии изменений коммитит их в ветку `content-data` и запускает `deploy`, дожидаясь его итога: итог прогона `publish-content` — итог публикации. Коммит в `main` не делается: `main` защищена, а коммит `GITHUB_TOKEN` не запускает `deploy` (7.1, п. 6; решение 041).
5. Перед выгрузкой рабочий процесс до 3 минут ждёт ответа `/health` с `dbConnected: true`. Если `GET /export` не отвечает (Render спит дольше ожидаемого или остановлен), прогон завершается с кодом `EXPORT_UNAVAILABLE`, файлы `data/` остаются прежними, сайт цел (7.5).
6. Админка показывает: «Зміни з'являться на сайті протягом кількох хвилин» и далее результат по `/publish/status`.
7. **Счётчик неопубликованных правок** сбрасывается только при успехе прогона, и только до времени выгрузки: правки, сделанные во время прогона, остаются в счётчике и уходят в следующую публикацию. Прогон, который закончился неудачей или не получил выгрузку, счётчик не трогает (решение 041).

**Две одновременные публикации не запускаются:** вторая получает 409 `PUBLISH_IN_PROGRESS` и сообщение «Публікація вже триває». Скрытие карточки ленты (9.5) предлагает публикацию сразу после действия: иначе редактор решит, что кнопка не сработала.

### 8.6. Служебные: состояние сервиса, статусы синхронизаций

| Эндпоинт | Метод | Кто | Что отдаёт |
|---|---|---|---|
| `/health` | GET | Без авторизации | `{ status, dbConnected, startedAt, version }`. Ни секретов, ни сведений о среде. Используется админкой для раннего пробуждения (8.7), не пингером |
| `/robots.txt` | GET | Без авторизации | `User-agent: *` и пустой `Disallow:` — обход разрешён. Из индекса сервис убирает заголовок `X-Robots-Tag: noindex, nofollow` на каждом ответе; запрет обхода спрятал бы этот заголовок от поисковика (11.4, п. 5). Render за спящий сервис отвечает сам (отчёт 06, раздел 2) |
| `/system/info` | GET | Владелец | Версия сборки бэкенда, время запуска процесса, число записей по сущностям, время последней публикации, число неопубликованных правок |
| `/system/sync` | GET | Владелец | Состояние синхронизаций: по источнику — итог, код причины, сбои подряд и время записи состояния; последние прогоны `Sync external` (время, запуск, итог, ссылка) — решение 049 |
| `/log` | GET | Владелец | Журнал действий (9.7) с фильтрами по пользователю и датам (адрес — по коду, решение 044) |

**Статусы синхронизаций отдаёт бэкенд** (решение 049, ответы Заказчика 23.11.2026). Прежняя схема — админка читает `data/sync-state.json` из своей сборки — устарела: админка с 21.11.2026 отдаётся с Render (решение 040), сборки сайта у неё нет. `/system/sync` читает `data/sync/sync-state.json` из ветки `sync-data` по `raw.githubusercontent.com` без токена и последние пять прогонов `Sync external` из API GitHub токеном публикации (право Actions). Кэш 60 секунд; при сбое — прежняя копия с пометкой, без неё — «невідомо», а не пустой список. Файл состояния переписывается только при смене итога или счётчика сбоев (7.5), поэтому раздел показывает у работающего источника «без збоїв з …», у сбойного — время последнего сбоя, а время каждого прогона — из списка прогонов. Синхронизация от бэкенда по-прежнему не зависит (7.1): при спящем Render сломанный источник видно в журнале Actions и в письме GitHub после третьего сбоя.

### 8.7. Поведение админки при спящем Render (ожидание до минуты)

1. **Раннее пробуждение.** Страница-будильник `/admin` на Pages при открытии, до любых действий человека, отправляет `GET /health` на Render. Когда сервис ответил, она переводит браузер на адрес админки на Render, где открывается форма входа (8, вступление). Ожидание около минуты (отчёт 06, раздел 2) теперь идёт до формы, а не накладывается на набор пароля: форма входа живёт на самом сервисе.
2. **Что видно при ожидании.** Через 3 секунды без ответа — строка «Сервіс прокидається, це займає до хвилини» и индикатор ожидания. Это не ошибка и не предупреждение: сообщение нейтральное, кнопка остаётся активной.
3. **Таймауты.** Клиентский таймаут 90 секунд, затем один автоматический повтор, затем сообщение «Не вдалося з'єднатися. Спробуйте ще раз» с кнопкой повтора. Код ответа в сообщение не выводится (2.3, требование 5).
4. **Ничего не теряется.** При неудачном сохранении форма остаётся заполненной, введённый текст не сбрасывается и не очищается; повтор отправляет те же данные. Сохранения черновиков в браузере нет (бриф, раздел 6).
5. **Будильника нет** (бриф, 5.1, п. 2). Единственное обращение к `/health` — то, что делает открытая админка, и только пока она открыта.
6. **Первая операция после пробуждения** может ждать ещё соединения с Atlas: при 503 `DB_UNAVAILABLE` админка повторяет запрос один раз через 3 секунды, прежде чем показать ошибку.

### 9.2. Вход, хэш пароля, смена пароля, выход

1. **Вход** — по 8.2: логин и пароль, cookie сессии, срок 12 часов.
2. **Первый владелец создаётся без интерфейса и без консоли.** Shell на бесплатном Render недоступен (отчёт 06, раздел 2), поэтому при запуске бэкенд проверяет: если учётных записей нет и заданы переменные окружения `BOOTSTRAP_OWNER_LOGIN` и `BOOTSTRAP_OWNER_PASSWORD_HASH`, он создаёт владельца и пишет об этом в журнал. Хэш Заказчик получает локально командой `npm run hash-password`; пароль в открытом виде в переменные окружения не попадает. После создания переменные удаляются из настроек сервиса. Владелец создан так 20.11.2026; логин в ТЗ не записывается — он есть у Заказчика и в коллекции `users`.
3. **Смена своего пароля** — в админке, с вводом текущего. Смена отзывает все остальные сессии этого пользователя.
4. **Сброс пароля редактора** делает владелец: задаёт временный пароль, запись получает `mustChangePassword`. Канала «восстановить по почте» нет и не планируется в версиях 1–3 (8.2, п. 5).
5. **Если владелец потерял свой пароль,** порядок один: разработчик меняет хэш в БД напрямую либо включается повторный `BOOTSTRAP` после удаления записи владельца. Порядок описывается в `docs/runbook-admin-access.md` — вместе с тем, как убедиться, что действие попало в журнал.
6. **Выход** удаляет серверную сессию. Закрытие вкладки сессию не удаляет: срок истекает сам.
7. **Блокировка** (`active: false`) гасит сессии немедленно и сохраняет записи журнала: учётные записи уволившихся не удаляются, а блокируются.

### 9.3. Структура интерфейса: разделы, список, форма, предпросмотр

**Разделы меню админки** (подписи — украинские, как на сайте): Підприємство · Контакти · Керівництво · Послуги · Публічна інформація · Вакансії · Зелені зони · Техніка · Тексти сторінок · Новини підприємства · Тематична стрічка · Кошик · *Службове* (только владельцу: Користувачі, Словник стрічки, Журнал дій, Резервні копії, Стан системи — состояние синхронизаций и сервиса, решение 049).

**Состав меню в версии 2** (решение 040): показываются только разделы, у которых есть эндпоинты, — Підприємство, Контакти, Керівництво, Послуги, Публічна інформація, Вакансії, Тексти сторінок, Кошик, а в «Службове» — Словник стрічки, Журнал дій, Резервні копії, Стан системи и смена своего пароля. Остальные разделы появляются вместе со своими задачами (5ж; Зелені зони и Техніка — версия 3; Користувачі — когда Заказчик заведёт редактора). Пунктов-заглушек «скоро» нет: редактор не должен нажимать то, что не работает.

**Список записей.** Название, состояние («Чернетка» / «Опубліковано»), дата изменения, кнопки «Редагувати» и «Приховати». Сортировка — по `order`, переключатель «показати чернетки». Поиска по админке нет: записей единицы и десятки.

**Форма.** Один столбец, поля в порядке важности, обязательные помечены, под каждым — короткая подсказка, что это и где появится на сайте. Языковые поля — двумя закладками `Українська / English`; закладка `English` помечена как необязательная, и её незаполненность не мешает сохранению (6.1, п. 4). Кнопки: «Зберегти», «Зберегти й опублікувати», «Скасувати». Уход со страницы при несохранённых правках — с подтверждением.

**Предпросмотр** (решение 046, ответы Заказчика 23.11.2026). Карточка или блок рисуются в админке теми же React-компонентами, что и на сайте (10.2), с данными из формы. Компоненты лежат в `site/src/components/cards/`; сайт превращает их в HTML при сборке без интеграции `@astrojs/react` — JavaScript на публичных страницах остаётся 0 КБ, клиентского рантайма React в сборке нет (решение 004). Образец есть в пяти разделах: Послуги, Керівництво, Вакансії, Публічна інформація (карточки) и Контакти (строка с кнопкой-телефоном). В «Куди звертатися», «Тексти сторінок» и «Підприємство» образца нет: на сайте это строка, абзац или таблица, и текст виден в самом поле. Место: на телефоне и планшете — под полями формы, перед кнопками; на широком экране — справа от формы, не уезжает при прокрутке. Образец меняется по мере ввода, без отдельной кнопки. Язык — открытой закладки; пустой английский — надпись «Англійською ще не заповнено», заполненный частично — карточка и перечень незаполненных полей. Если запись сейчас на сайте не видна — чернетка, номер не отмечен «Номер перевірено», прошёл срок «Показувати до», документ не попадает в блоки карточек, фото без описания, — над образцом называется причина простыми словами. Образец не нажимается: телефон и ссылки в нём не срабатывают, случайное нажатие не уводит со страницы с несохранёнными правками. Предпросмотра целой страницы со сервера нет: сайт статический, страница появляется только после сборки. Это ограничение называется в подписи образца: «Так виглядатиме на сайті».

**Полоса публикации** закреплена внизу экрана: число неопубликованных правок, время последней публикации, кнопка «Опублікувати зміни», после нажатия — состояние по `/publish/status`. До задачи 5д (8.5) полоса показывает только число неопубликованных правок и время последней публикации; кнопки нет — неработающая кнопка выглядит сломанной (решение 040).

**Текст полей с разметкой** (9.8, п. 1; решение 047, ответы Заказчика 23.11.2026). Шесть многострочных полей — «Довідка про підприємство», «Біографія», «Опис» послуги, «Що ми робимо», «Вимоги» вакансії, «Текст» блока страницы — принимают закрытый набор: `**жирний**`, `[текст](адреса)`, строка с `- ` — пункт маркированного списка одного уровня (`• ` из Word — тоже). Над полем три кнопки «Жирний», «Посилання», «Список» вставляют знаки в текст; Ctrl+B и Ctrl+K. Визуального редактора нет: в поле виден сам текст со знаками, вид показывает карточка предпросмотра, а в разделах без карточки («Підприємство», «Тексти сторінок») — образец под полем, когда в тексте есть разметка. Под полем — подсказка о знаках на обеих закладках. Незакрытые `**` и скобки без адреса выводятся как набраны и ошибкой не считаются. Ссылка открывается в той же вкладке; ссылка на почту выводится числовыми HTML-сущностями (решение 008). Предел длины поля считается вместе со знаками. Английский текст — с той же разметкой. Текст без разметки выводится теми же абзацами, что прежде.

### 9.4. Требования UX для нетехнического редактора

1. **Язык.** Все подписи, подсказки, кнопки и сообщения — на украинском. Слов «валидация», «деплой», «API», «JSON», «токен», «слаг» в интерфейсе нет. Технические понятия либо названы по-человечески («адреса сторінки»), либо скрыты от редактора.
2. **Ошибки — действием, а не кодом** (2.3, требование 5), с указанием, что именно сделать. Поле с ошибкой подсвечивается и получает фокус.
3. **Подтверждения** — только у необратимого и у массового: удаление, снятие с публикации, смена порядка целиком. У обратимого (скрыть карточку) подтверждения нет, есть отмена.
4. **«Кошик»** на 30 дней с кнопкой «Відновити»: ошибочное удаление исправляет сам редактор (6.1, п. 7).
5. **Состояние сохранения видно всегда:** «Не збережено» рядом с кнопкой, пока есть правки. Автосохранения нет — и оно не обещается, чтобы редактор не полагался на то, чего нет.
6. **Мобильное и планшетное** использование: админка работает на планшете, тач-цели не меньше 44×44 px, формы в один столбец (11.1). Полноценная правка с телефона не требуется, но вход, скрытие карточки и правка телефона с телефона работают.
7. **Доступность** — те же требования, что к публичным страницам (11.3): работа с клавиатуры, видимый фокус, контраст.
8. **Страница помощи** `/admin/help` с шестью короткими рецептами: исправить телефон · додати вакансію · приховати картку · замінити фото · опублікувати зміни · що робити, якщо адмінка довго відкривається. Рецепт — три-четыре шага, без скриншотов, которые устареют. Рецепт появляется вместе с тем, что он описывает: в 5г — четыре (телефон, вакансія, приховати картку, довго відкривається), «замінити фото» — с 5е, «опублікувати зміни» — с 5д (решение 040).
9. **Инструкция редактору** (бриф, риск 4) — это и есть `/admin/help` плюс один лист на печать; отдельного документа в базе знаний не создаётся.

### 9.5. Модерация импортированного: скрытие карточки ленты

1. **Одно действие.** В разделе админки «Стрічка новин» (до решения 055 — «Новини галузі») каждая карточка имеет кнопку «Приховати» без подтверждения (действие обратимо, сообщение даёт «Повернути», 9.4, п. 3); скрытая переносится в конец списка с пометкой и кнопкой «Повернути». Раздела «Новини підприємства» нет (решение 029). Место скрытой карточки занимает следующая: на главной остаётся 3 карточки, на «Новинах» — все остальные страницами (4.8). Список показывает, где окажется каждая карточка после публикации: «на головній і на 1-й сторінці «Новин»» или «в «Новинах», сторінка N».
2. **Скрытие — только у нас.** В источнике запись не меняется: на сайте издателя она остаётся (2.5). Подсказка в интерфейсе говорит это прямым текстом.
3. **Скрытие переживает синхронизацию.** Решение хранится в `Moderation` по естественному ключу записи (6.3, 6.4) и применяется при каждой сборке. Скрытая карточка не возвращается при следующем прогоне (4.8).
4. **Текст чужой публикации не правится.** Редактор не может изменить заголовок, дату, источник и отрывок карточки ленты: это чужой текст, и его правка превратила бы цитату в нашу переделку. Доступно только скрытие и возврат. Выбора категории нет: категорий карточек нет, иллюстрация одна на все карточки (4.8; решение 031).
5. **Посты Facebook** — исключено (решение 029).
6. **Скрытие предлагает публикацию** сразу: без неё карточка остаётся на сайте до следующей публикации (8.5). Скрытие и возврат увеличивают счётчик неопубликованных правок в полосе публикации, а сообщение после действия называет кнопку «Опублікувати зміни». Сама публикация не запускается: несколько скрытий подряд уходят одной публикацией (решение 043).
7. **Все действия модерации** попадают в журнал (9.7): кто скрыл, что и когда.

### 9.6. Резервные копии БД и порядок восстановления

Бесплатных резервных копий у кластера Atlas нет: функция платная, требует карты и находится в закрытом предпросмотре (отчёт 06, раздел 1, п. 3). Поэтому копия делается своими силами.

1. **Что копируется.** Только БД: контент 6.2, пользователи и журнал 6.4, решения `Moderation`, загруженные файлы, ещё не ушедшие на сайт (8.4, п. 6), служебная запись публикации. Сессии не копируются: после восстановления все входят заново. Опубликованные изображения, документы и JSON-данные лежат в репозитории и уже имеют историю в git — в копию они не входят.
2. **Чем.** `mongodump` из рабочего процесса `backup` (отчёт 06, раздел 7, п. 3): раз в месяц, 1-го числа ночью по Киеву, и по кнопке владельца «Створити резервну копію» в админке. Рабочий процесс подключается отдельным пользователем Atlas с правом только на чтение; его строка подключения — секрет Actions `BACKUP_MONGODB_URI`. Ключ, с которым работает Render, для копий не используется (решение Заказчика 22.11.2026).
3. **Шифрование обязательно.** Дамп содержит хэши паролей и данные сотрудников, а репозиторий и артефакты прогонов публичного репозитория доступны любому. Поэтому дамп шифруется (`age`, открытый ключ — в репозитории, закрытый — только у владельца) и только после этого выкладывается артефактом прогона. **Нешифрованный дамп не попадает ни в репозиторий, ни в артефакт, ни в чат ни при каких условиях.** Закрытый ключ владелец создаёт сам на своём компьютере и хранит в менеджере паролей, вторая копия — офлайн на флешке (решение Заказчика 22.11.2026). Агенту и в чат передаётся только открытый ключ `age1…`.
4. **Срок хранения артефактов** в публичном репозитории — от 1 до 90 дней, по умолчанию 90 (документация GitHub «Configuring the retention period for GitHub Actions artifacts and logs», проверено 22.11.2026). Артефакт копии выкладывается со сроком 90 дней; владелец скачивает копию и хранит три последние у себя, не полагаясь на срок GitHub.
5. **Когда копия делается обязательно, помимо расписания:** перед изменением схемы данных (повышением `schemaVersion`), перед обновлением зависимостей бэкенда, перед передачей админки редактору.
6. **Порядок восстановления** (в `docs/runbook-restore.md`, проверяется один раз на пустой БД до передачи админки редактору): расшифровать копию → создать пустую БД или очистить текущую → `mongorestore` → войти в админку и сверить число записей по коллекциям с отчётом прогона `backup`, которым сделана копия → опубликовать изменения и убедиться, что сайт собрался. Сверка с `/system/info` заменена отчётом прогона: служебного раздела ещё нет (решение Заказчика 22.11.2026).
7. **Ограничения `mongodump` на бесплатном кластере** известны: база `admin` и часть опций недоступны (отчёт 06, раздел 3) — в порядке восстановления они не используются.
8. **Проверка копии** — не «файл создался», а «из копии поднялась рабочая БД». Копия шифруется на двух получателей: ключ владельца и одноразовый ключ прогона, который живёт только в этом прогоне и нигде не сохраняется. Тем же прогоном копия расшифровывается одноразовым ключом, поднимается `mongorestore` в чистой MongoDB на раннере, и число документов по коллекциям сверяется с исходной БД; расхождение — прогон красный. Так проверяется каждая копия, а не одна. Один раз владелец расшифровывает настоящую копию своим ключом по `docs/runbook-restore.md`: так проверяется сам ключ. Итог записывается в журнал решений (решение Заказчика 22.11.2026).

### 9.7. Журнал действий

1. **Что записывается.** Вход и выход, неудачные попытки входа, создание, правка, удаление и восстановление записи, смена состояния публикации, загрузка и удаление файла, скрытие и возврат карточки, запуск публикации, правка словаря, действия с учётными записями, создание и восстановление резервной копии.
2. **Состав записи:** время, кто, действие, сущность и её идентификатор, результат, краткие детали. Паролей, токенов и строк подключения в деталях нет (7.5, п. 6).
3. **Запись только добавляется.** Из интерфейса журнал не правится и не чистится; плановая чистка удаляет записи старше 180 дней.
4. **Кто видит:** владелец (9.1), фильтры по пользователю и датам, вывод постранично по 50 записей, новые первыми; действия названы по-украински, без служебных кодов (решение Заказчика 22.11.2026).
5. **Чего в журнале нет.** Подтверждения карточек руководства (5.4, п. 2) записываются в журнал решений ТЗ (13.3), а не здесь: это решение по продукту и согласие человека, а не действие в интерфейсе. Журнал действий фиксирует, кто поставил отметку в админке, но доказательством согласия служит запись 13.3.
6. **Неудачный вход с несуществующим логином** записывается как «невідомий логін» без введённого текста: в поле логина иногда вводят пароль (решение Заказчика 22.11.2026).

### 9.8. Вопросы к постройке админки версии 2

Записаны решением Заказчика 18.11.2026 как условия будущей задачи. В версию 1 не входят и сейчас не строятся; матрица прав 9.1 ими не расширяется — она уже покрывает всё наполнение.

1. **Формат текста в полях.** Обычный текст плюс закрытый набор: полужирный, ссылка, список. Набор размечается своей разметкой, а не хранится готовой разметкой страницы. Визуальный редактор с готовой разметкой не применяется: он даёт редактору чужие стили, вставку из Word и разметку, которой нет в дизайн-системе. **Построено 23.11.2026** (решение 047): набор и вывод — 9.3, «Текст полей с разметкой».
2. **Проверка начала адреса ссылок.** Принимаются только `http`, `https`, `tel` и `mailto`. Остальные начала адреса отклоняются с подсказкой на украинском (9.4, п. 2). **Построено 23.11.2026** (решение 047): проверяют и форма, и сервер (схема `richLangText`), отказ называет ссылку: «Посилання «…»: адреса має починатися з https://, http://, tel: або mailto:»; ссылка с пробелом в адресе и без адреса — тоже отказ.
3. **Загрузка изображений.** До постройки решить: какие форматы принимаются, какой предел веса, где хранится файл при бюджете 0 грн, как снимаются метаданные снимка. Без ответа на все четыре вопроса загрузка не строится. **Закрыто 20.11.2026** решением Заказчика «делать по рекомендациям»: ответы — 8.4, п. 1, 2, 4 и 6 (JPEG, PNG, WebP всем и SVG только владельцу; до 2 МБ; хранение в репозитории; EXIF удаляется при приёме).
4. **Границы правки.** Редактору не даётся управление вёрсткой, цветами, шрифтами и порядком блоков сверх задуманного задачей: это значения дизайн-системы, а не наполнение.
