# Эксперимент: чтение постов страницы Facebook через API Meta

Версия 1.0 от 13.11.2026. Результат этапа 3 дорожной карты (`00_brief-sait-kp-uzn.md`, разделы 5.2, 7, 9). Закрывает пометку **[ПРОВЕРИТЬ]** в разделе 5.2 брифа — кроме перечисленного в «Что не проверено».
Пометка **[ПРОВЕРИТЬ]** = не подтверждено по первоисточнику.

**Как проверялось.** Только официальная документация Meta (developers.facebook.com), открыта 13.11.2026; список — в разделе 9. Объём согласован с Заказчиком: без живого прогона, без тестового приложения.

**Что не проверено.**
- Живое поведение: что именно вернёт API для страницы `kpuzndesn`, какой срок покажет отладчик токенов.
- Нужен ли сотруднику аккаунт разработчика Meta для роли «тестировщик»: текущая страница документации говорит, что приглашение можно отправить и обычному пользователю; более старая версия требовала аккаунт разработчика.
- Как называются уровни доступа к странице в интерфейсе Facebook и какой из них даёт нужные задачи (CREATE_CONTENT / MANAGE / MODERATE) — документация для разработчиков этого не описывает.
- Срок жизни ссылок на изображения (`full_picture`): в прочитанных страницах не указан.
- Какой тип приложения предложит панель при создании и есть ли у него переключатель режимов: документация оговаривает, что уровни доступа описаны для приложений, созданных «по типу».
- Точные числа лимита запросов: сказано только, что лимит есть и счётчик виден в панели приложения.
- Набор прав: две страницы документации дают разные списки (см. раздел 3).

## 1. Главное

1. **Анонимного чтения нет.** Graph API не отдаёт посты публичной страницы без токена. Путей два: токен от человека, который управляет страницей, или функция Page Public Content Access (чтение чужих страниц).
2. **Чтение чужой страницы** (Page Public Content Access) требует проверки приложения Meta и верификации бизнеса с документами юрлица. Для личной инициативы с бюджетом 0 грн — не подходит.
3. **Чтение «своей» страницы** — без проверки приложения и без верификации бизнеса, если все, кто выдаёт приложению права, имеют роль в самом приложении. Это наш случай: права выдаёт один человек один раз.
4. **Токен страницы, полученный из долгоживущего токена пользователя, не имеет срока действия.** Но он привязан к человеку: перестаёт работать при смене его пароля, отзыве приложения, потере роли на странице, событиях безопасности.
5. **Участие сотрудника-администратора неизбежно, но может быть разовым и без приложения:** достаточно, чтобы он выдал Заказчику доступ к странице. Тогда токен выпускает сам Заказчик со своего аккаунта разработчика (рекомендация, раздел 6).
6. Токен — статическая строка без срока; годится для хранения в секретах GitHub (схема «без будильника», `claude/06…`, раздел 7, п. 1).

## 2. Ответ на вопрос «зачем доступ, если только читаем»

| Способ | Кто нужен | Проверка приложения | Верификация бизнеса | Свой дизайн карточек |
|---|---|---|---|---|
| Токен страницы от человека с задачами на странице | Администратор страницы (разово) | Нет | Нет | Да |
| Page Public Content Access | Никто со стороны страницы | Да | Да | Да |
| Встраиваемый блок Page Plugin | Никто | Нет, приложение не нужно | Нет | Нет |
| Ручное добавление в админке | Редактор сайта | — | — | Да |

Оговорка по Page Public Content Access: пока приложение в разработке, функция работает только для страниц, чей администратор сам имеет роль в приложении. То есть и здесь без администратора страницы не обойтись, а токен пользователя живёт около 60 дней — хуже первого способа.

## 3. Набор прав

Запрос: `GET /{page-id}/feed` (есть также `/{page-id}/published_posts`).

| Источник | Что требует |
|---|---|
| Справочник Page Feed | Токен от человека, который может выполнять на странице хотя бы одну из задач CREATE_CONTENT, MANAGE, MODERATE; права `pages_read_engagement` и `pages_read_user_content` |
| Руководство Pages API → Posts | Токен страницы; права `pages_manage_engagement`, `pages_manage_posts`, `pages_read_engagement`, `pages_read_user_engagement`; задачи CREATE_CONTENT, MANAGE и MODERATE |
| Обзор Pages API | `pages_show_list` — список страниц пользователя (нужен для `/me/accounts`, откуда берётся токен страницы); `pages_read_engagement` — чтение контента страницы |

Расхождение между страницами документации — факт; какая права достаточна, покажет живой прогон.
**Запрашивать при прогоне минимум:** `pages_show_list`, `pages_read_engagement`, `pages_read_user_content`. Права на публикацию (`pages_manage_*`) не запрашивать, пока API без них не откажет: сайту запись на страницу не нужна, а утечка токена с правом публикации опаснее.

Поля для карточки брифа (раздел 5.2):

| Карточка | Поле API | Примечание |
|---|---|---|
| Заголовок и текст | `message` | Заголовка у поста нет — режем сами |
| Фото | `full_picture` | Большая сторона не более 720 пикселей |
| Ссылка на пост | `permalink_url` | |
| Дата | `created_time` | |
| Остальные вложения | `attachments` | |

Ограничения чтения: не более 100 постов за запрос; около 600 опубликованных постов за год; посты с истёкшим сроком не отдаются; видеопосты читает только администратор страницы; Reels — отдельным запросом. Для сайта-визитки с запасом.

## 4. Срок жизни токена

| Токен | Срок | Как получить |
|---|---|---|
| Пользователя, короткий | Часы (около 1–2) | Вход через Facebook / Graph API Explorer |
| Пользователя, долгий | Около 60 дней | Обмен короткого; нужны ID и секрет приложения, обмен только на сервере или локально |
| Страницы из короткого токена пользователя | Часы | `/me/accounts` |
| Страницы из долгого токена пользователя | Без срока | `/{user-id}/accounts` с долгим токеном |

Meta отдельно предупреждает: на неизменность сроков не полагаться.

Что убивает бессрочный токен страницы:
- человек сменил пароль Facebook или вышел из приложения (ошибка 190, подкод 460);
- человек отозвал доступ приложения (190 / 458);
- человек потерял роль на странице (190 / 492);
- Meta аннулировала сессию по соображениям безопасности.
Meta об аннулировании не уведомляет — узнаём только по ошибке запроса.

Правило «доступ к данным истекает через 90 дней неактивности пользователя» на `pages_show_list`, `pages_read_engagement`, `pages_read_user_content` не распространяется (они в списке исключений). Отдельное правило: право, которым приложение не пользуется 90 дней, может истечь — регулярная синхронизация это снимает.

Следствия для ТЗ:
- Ошибка токена ≠ «новостей нет»: сайт показывает последние сохранённые карточки, владельцу уходит уведомление (правило брифа, раздел 6: «данные / пусто / неизвестно»).
- Нужна короткая инструкция «перевыпуск токена» — она понадобится при первой же смене пароля.
- Фото копировать к себе при синхронизации, не ссылаться на адрес Facebook: срок жизни ссылок не подтверждён **[ПРОВЕРИТЬ]**.

## 5. Проверка приложения и верификация бизнеса

- Уровень Standard Access выдаётся автоматически, без проверки. Права можно запрашивать только у людей с ролью в приложении (администратор, разработчик, тестировщик). Документация прямо называет назначение: приложения, которыми пользуются только люди с ролями.
- Advanced Access (права от любого пользователя) требует верификации бизнеса, а для отдельных прав — ещё и проверки приложения. Нам не нужен.
- Верификация бизнеса не требуется, если приложением пользуются только люди с ролью в нём.
- Приложение остаётся в режиме разработки. В этом режиме оно не видно в поиске Meta, права выдают только люди с ролями. Ограничений по сроку жизни приложения в режиме разработки в прочитанных страницах нет; запрета тоже **[ПРОВЕРИТЬ]** — блог Meta 2019 года рекомендует для «продакшена» режим Live.
- Роли: администратору и разработчику приложения нужен аккаунт разработчика Meta; тестировщиков — до 50 в приложении без привязки к бизнесу.

**Итог: проверка приложения и верификация бизнеса для нашей схемы не нужны.** Они понадобятся только если токен должен выдавать человек без роли в приложении или если читать страницу без участия её администратора.

## 6. Кто выпускает токен: два варианта

| | А. Заказчик (рекомендация) | Б. Сотрудник-администратор |
|---|---|---|
| Что делает сотрудник | Один раз выдаёт Заказчику доступ к странице в настройках Facebook | Принимает роль тестировщика в приложении, входит через Facebook, выдаёт права |
| Чей пароль привязан к токену | Заказчика | Сотрудника |
| Кто перевыпускает токен | Заказчик сам | Снова сотрудник |
| Риск | Сотрудник или руководство отзовут доступ к странице | Сотрудник сменил пароль, уволился — новости остановились до его участия |
| Не проверено | Какой уровень доступа к странице даёт нужные задачи **[ПРОВЕРИТЬ]** | Нужен ли сотруднику аккаунт разработчика **[ПРОВЕРИТЬ]** |

Причина рекомендации: риск 1 раздела 7 брифа («токен зависит от сотрудника») сводится к одному разовому действию; дальше всё в руках Заказчика.

## 7. Запасной вариант: Page Plugin

- Работает: из социальных плагинов 10.02.2026 отключены только кнопка Like и плагин комментариев; Page Plugin в списке отключённых нет.
- Вкладка `timeline` показывает последние посты страницы. Приложение, токен и администратор не нужны; страница должна быть публичной и без ограничений по стране и возрасту.
- Минусы: дизайн Facebook, не наш; грузит сторонний скрипт (JavaScript SDK) — против правила 7 инструкций о скорости первого экрана; ширина не подстраивается после загрузки без перерисовки; для посетителей из «Европейского региона» Meta (ЕС, Великобритания и др.; Украины в списке нет) плагины зависят от согласия на cookie.
- Место в схеме: аварийная замена, если токен получить не удалось. Иначе — ручное добавление новости в админке.

## 8. План живого прогона (после «да» Заказчика)

Цель — закрыть раздел «Что не проверено». Render не нужен, кода нет: только панель Meta и Graph API Explorer.
1. Сотрудник выдаёт Заказчику доступ к странице (вариант А). Проверка: страница появилась у Заказчика в списке управляемых.
2. Заказчик создаёт приложение в developers.facebook.com, режим разработки.
3. Graph API Explorer: токен пользователя с правами `pages_show_list`, `pages_read_engagement`, `pages_read_user_content`.
4. Обмен на долгий токен пользователя → `/{user-id}/accounts` → токен страницы.
5. Отладчик токенов: срок (ожидается «никогда»), список прав.
6. `GET /{page-id}/feed?fields=message,full_picture,permalink_url,created_time&limit=10` — сверить поля с карточкой.
7. Зафиксировать: хватило ли трёх прав; что с постами без текста и без фото; срок ссылки `full_picture` (повторить запрос через сутки).
8. Токен и секрет приложения — не в чат и не в git; после прогона токен отозвать или сохранить в менеджере паролей Заказчика.

## 9. Найдено попутно (не делалось)

1. В брифе пометку **[ПРОВЕРИТЬ]** раздела 5.2 можно заменить ссылкой на этот отчёт.
2. Формулировка брифа 5.2 «токен выдаётся от имени администратора» уточняется: от имени любого человека с задачами на странице — это и делает возможным вариант А.
3. Для ТЗ: место хранения токена — секреты GitHub Actions; секрет приложения нужен только при выпуске токена и в секретах не хранится.
4. Версия API в примерах документации — v25.0; версии со временем отключаются, номер версии выносить в конфигурацию.
