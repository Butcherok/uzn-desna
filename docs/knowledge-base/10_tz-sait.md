## 1. Назначение и границы

### 1.1. Цель документа, источники правды, порядок внесения изменений

**Цель.** ТЗ описывает, что должно быть построено: страницы, данные, интеграции, роли, стек, критерии приёмки. ТЗ — единственный документ, по которому проверяется готовность версии. Дизайн, тексты и код из ТЗ не выводятся автоматически: они создаются на этапах 5–8 дорожной карты (бриф, раздел 9) и обязаны соответствовать ТЗ.

**Источники правды и их приоритет.** При расхождении прав документ, стоящий выше:

| № | Документ | Что в нём правда |
|---|---|---|
| 1 | Это ТЗ | Требования к продукту: страницы, поля, поведение, приёмка |
| 2 | `01_pasport-pidpryiemstva.md` | Сведения о предприятии: реквизиты, контакты, деятельность |
| 3 | `claude/04_vymohy.md` | Нормы законодательства, обязанности раскрытия, выводы по аналогам |
| 4 | `00_brief-sait-kp-uzn.md` | Цель, границы, состав версий, дорожная карта |
| 5 | `claude/11_dyzain-systema.md` | Значения дизайн-системы: палитра и контрасты, шрифты, шкала, отступы, компоненты |
| 6 | `claude/05_…`–`claude/08_…` | Факты по внешним сервисам, проверенные экспериментами |
| 7 | `docs/` в репозитории `Butcherok/uzn-desna` | Состояние разработки, план, решения по коду, уроки |

**Копии документов базы знаний в репозитории** (`docs/knowledge-base/`, 10.3) мастером не являются: при расхождении копии и базы знаний прав документ базы знаний. Копия нужна для чтения документа рядом с кодом и как резерв; она правится только следом за базой знаний, той же задачей (решение Заказчика 15.11.2026).

Состояние разработки в ТЗ не описывается: оно только в `docs/project-context.md`.

**Порядок внесения изменений.**
1. Изменение требования вносится в ТЗ до начала работ по нему, а не после.
2. Правка меняет только затронутую часть; документ целиком не переписывается.
3. Номер версии ТЗ повышается на 0.1 при любой правке требования и на 1 при утверждении новой части. В заголовке файла указывается, что изменено.
4. Решения по продукту записываются в журнал решений (13.3), решения по коду — в `docs/decisions/`.
5. Утверждает изменения только Заказчик (Шкляр Р.П.).

## 2. Пользователи и сценарии

Приоритет при конфликте требований: 2.1 выше 2.3, 2.3 выше 2.2 и 2.4.

### 2.1. Житель района с телефона

Основной пользователь. Приходит с конкретной бедой: упало или угрожает упасть дерево, не полит газон, не убрана листва, сломано ограждение. Телефон в руке, связь может быть медленной, сайт открывает впервые.

**Целевой сценарий:** найти нужный телефон не более чем за два касания от любой страницы.
- С главной: блок «Куди звертатися» в первом или втором экране → страница сценариев → телефон.
- С любой страницы: пункт «Куди звертатися» в верхнем меню → телефон.
- Телефон — ссылка `tel:`, нажатие открывает набор номера.

**Из этого следуют требования:**
1. Верстка мобильная первой; тач-цели не меньше 44×44 px (11.1).
2. Телефоны всех разделов — всегда ссылки `tel:` с номером в формате `+380…`.
3. Публичные страницы не ждут бэкенд и открываются при спящем Render (бриф, 5.1, п. 1).
4. Текст сценария — одно-два предложения без канцелярита: что произошло → куда звонить.
5. Лишнего в первом экране нет: ни карусели, ни приветственного видео, ни всплывающих окон.

### 2.2. Руководство и сотрудники на внутреннем показе

Получают ссылку от Заказчика. Смотрят, верно ли показано предприятие, и подтверждают свои карточки.

**Целевой сценарий:** открыть «Про підприємство» → увидеть свою карточку (фото, ФИО, должность, телефон, биография по клику) → подтвердить или назвать правку.

**Требования:**
1. Карточка руководителя по образцу чинной страницы (`claude/04_vymohy.md`, раздел 5, «Что взять», п. 1): фото, ФИО, должность, телефон, раскрывающаяся биография.
2. Подтверждение каждым из пяти фиксируется в журнале решений (13.3) — это и есть согласие на публикацию фото и биографии (`claude/04_vymohy.md`, раздел 3).
3. До подтверждения карточка публикуется только в объёме, разрешённом законом: должность и оплата труда руководителя и заместителей не являются информацией с ограниченным доступом; фото и биографии остальных — только с согласия.
4. Страница понятна без объяснений: разделы названы так, как их называют на предприятии.

### 2.3. Редактор без технических навыков

Сотрудник предприятия. Задача: исправить телефон, добавить вакансию, скрыть неподходящую карточку ленты, заменить фото.

**Целевой сценарий:** вход в `/admin` → раздел → список → форма → сохранение → изменение видно на сайте.

**Требования:**
1. Все подписи интерфейса на украинском, без технического жаргона (инструкции проекта, п. 7).
2. Редактор не может удалить ничего безвозвратно без подтверждения и не имеет доступа к учётным записям, секретам и служебным разделам.
3. При спящем бэкенде вход занимает до минуты; интерфейс показывает, что идёт ожидание, а не ошибку (8.7).
4. Как правка попадает на публичные страницы, описано в 8.5; редактор видит результат своего действия без обращения к разработчику.
5. Ошибки объясняются действием, а не кодом: «Файл більший за 2 МБ», а не «413».

### 2.4. Владелец (Заказчик)

Заводит учётные записи, принимает версии, следит за состоянием синхронизаций, восстанавливает данные из резервной копии.

**Целевой сценарий:** открыть служебный раздел админки → увидеть время и результат последней синхронизации по каждому источнику → при сбое понять, какой источник и почему.

**Требования:** права по матрице 9.1; служебные эндпоинты 8.6; журнал действий 9.7; порядок резервного копирования и восстановления 9.6.

### 3.2. URL-схема, языковые префиксы, канонические адреса, базовый путь

1. **Базовый путь.** Адрес сайта — `[адрес сайта: Butcherok.github.io/uzn-desna или свой домен — Заказчик]`. От него зависят параметр `base` сборщика, канонические адреса, `sitemap.xml` и абсолютные ссылки. До ответа сборка настраивается на путь из переменной окружения с подпутём проекта по умолчанию; смена адреса не должна требовать правок в коде страниц.
2. **Слаги** — английские, в нижнем регистре, слова через дефис: `about`, `public-info`, `services`, `where-to-ask`, `contacts`, `news`, `tenders`, `jobs`, `green-zones`, `equipment`. Слаги не переводятся при смене языка.
3. **Завершающая косая черта** обязательна: каждая страница — папка с `index.html`. Адрес без косой черты перенаправляется на адрес с ней средствами сборщика.
4. **Языковые префиксы.** Украинский — без префикса (`/services/`), английский — с префиксом `/en/` (`/en/services/`). Украинская версия загружается по умолчанию: это требование Закона № 2704-VIII, ст. 27 ч. 6 (`claude/04_vymohy.md`, раздел 3). Автоматического определения языка браузера нет, перенаправлений по языку нет: язык меняется только переключателем.
5. **Канонический адрес** указывается на каждой странице, абсолютным адресом своей языковой версии.
6. **Связь версий:** `hreflang` для `uk` и `en` плюс `x-default`, указывающий на украинскую версию. Для страницы, не имеющей английского перевода, `hreflang` для `en` не указывается, а переключатель ведёт на английскую главную.
7. **Параметры в адресах не используются:** состояние страниц в адресной строке не хранится, фильтров и постраничной навигации в версиях 1–3 нет.
8. **Адреса не меняются** после публикации. Если смена понадобится, старый адрес остаётся страницей-перенаправлением.

### 3.3. Служебное поведение: 404, пустой блок, `noindex`

**404.** Файл `404.html` в корне сборки; GitHub Pages отдаёт его на несуществующие адреса. Содержимое: заголовок «Сторінку не знайдено», одно предложение, ссылки на Головну, «Куди звертатися» и «Контакти», телефон приймальні. Код ответа задаёт хостинг, страница его не подменяет.

**Три состояния блока** (термины 1.3). Правило общее для всех страниц:

| Состояние | Что показывает публичная страница |
|---|---|
| Данные | Содержимое блока |
| Пусто | Короткий текст «Поки немає» (для ленты и новостей — «Новин поки немає») либо блок скрывается, если это указано в требованиях страницы |
| Неизвестно | Последние сохранённые данные с подписью даты получения. Если сохранённых данных нет — «Дані тимчасово недоступні» |

Запрещено: показывать «пусто» при ошибке источника; показывать пустой заголовок блока без содержимого; очищать ранее сохранённые данные из-за ошибки (бриф, 5.4, п. 5).

**Закрытие от поисковиков** (бриф, раздел 1). До решения руководства:
1. На каждой странице `<meta name="robots" content="noindex, nofollow">`.
2. `robots.txt` с `Disallow: /` для всех агентов.
3. `sitemap.xml` в версиях 1–3 не публикуется.
4. Снятие закрытия — отдельной задачей одним PR после решения руководства, порядок в 11.4.
Публичный репозиторий и адрес GitHub Pages остаются доступными любому по ссылке: `noindex` скрывает сайт от поиска, но не делает его закрытым (бриф, риск 3). Поэтому согласия на фото и биографии нужны уже на внутреннем показе (`claude/04_vymohy.md`, раздел 4).

## 4. Постраничные требования

Единый шаблон описания каждой страницы: **назначение → блоки → обязательные поля → источник данных → поведение при отсутствии данных → версия.**

Общее для всех страниц:
- Один заголовок первого уровня на страницу, совпадающий с названием раздела в меню.
- Телефоны — ссылки `tel:`, адреса электронной почты — ссылки `mailto:` с защитой от ботов (5.4).
- Внешние ссылки открываются в новой вкладке и помечены как внешние.
- Все изображения имеют `alt` (5.3).
- Данные, помеченные **[ПЕРЕВІРИТИ]** в паспорте, выводятся только после подтверждения Заказчиком; до этого поле остаётся пустым.

### 4.1. Головна

**Назначение.** За один экран показать, чьё это предприятие, и увести жителя в нужный раздел.

**Блоки.**
1. Первый экран: название предприятия, рисунок-баннер, кнопка «Куди звертатися».
2. Лозунг — одна строка под баннером, перед карточками разделов.
3. Быстрые переходы: карточки разделов.
4. Блок «Новини галузі» — три последние карточки тематической ленты 4.8 (версия 2; решение Заказчика 20.11.2026). Ленты нет — блока нет. Посты Facebook на главной не выводятся.
5. Контакты кратко: адрес, телефон приймальні, часы работы.

**Обязательные поля.** Название; лозунг; рисунок-баннер.

Лозунг — «Озеленення й догляд — наша щоденна робота» (решение Заказчика 18.11.2026). Абзаца-представления на главной нет: назначение предприятия раскрывает страница «Про підприємство», а на главной его место занимает лозунг.

**Блока цифр на главной нет** (решение Заказчика 18.11.2026). Публикуются только те показатели, у которых сходится арифметика, и живут они там, где уже выводятся, — на «Про підприємство». Площадь обслуживания: итог чинної сторінки 1143,917556 га не сходится с собственной разбивкой по девяти категориям, сумма которых 1116,638956 га; паспортная цифра 1139,4242 га помечена **[ПЕРЕВІРИТИ актуальність]** и разбивкой не подтверждена. **При отсутствии данных.** Ошибка API — последние сохранённые карточки с датой получения (состояние «неизвестно», 3.3). Постов нет — «Новин поки немає» и ссылка на страницу Facebook. Запасной путь при длительном отказе API: встраиваемый блок страницы или ручное добавление новости в админке (бриф, 5.2).

**Версия.** 2.

## 5. Контент и языки

### 5.1. Правило двух языков

1. Украинский — язык по умолчанию, загружается без префикса (3.2). Это требование закона, а не предпочтение (`claude/04_vymohy.md`, раздел 3).
2. Английская версия по объёму не превышает украинскую (4.13).
3. Любой текст на сайте либо существует в двух языках, либо явно помечен «тільки українською» (инструкции проекта, п. 7).
4. Исключение: чужие публикации в тематической ленте выводятся на языке оригинала (украинский или английский) без перевода; подпись карточки сообщает язык (бриф, раздел 3).
5. Названия разделов, подписи кнопок и сообщения об ошибках переводятся вместе со страницей; непереведённая подпись в английской версии — дефект.
6. Единицы и форматы: даты `ДД.ММ.РРРР`, телефоны `+38 (0XX) XXX-XX-XX`, суммы с пробелом между тысячами и символом «грн» после числа.

### 5.2. Правила текстов

1. **Заголовок карточки Facebook** — первая строка или первое предложение поста; длиннее 90 символов обрезается по границе слова с многоточием.
2. **Обрезка текста до 200 символов** — по границе слова, с многоточием; обрезка никогда не делается посреди слова или ссылки.
3. **Отрывок сторонней публикации** выводится только у источников, явно разрешающих частичное использование (бриф, 5.4, п. 7). Для остальных карточка состоит из заголовка, источника, даты и ссылки.
4. **Тексты разделов** пишет Заказчик или разработчик по его тезисам; придуманных сведений о предприятии в текстах нет (инструкции проекта, п. 5).
5. **Язык текстов для жителя** — обиходный: «впало дерево», а не «виявлено аварійне насадження».
6. **Длина:** описание услуги и сценария — до двух предложений; справка о предприятии — до 1500 знаков с разбивкой на абзацы.

### 5.3. Изображения

1. **Форматы:** WebP основной, JPEG запасной для фото; SVG для логотипа и иконок. PNG — только там, где нужна прозрачность без вектора.
2. **Размеры:** изображение первого экрана — не шире 1600 px; фото карточек — 800 px по длинной стороне; фото руководства — 400×400 px. Каждое изображение отдаётся в двух плотностях. Баннер первого экрана — один исходник 1600×900 на состояние темы, выводится в трёх соотношениях через `object-fit: cover` (4:3 до 600 px, 3:2 до 1024 px, 21:9 от 1024 px); поэтому всё, что должно быть видно на любом экране, лежит внутри центральных 75 % ширины и 76 % высоты кадра, а по краям — только то, что не жалко обрезать (решение 020). У настоящего баннера из Мануса за центральные 75 % ширины выходит по ~140 px внешнего крыла обоих зданий; входы и стеклянный свод внутри — принято Заказчиком 19.11.2026 (решение 022).
3. **Вес:** суммарный вес изображений первого экрана не превышает бюджет из 11.2.
4. **`alt`** обязателен и описывает содержимое, а не файл: «Робітники висаджують кущі у парку», а не «photo1». Декоративное изображение получает пустой `alt`.
5. **Права.** Чужие логотипы, фото и иллюстрации без права использования не применяются (инструкции проекта, п. 8). Фото объектов — собственные снимки предприятия. Фото источников тематической ленты не выводятся.
6. **Логотип.** Логотипом предприятия принят наш рисунок — знак «дерево в колі» (решение Заказчика 18.11.2026; своего файла логотипа у предприятия нет). Знак существует в двух формах одного рисунка: **Д4** в шапке рядом с текстовым названием — круг радиусом 15, крона из трёх долей с неровным верхним краем, короткий ствол, прорезь ствола в кроне от её нижнего края до середины, тонкая полоска земли от края до края круга; **Д2** на значке вкладки — тот же рисунок, увеличенный в 16/15, круг занимает весь квадрат. Крона намеренно не круглая: ровный круг на стволе над полоской читается как лампочка (решение Заказчика 18.11.2026). Знак двухцветный, оба значения — из палитры (дизайн-система, раздел 3). Формы, значения и классы — `claude/11_dyzain-systema.md`, разделы 1, 3 и 7; построение и отброшенные варианты — `docs/decisions/015-tree-mark.md` и `docs/decisions/016-tree-mark-shape.md`. Заглушка 29 этим закрыта.
7. **Фото предприятия:** `[фото: объекты района, техника, работы, коллектив, с подтверждённым правом использования — Заказчик]`. До их получения страницы выводятся без фотоблоков, а не с фотографиями со стороны.
8. **Иллюстрации категорий ленты** — собственные, по категории карточки (4.8).
9. **Шрифты.** Пара принята 13.11.2026 и изменена 20.11.2026: Fixel Display (MacPaw) для заголовков и Inter для текста, оба под лицензией SIL Open Font License 1.1, подключаются локальными файлами WOFF2 с домена сайта, без сторонних шрифтовых сервисов. Засечковая Literata в заголовках отброшена: читалась как Times New Roman. Подмножество «кириллица + латиница», переменная ось начертаний, суммарно 55,6 КБ на два файла против бюджета 120 КБ (11.2). Значения, имена семейств и места файлов — `claude/11_dyzain-systema.md`, раздел 2; основание — `docs/decisions/028-heading-font-fixel.md`.
10. **Значок вкладки (favicon).** Файл `site/public/favicon.svg`, 32×32, подключается в оболочке страниц строкой `<link rel="icon" type="image/svg+xml" sizes="any">` с адресом через базовый путь: корневой `/favicon.ico` до страниц проекта не доходит, сайт живёт в подпапке. К адресу добавлена метка версии (сейчас `?v=3`): кэш значков браузера держит значок дольше страницы, и без смены адреса браузер остаётся на прежнем файле. Метка увеличивается на единицу при каждой правке рисунка значка. На значке — знак предприятия «дерево в колі» в форме Д2 (п. 6): тот же рисунок, что в шапке, с кругом во весь квадрат. Цвета внутри файла написаны числами: файл значка — отдельный документ, слой токенов на него не действует (дизайн-система, раздел 1, п. 4). Запасной растровый файл не подключается; показ значка в Safari проверяет Заказчик на своих устройствах.

### 5.4. Персональные данные

1. **Что публикуется о руководстве.** Должность и сведения об оплате труда руководителя и заместителей не являются информацией с ограниченным доступом (Закон № 2297-VI, ст. 5 ч. 3). Биография по закону обязательна только для руководителя. Фото и биографии остальных — только с согласия человека (Цивільний кодекс, ст. 307, 308) — **[ПРОВЕРИТЬ]** по первоисточнику, как указано в `claude/04_vymohy.md`, раздел 7.
2. **Как фиксируется согласие.** Каждый из пяти видит свою карточку на внутреннем показе и подтверждает её. Подтверждение записывается в журнал решений (13.3): дата, кто подтвердил, какой состав полей. Отдельных бумаг не оформляется. То, что сведения уже опубликованы на чинной странице, согласия не заменяет: оно давалось Київзеленбуду для его сайта.
3. **До подтверждения** карточка публикуется в том объёме, в каком эти же сведения уже оприлюднені органом управління на чинній сторінці підприємства: ФИО, должность, фото и биография (решение Заказчика 17.11.2026, `docs/decisions/011-leaders-page-data.md`). Отметка подтверждения собирается на внутреннем показе и записывается в 13.3; просьба убрать своё — правка одной записи данных. Сведения, которых на чинній сторінці нет, до подтверждения не публикуются.
4. **Состав и должности** перед публикацией сверяются с Заказчиком: чинную страницу предприятие не контролирует, данные там могут быть устаревшими.
5. **`[состав пяти человек, подтверждающих свои карточки — Заказчик]`**.
6. **Сотрудники помимо руководства** на сайте не называются: ни ФИО, ни личных телефонов. В карточках услуг, сценариев и вакансий указываются телефоны подразделений, а не людей.
7. **E-mail скрыт от ботов:** адрес собирается в разметке из частей и выводится скриптом либо хранится в атрибуте в закодированном виде. Простого текстового `mailto:` в исходном коде страницы нет. Требование относится и к адресу в подвале.
8. **Данные посетителей не собираются:** форм нет, аналитики нет, сторонних скриптов слежения нет, файлы cookie не устанавливаются. Это проверяется при приёмке версии 1.

## 6. Модель данных

Модель описана в двух разрезах: что хранится в БД (редактируемое человеком) и что хранится в репозитории в виде JSON (полученное от внешних источников и выгруженное для сборки). Полный перечень полей по каждой сущности — приложение 13.1; здесь — назначение, ключ, особенности и версия.

### 6.1. Общие правила: идентификаторы, даты, языковые поля, черновик/опубликовано, created/updated

1. **Два хранилища и одно направление потока.** Единственный источник правды для редактируемого контента — БД MongoDB Atlas, доступная только бэкенду. Единственный источник данных для публичных страниц — JSON-файлы в репозитории (6.6). Данные движутся в одну сторону: БД → выгрузка → JSON → сборка. Публичные страницы к БД и к бэкенду не обращаются никогда (2.1, требование 3).
2. **Идентификаторы.** В БД — `_id` (ObjectId), в JSON наружу не выводится. У сущностей, на которые ссылаются страницы, есть `slug`: латиница, нижний регистр, дефисы, уникален в пределах сущности, после первой публикации не меняется. Внешние записи ключуются естественным ключом источника: пост Facebook — `postId`, закупка — `tenderID`, карточка ленты — `urlKey` (нормализованный адрес: нижний регистр схемы и хоста, без `www`, без параметров отслеживания `utm_*`, `fbclid`, без завершающей косой черты).
3. **Даты.** Хранение и JSON — строка ISO 8601 в UTC (`2026-11-13T09:33:07.871Z`). Приведение к киевскому времени и к формату `ДД.ММ.РРРР` (5.1, п. 6) выполняется при сборке, не при хранении. Поля `createdAt` и `updatedAt` есть у каждой редактируемой сущности, заполняются сервером, редактору не показываются на правку.
4. **Языковые поля.** Текстовое поле, у которого есть английская версия, хранится объектом `{ "uk": "…", "en": "…" }`. `uk` обязательно; `en` допускает отсутствие или пустую строку — это одно и то же состояние «перевода нет». Правило 4.13 проверяется при сборке: английская страница собирается, только если переведены все обязательные поля её сущностей. Какие поля языковые — в 13.1.
5. **Черновик и публикация.** У публикуемых сущностей поле `status`: `draft` или `published`. В выгрузку (6.6) попадают только `published`. Перевод сущности в `draft` — штатный способ убрать карточку с сайта, не удаляя её.
6. **Порядок вывода.** У сущностей с ручной сортировкой (`Leader`, `Service`, `Scenario`, `PublicDoc`, `GreenZone`, `Equipment`, `Vacancy`) есть целое `order`; сортировка по возрастанию, при равенстве — по `createdAt` по возрастанию. Редактор меняет порядок перетаскиванием или вводом числа (9.3). У внешних записей порядок задан датой, `order` нет.
7. **Удаление — мягкое.** `deletedAt` вместо физического удаления; запись с `deletedAt` не выгружается и в списках админки показывается только в «Кошику» 30 дней, затем удаляется плановой задачей. Физическое удаление доступно только владельцу и только из «Кошика» (2.3, требование 2).
8. **Валидация.** Схемы описаны один раз (Zod) и используются и бэкендом при записи, и сборкой при чтении JSON (10.2). Телефон хранится как `+380XXXXXXXXX`, маска применяется при выводе. Адреса — абсолютные `https://`. Строки обрезаются по длине, заданной в 13.1; молчаливого обрезания при сохранении нет — форма сообщает о переполнении до отправки.
9. **Бинарных данных в БД нет.** Изображения и документы лежат в репозитории (8.4); в сущностях хранится путь вида `media/leaders/karp-ye-a-7f3a1c2b.jpg` и подписи (`alt`, автор, права). Это следствие лимита бесплатного кластера — 0,5 ГБ на документы и индексы (отчёт 06, раздел 3).
10. **Что в модели не появляется никогда:** персональные данные посетителей, адреса электронной почты посетителей, формы обращений, аналитика, cookie-профили (5.4, п. 8), пароли в открытом виде, токены внешних сервисов (7.2, 10.5).

Три решения разработчика по этому перечню:

1. **`FeedRule` добавлен к перечню оглавления 6.2.** Основание: отчёт 08, раздел 6 («правится в админке — решение для ТЗ») и раздел 9, п. 4. Без этой сущности правка словаря требует PR, то есть разработчика, что противоречит смыслу раздела. Структура разделов ТЗ при этом не меняется.
2. **`Contact` отделён от `Enterprise`,** хотя телефонов немного: карточки услуг и сценариев ссылаются на контактную точку (`contactId`), и смена номера приймальні должна быть одной правкой, а не правкой тридцати карточек.
3. **Цифры главной — в `StaticBlock`, а не отдельная сущность.** Блок цифр выводится целиком или скрывается целиком (4.1), поэтому отдельные записи на показатель не нужны.

### 6.3. Синхронизируемые: FacebookPost, FeedItem, Tender, SyncState

Эти записи человеком не правятся и в БД не хранятся. Их пишет синхронизация (7.1) прямо в JSON репозитория; предыдущая версия файла и есть кэш, о котором говорит бриф, 5.1, п. 3: требование «кэш не в памяти процесса Render» выполняется тем, что синхронизацию выполняет не бэкенд, а GitHub Actions (отчёт 06, раздел 7, п. 1). В БД от внешних записей живёт только решение редактора — `Moderation` (6.4).

| Запись | Ключ | Поля | Хранится | Выводится |
|---|---|---|---|---|
| `FacebookPost` | `postId` | `title` (выведен по правилу 5.2, п. 1), `excerpt` (≤200 символов), `imagePath` (копия фото у нас), `permalinkUrl`, `createdTime`, `fetchedAt`, `manual` | 20 последних | 6 на «Новини» |
| `FeedItem` | `urlKey` | `url`, `title`, `sourceId`, `sourceName`, `sourceDomain`, `lang` (`uk`/`en`), `publishedAt`, `excerpt` (только у разрешающих источников), `category`, `via` (`tag`/`rss`/`gdelt`), `fetchedAt` | 40 последних по дате публикации | 8 на «Новини», 3 на главной |
| `Tender` | `tenderID` | `title`, `status`, `amount`, `currency`, `vatIncluded`, `datePublished` (разобран из номера), `tenderEndDate`, `url` | 20 последних | 10, остальное — по ссылке на Prozorro |
| `SyncState` | `source` | `lastRunAt`, `lastSuccessAt`, `result` (`ok`/`partial`/`error`), `errorCode`, `errorMessage` (с маскированием, 7.5), `itemsFetched`, `itemsNew`, `consecutiveFailures` | По одной записи на источник | Только в админке (2.4) |

Правила, общие для всех трёх видов внешних записей:

1. **Поля источника не переписываются.** Заголовок, дата и адрес сохраняются как отданы источником; наше — только обрезка по правилам 5.2 и выбор иллюстрации по категории. Редактор не может править текст чужой публикации (9.5).
2. **Фото Facebook копируются к себе** при синхронизации и не подключаются ссылкой на домены Meta: срок жизни ссылок `full_picture` не подтверждён (отчёт 07, раздел 4). Фото источников тематической ленты не скачиваются и не выводятся вовсе (отчёт 08, раздел 5).
3. **Вытеснение, а не удаление по возрасту.** При превышении лимита хранения уходит самая старая запись. Для ленты это условие работоспособности при 1,85 карточки в неделю (отчёт 08, раздел 12.4).
4. **Скрытая запись остаётся в файле** с признаком `hidden`, выставленным при сборке по данным `Moderation`, и не выводится. Так она не возвращается при следующей синхронизации (4.8).
5. **`manual: true`** — ручная новость, добавленная в админке как запасной путь при отказе API Meta (4.7, бриф 5.2). Такие записи синхронизация не затирает: она пишет только записи с `manual: false`.

### 6.4. Доступ: User, Session, ActionLog

| Сущность | Поля | Правила |
|---|---|---|
| `User` | `login` (латиница, не адрес электронной почты), `displayName`, `passwordHash`, `role` (`owner`/`editor`), `active`, `mustChangePassword`, `createdAt`, `lastLoginAt`, `passwordChangedAt` | Пароль хранится только хэшем (инструкции проекта, п. 6): bcrypt, cost 12. Выбор bcrypt, а не argon2id — память бесплатного экземпляра Render не указана в документации и не проверена (отчёт 06, «Что не проверено»), а argon2id требует её осознанно. Электронная почта в учётной записи не хранится: восстановления по почте нет (9.2), а лишние персональные данные в публичном проекте не нужны |

### 6.5. Три состояния выдачи: данные / пусто / неизвестно

Состояние — не вычисление страницы, а поле данных. Каждый блок, зависящий от внешнего источника, представлен в JSON объектом:

```
{ "state": "data" | "empty" | "unknown",
  "items": [ … ],
  "fetchedAt": "…",        // когда получены показываемые записи
  "lastSuccessAt": "…",    // когда источник отвечал в последний раз
  "sourceErrors": [ { "source": "…", "code": "…" } ] }
```

Правила записи состояния (их исполняет синхронизация, а не страница):

| Что произошло | `state` | Что делается с `items` |
|---|---|---|
| Источник ответил, записи есть | `data` | Переписываются полученными |
| Источник ответил, записей нет | `empty` | Очищаются |
| Источник недоступен, ответил ошибкой или неразбираемым телом | `unknown` | **Остаются прежними**, `fetchedAt` не меняется |
| Часть источников ленты ответила, часть нет | `data` | Обновляются по ответившим; `sourceErrors` перечисляет остальные |

Страница выводит состояние по правилу 3.3 и не имеет права подменять `unknown` на `empty`. Проверка этого — отдельный пункт чек-листа версии 2 (12.3): синхронизация прогоняется с намеренно испорченным адресом источника, страница должна показать прежние карточки с датой получения.

### 6.6. Формат статических данных для фронта: JSON в репозитории, схема и её версия

1. **Место.** Каталог `data/` в корне репозитория. Файлы: `enterprise.json`, `contacts.json`, `leaders.json`, `services.json`, `scenarios.json`, `public-docs.json`, `vacancies.json`, `green-zones.json`, `equipment.json`, `static-blocks.json`, `feed-rules.json` — выгрузка из БД; `facebook.json`, `feed.json`, `tenders.json`, `sync-state.json` — результат синхронизации.
2. **Конверт файла** одинаков для всех:

```
{ "schemaVersion": 1,
  "generatedAt": "2026-11-13T09:33:07.871Z",
  "source": "admin-export" | "sync",
  "state": "data" | "empty" | "unknown",   // только у файлов синхронизации
  "items": [ … ] }
```

3. **Версия схемы.** `schemaVersion` повышается при любом несовместимом изменении полей. Сборка проверяет каждый файл схемой Zod и при неизвестной версии или непрохождении проверки **падает с внятной ошибкой**, а не собирает страницу молча без блока. Это прямой перенос урока «ошибка внешнего API ≠ пустой результат» (бриф, раздел 6) на собственные данные.
4. **Размер.** Один файл — до 200 КБ. Изображений и двоичных данных в JSON нет, только пути (6.1, п. 9).
5. **Коммиты.** Файлы `data/` коммитятся так же, как код: история правок контента — это история git, отдельного журнала версий контента в БД не ведётся. Коммит синхронизации делается только при изменении содержимого; пустых коммитов нет.
6. **Версия 1 живёт на тех же файлах.** До появления админки `data/*.json` правятся руками в PR. Поэтому форматом JSON нельзя распоряжаться свободно: он публичный интерфейс между версиями 1 и 2, и его изменение — повышение `schemaVersion` с правкой выгрузки.

## 7. Интеграции и синхронизация

### 7.1. Общая схема: GitHub Actions → JSON в репозиторий → сборка Pages; бэкенд нужен только админке

Схема принята по отчёту 06, раздел 7, п. 1 (решение «без будильника»); внешний пингер и самопинг отброшены 13.11.2026 (бриф, 5.1, п. 2).

**Три независимых пути.**

| Путь | Чем запускается | Что делает | Нужен ли бэкенд |
|---|---|---|---|
| Синхронизация внешних источников (`sync-external`) | Расписание, 3 раза в сутки | Читает ленту, Facebook и Prozorro → пишет `facebook.json`, `feed.json`, `tenders.json`, `sync-state.json`, копии фото постов → коммит в ветку `sync-data` → при изменении данных сайта запускает `deploy` (решение 023) | Нет |
| Публикация правок (`publish-content`) | Кнопка «Опублікувати зміни» в админке (8.5) и первое число месяца по расписанию | Запрашивает у бэкенда выгрузку (`GET /export`) → пишет редактируемые файлы `data/` → коммит | Да, на 1–2 минуты |
| Сборка и деплой (`deploy`) | Любой коммит в `main`; запуск из `sync-external`; ежедневно по расписанию — для «Актуально до» вакансий (4.10) | Берёт `data/sync/` из ветки `sync-data`, собирает сайт и публикует на GitHub Pages | Нет |

**Почему так, а не «бэкенд сам синхронизирует».** Бесплатный экземпляр Render спит через 15 минут и просыпается около минуты, файловая система и память не переживают сон, а часы (750 в месяц на всё рабочее пространство) при постоянно разбуженном сервисе расходуются почти полностью — 744 из 750 (отчёт 06, разделы 1 и 2). При выбранной схеме Render будит только работа редактора и публикация: расход — десятки часов в месяц вместо 744 (расчёт в 7.6).

**Следствия, обязательные к исполнению.**
1. Токены внешних сервисов лежат в секретах GitHub Actions, а не в переменных Render (отчёт 07, раздел 9, п. 3).
2. Синхронизация не обращается к бэкенду и к БД вовсе: ключей, кроме токена Facebook, у неё нет; у ленты и Prozorro ключей нет совсем.
3. Отказ Render не влияет ни на публичные страницы, ни на синхронизацию — только на админку.
4. Отказ синхронизации не влияет на правки редактора: это разные рабочие процессы и разные файлы.
5. Расписание рабочих процессов в публичном репозитории может быть отключено после 60 дней без активности, а запуски по расписанию могут задерживаться (отчёт 06, раздел 4) — **[ПРОВЕРИТЬ]**, считаются ли активностью коммиты самой синхронизации. Страховка: ручной запуск (`workflow_dispatch`) доступен владельцу всегда, а состояние последней синхронизации видно в админке (8.6).
6. **Синхронизация не пишет в `main`** (решение 023). Push из рабочего процесса с `GITHUB_TOKEN` в защищённую `main` отклоняется, а коммит, сделанный этим токеном, не запускает рабочие процессы по `push` (документация GitHub: события `GITHUB_TOKEN`, кроме `workflow_dispatch` и `repository_dispatch`, новых прогонов не создают). Поэтому данные живут в ветке `sync-data`, `sync-external` запускает `deploy` вручную, а в `main` лежит заготовка `data/sync/tenders.json` с `state: unknown`.

### 7.2. Facebook: права токена страницы, частота, фолбэк

1. **Схема получения токена — вариант А отчёта 07, раздел 6:** сотрудник-администратор один раз выдаёт Заказчику доступ к странице, дальше Заказчик сам выпускает и перевыпускает токен страницы со своего аккаунта разработчика. Причина: риск «новости остановились до участия сотрудника» (бриф, риск 1) сводится к одному разовому действию.
2. **Токен** — страницы, полученный из долгоживущего токена пользователя, без срока действия (отчёт 07, раздел 4). Хранится в секрете `FB_PAGE_TOKEN`, идентификатор страницы — в секрете `FB_PAGE_ID`. Секрет приложения в секретах не хранится: он нужен только при выпуске токена.
3. **Права запрашиваются минимальные:** `pages_show_list`, `pages_read_engagement`, `pages_read_user_content`. Права на публикацию (`pages_manage_*`) не запрашиваются, пока API без них не откажет (отчёт 07, раздел 3): сайту запись на страницу не нужна, а утечка токена с правом публикации опаснее.
4. **Запрос:** `GET /v{версия}/{page-id}/feed?fields=message,full_picture,permalink_url,created_time&limit=10`. Номер версии API — в конфигурации, не в коде запроса (отчёт 07, раздел 9, п. 4).
5. **Частота** — вместе с лентой, 3 раза в сутки: отдельного расписания не нужно, лимитов Meta такой объём не касается.
6. **Проверка приложения Meta и верификация бизнеса не требуются** при схеме «права выдаёт человек с ролью в приложении» (отчёт 07, раздел 5, итог). Приложение остаётся в режиме разработки. Остаточная неопределённость — тип приложения и то, какой уровень доступа к странице даёт нужные задачи: закрывается живым прогоном по плану отчёта 07, раздел 8, до начала работ по версии 2. Заглушка 21 реестра до прогона остаётся.
7. **Фото.** `full_picture` скачивается при синхронизации, приводится к WebP при сборке и кладётся в `media/fb/{postId}`. Большая сторона у Meta не более 720 px (отчёт 07, раздел 3) — это и есть предел качества блока. Файлы постов, вышедших за пределы 20 хранимых, удаляются тем же коммитом.
8. **Ошибки токена** (`190` с подкодами `458`, `460`, `492`) означают, что человек сменил пароль, отозвал доступ или потерял роль на странице (отчёт 07, раздел 4). Поведение: `state: unknown`, прежние карточки остаются, `consecutiveFailures` растёт, на третьем подряд сбое рабочий процесс завершается с ошибкой — владелец получает письмо GitHub о падении. Отдельного канала уведомлений не создаётся: с бесплатного Render почту отправить нельзя (отчёт 06, раздел 1, п. 5), а письмо о падении рабочего процесса бесплатно и не требует секретов.
9. **Перевыпуск токена** — короткая инструкция в `docs/runbook-facebook-token.md`: что открыть, что нажать, какой секрет заменить, как убедиться, что блок ожил. Пишется в той же задаче, что и интеграция: она понадобится при первой же смене пароля.
10. **Запасные пути, в порядке применения:** ручная новость в админке (`manual: true`, 6.3) → встраиваемый блок Page Plugin. Page Plugin применяется только как аварийная замена: он тянет сторонний скрипт в страницу, что противоречит требованию скорости первого экрана (отчёт 07, раздел 7).

### 7.5. Отказоустойчивость: ошибка источника не очищает блок, TTL-кэш в БД, общий Promise, каталог ошибок, лог с маскированием

1. **Главное правило** — 6.5: ошибка превращается в `state: unknown` с сохранением прежних записей, а не в пустой блок. Нарушение — дефект приёмки (12.3).
2. **Повторы.** Три попытки на запрос, паузы 1 с, 5 с, 25 с, таймаут одного запроса 15 с, бюджет шага 10 минут. Для GDELT (если включён) пауза между запросами не меньше 5 с, повторы с нарастанием до минут и кэш прошлой выдачи: при живом прогоне адрес был заблокирован ошибкой 429 на 12 с лишним минут, а раннеры GitHub работают с общих адресов (отчёт 08, раздел 12.3).
3. **Частичный отказ — не падение.** Прогон, в котором часть источников ответила, завершается успешно и пишет `sourceErrors`. Прогон завершается ошибкой (и владелец получает письмо GitHub) в трёх случаях: все источники одного файла недоступны; один источник недоступен третий прогон подряд; результат не проходит проверку схемой. Первое правило действует для файлов с несколькими источниками (лента); для файла с одним источником (`tenders.json`, `facebook.json`) действует второе — иначе первый же сбой слал бы письмо (решение 023).
4. **TTL-кэш и общий Promise на параллельные вызовы** (перенос из проекта бота, бриф, раздел 6) применяются на двух уровнях: в скрипте синхронизации — чтобы один адрес не запрашивался дважды в одном прогоне; в слое `gateway` бэкенда — чтобы повторные обращения админки за одним и тем же (выгрузка, статусы) не множили работу. Срок жизни кэша в бэкенде — 60 секунд, кэш в памяти процесса, а не в БД: он не обязан переживать сон Render, а переживать его нечему (отчёт 06, раздел 2).
5. **Каталог ошибок.** Код ошибки — из закрытого перечня, не свободный текст:

| Код | Когда | Что видит посетитель | Что делает владелец |
|---|---|---|---|
| `SRC_TIMEOUT` | Источник не ответил за 15 с | Прежние карточки | Ничего; смотрит повтор следующего прогона |
| `SRC_HTTP_4XX` | Источник ответил 4xx, кроме 429 | Прежние карточки | Проверяет адрес источника: возможна смена вёрстки или адреса |
| `SRC_HTTP_5XX` | Источник ответил 5xx | Прежние карточки | Ничего |
| `SRC_RATE_LIMIT` | 429 | Прежние карточки | Ничего; при трёх прогонах подряд — снизить частоту |
| `SRC_PARSE` | Тело получено, но не разобрано | Прежние карточки | Проверяет вёрстку источника (риск 6 брифа) |
| `TOKEN_INVALID` | Ошибка 190 Meta | Прежние карточки блока Facebook | Перевыпускает токен по `docs/runbook-facebook-token.md` |
| `EXPORT_UNAVAILABLE` | Бэкенд не ответил на `GET /export` | Прежние данные страниц, сайт цел | Повторяет публикацию из админки |
| `SCHEMA_MISMATCH` | JSON не проходит проверку схемой | Сборка не публикуется, на сайте остаётся прежняя версия | Обращается к разработчику |

6. **Лог с маскированием.** В вывод рабочего процесса и в `sync-state.json` не попадают: токены, строка подключения к БД, значения заголовков авторизации, cookie. Маскирование по списку имён секретов и по шаблону — значение заменяется на `***` целиком, без «последних четырёх символов». Тела ответов источников в лог не пишутся, пишется длина и код ответа. Проверка маскирования — пункт чек-листа версии 2.
7. **Деградация блоков по отдельности.** Отказ ленты не влияет на блок Facebook, отказ Prozorro — на новости; каждый блок читает свой файл и своё состояние. Общего «аварийного режима сайта» нет.

## 8. API бэкенда

Бэкенд версии 2 — только API. Интерфейс админки входит в ту же статическую сборку, что и сайт, и отдаётся с GitHub Pages по адресу `/admin` (4.14); с Render он получает данные запросами из браузера. Отсюда два следствия: обращения к API межсайтовые (8.1, CORS), а в собранном коде админки нет и не может быть секретов — ни токенов, ни строки подключения к БД.

### 8.1. Общие правила: база, формат ошибок и кодов, CORS, ограничение частоты

1. **База:** `https://[адрес сервиса бэкенда на Render — Заказчик и разработчик]/api/v1`. Номер версии в пути обязателен: он позволит менять формат, не ломая уже собранную админку.
2. **Формат.** Запрос и ответ — JSON, UTF-8. Успех: тело ответа — объект сущности или `{ "items": [...], "total": n }`. Пустой успех — 204 без тела.
3. **Формат ошибки** один для всех эндпоинтов:

```
{ "error": { "code": "VALIDATION_FAILED",
             "message": "Телефон має бути у форматі +380XXXXXXXXX",
             "fields": { "phone": "Невірний формат" } } }
```

`code` — из закрытого перечня, `message` — готовый к показу текст на украинском, без кодов и жаргона (2.3, требование 5). Коды: `UNAUTHENTICATED`, `FORBIDDEN`, `NOT_FOUND`, `VALIDATION_FAILED`, `CONFLICT`, `FILE_TOO_LARGE`, `UNSUPPORTED_FILE_TYPE`, `RATE_LIMITED`, `PUBLISH_IN_PROGRESS`, `GITHUB_UNAVAILABLE`, `DB_UNAVAILABLE`, `INTERNAL`.
4. **Коды HTTP.** 200, 201, 204; 400 — неразбираемое тело; 401 — нет или истекла сессия; 403 — роли не хватает; 404; 409 — конфликт (занятый `slug`, идущая публикация); 413 — файл больше предела; 422 — не прошло проверку схемой; 429 — ограничение частоты; 500; 503 — БД недоступна.
5. **CORS.** Разрешён единственный источник — адрес сайта на Pages, плюс `http://localhost:4321` в режиме разработки. `Access-Control-Allow-Credentials: true`, список методов и заголовков закрытый. Подстановочного `*` нет ни в одном окружении: с `credentials` он и не работает, и открывает API любому сайту.
6. **Ограничение частоты.** 60 запросов в минуту на сессию; 10 попыток входа за 15 минут на пару «логин + адрес»; 5 публикаций в час. Ответ 429 с заголовком `Retry-After` и сообщением «Занадто багато спроб. Спробуйте за хвилину».
7. **Размеры.** Тело JSON — до 1 МБ; загрузка файла — до 2 МБ для изображений и до 10 МБ для документов (8.4).
8. **Публичных эндпоинтов чтения контента нет.** Публичные страницы читают JSON из сборки (6.6) и к API не обращаются. Без авторизации доступны только `GET /health` и `GET /robots.txt` (8.6).
9. **Идемпотентность.** `PATCH` и `PUT` по идентификатору можно повторять безопасно. Состояние не меняется методом `GET` ни в одном эндпоинте.
10. **Часовой пояс и форматы** — по 6.1, п. 3: в API ходят только даты UTC в ISO 8601.

### 8.2. Аутентификация и сессии

| Эндпоинт | Метод | Кто | Что делает |
|---|---|---|---|
| `/auth/login` | POST | Все | Принимает `{ login, password }`; при успехе ставит cookie сессии и отдаёт `{ login, displayName, role, mustChangePassword }` |
| `/auth/logout` | POST | Вошедшие | Удаляет сессию на сервере и гасит cookie |
| `/auth/me` | GET | Вошедшие | Отдаёт текущего пользователя; админка вызывает первым делом при открытии |
| `/auth/password` | POST | Вошедшие | Смена своего пароля: `{ currentPassword, newPassword }` |

1. **Cookie сессии:** `HttpOnly`, `Secure`, `SameSite=Lax`, срок 12 часов. Токен в cookie — случайные 32 байта; в БД хранится только его хэш (6.4). В `localStorage` и `sessionStorage` не хранится ничего (бриф, раздел 6: «не берём хранение в localStorage»).
2. **Защита от подделки запросов:** `SameSite=Lax` плюс обязательный заголовок `X-Requested-With: uzn-admin` на всех изменяющих запросах; изменяющих `GET`-запросов нет (8.1, п. 9).
3. **Сообщение при неудаче** одно и то же для неверного логина и неверного пароля: «Невірний логін або пароль» — чтобы перебор не подсказывал, какие логины существуют.
4. **Пароль:** не короче 12 символов, проверка по короткому списку очевидных паролей; требований «заглавная, цифра, символ» нет — они не усиливают пароль, а усложняют жизнь редактору. Хэш — bcrypt, cost 12 (6.4).
5. **Восстановления пароля по почте нет:** с бесплатного Render почта не отправляется (отчёт 06, раздел 1, п. 5). Порядок возврата доступа — 9.2.
6. **`mustChangePassword`** закрывает всё, кроме `/auth/me` и `/auth/password`: редактор, которому владелец выдал временный пароль, обязан сменить его до первой правки.

### 8.3. Эндпоинты контента по сущностям 6.2

Единый набор для каждой списочной сущности (`contacts`, `leaders`, `services`, `scenarios`, `vacancies`, `public-docs`, `green-zones`, `equipment`, `static-blocks`):

| Эндпоинт | Метод | Что делает |
|---|---|---|
| `/{сущность}` | GET | Список, включая черновики и (по параметру `trashed=1`) удалённые |
| `/{сущность}` | POST | Создание; `status` по умолчанию `draft` |
| `/{сущность}/{id}` | GET, PATCH | Чтение и частичная правка |
| `/{сущность}/{id}` | DELETE | Мягкое удаление: ставит `deletedAt` |
| `/{сущность}/{id}/restore` | POST | Возврат из «Кошика» |
| `/{сущность}/{id}/status` | POST | `{ "status": "published" | "draft" }` |
| `/{сущность}/order` | PATCH | `{ "ids": [...] }` — новый порядок целиком |

Синглтоны (`enterprise`, `feed-rules`) имеют только `GET` и `PATCH`. Модерация внешних карточек:

| Эндпоинт | Метод | Что делает |
|---|---|---|
| `/moderation` | GET | Список скрытых записей с ключами и датами |
| `/moderation/{kind}/{key}` | PUT | `{ "hidden": true | false }`, где `kind` — `facebook` или `feed` |
| `/news/manual` | POST, PATCH, DELETE | Ручная новость (`manual: true`, 6.3) — запасной путь при отказе API Meta |

Правила для всех эндпоинтов контента:
1. Тело проверяется той же схемой Zod, что применяется при сборке (6.1, п. 8). Непрошедшее — 422 с перечнем полей.
2. `slug` формируется из названия автоматически и правится только владельцем; после первой публикации смена `slug` требует подтверждения и записывается в журнал действий (3.2, п. 8).
3. Перевод в `published` проверяет обязательные поля публикации: карточка руководителя без `confirmedAt` в `published` не переводится (4.2, 5.4, п. 3), сценарий без телефона — тоже (4.5).
4. Правка не попадает на сайт сама: нужна публикация (8.5). Ответ на успешную правку содержит `pendingChanges` — сколько правок ждёт публикации.

### 8.4. Загрузка изображений и документов

| Эндпоинт | Метод | Что делает |
|---|---|---|
| `/uploads` | POST | `multipart/form-data`: файл, `entity`, `slug`, `alt`. Отдаёт `{ path, bytes, width, height }` |
| `/uploads` | GET | Список загруженных файлов с указанием, кто и где их использует |
| `/uploads/{path}` | DELETE | Удаление неиспользуемого файла; используемый — 409 |

1. **Допустимые типы:** `image/jpeg`, `image/png`, `image/webp` — всем; `image/svg+xml` — только владельцу и только после очистки разметки от скриптов и внешних ссылок; `application/pdf` и файлы Word — для `PublicDoc` версии 2.
2. **Пределы:** изображение до 2 МБ, документ до 10 МБ. Сообщение об отказе — действием: «Файл більший за 2 МБ. Зменшіть зображення й спробуйте ще раз» (2.3, требование 5).
3. **Проверка на сервере** — по фактическому содержимому (сигнатуре файла), а не по расширению и не по заголовку `Content-Type`.
4. **Метаданные EXIF удаляются** при приёме: в снимках с телефона могут быть координаты и имя автора, которые незачем публиковать.
5. **Имя файла задаёт сервер:** `media/{entity}/{slug}-{8 знаков хэша}.{расширение}`. Исходное имя не используется: в нём бывают кириллица, пробелы и даты.
6. **Хранение — репозиторий** (решение 7.6). Бэкенд записывает файл в репозиторий через API GitHub тем же токеном, которым запускает публикацию (8.5). В БД остаётся только путь.
7. **Приведение к форматам и размерам (5.3) выполняется при сборке, а не на Render:** память и процессор бесплатного экземпляра в документации не указаны и не проверены (отчёт 06, «Что не проверено»), а обработка изображений — самая тяжёлая операция в проекте. В репозиторий кладётся оригинал, в сборку идут производные WebP в двух плотностях.
8. **Неиспользуемые файлы.** Сборка составляет отчёт о файлах, на которые никто не ссылается; автоматического удаления нет — удаляет владелец вручную (9.1).

### 8.5. Публикация: как правка редактора попадает в статическую сборку

| Эндпоинт | Метод | Кто | Что делает |
|---|---|---|---|
| `/publish` | POST | Владелец, редактор | Проверяет все `published` записи схемами; запускает рабочий процесс `publish-content` в GitHub; отдаёт `{ runId, startedAt }` |
| `/publish/status` | GET | Владелец, редактор | Последняя публикация: время, результат, кто запустил, ссылка на прогон |
| `/export` | GET | Только по токену | Отдаёт полный набор редактируемых данных (только `published`), модерацию и словарь — в формате конверта 6.6 |

**Порядок.**
1. Редактор правит данные — они ложатся в БД и на сайте пока не видны. Индикатор в админке показывает число неопубликованных правок.
2. Редактор нажимает «Опублікувати зміни». Бэкенд проверяет данные схемами и отказывает с перечнем проблемных записей, если что-то не проходит: неверные данные не должны доходить до сборки, где они обрушат её (6.6, п. 3).
3. Бэкенд вызывает `workflow_dispatch` рабочего процесса `publish-content`. Токен GitHub — в переменных окружения Render, с правом запуска рабочих процессов только этого репозитория; в репозиторий, в код админки и в чат он не попадает.
4. Рабочий процесс запрашивает `GET /export` с токеном выгрузки (общий секрет между Render и Actions), пишет файлы `data/`, коммитит их при наличии изменений и тем самым запускает `deploy`.
5. Если `GET /export` не отвечает (Render спит дольше ожидаемого или остановлен), прогон завершается с кодом `EXPORT_UNAVAILABLE`, файлы `data/` остаются прежними, сайт цел (7.5).
6. Админка показывает: «Зміни з'являться на сайті протягом кількох хвилин» и далее результат по `/publish/status`.

**Две одновременные публикации не запускаются:** вторая получает 409 `PUBLISH_IN_PROGRESS` и сообщение «Публікація вже триває». Скрытие карточки ленты и поста Facebook (9.5) предлагает публикацию сразу после действия: иначе редактор решит, что кнопка не сработала.

### 8.6. Служебные: состояние сервиса, статусы синхронизаций

| Эндпоинт | Метод | Кто | Что отдаёт |
|---|---|---|---|
| `/health` | GET | Без авторизации | `{ status, dbConnected, startedAt, version }`. Ни секретов, ни сведений о среде. Используется админкой для раннего пробуждения (8.7), не пингером |
| `/robots.txt` | GET | Без авторизации | `User-agent: *` и `Disallow: /`. Обязателен: Render сам отвечает «disallow all» только спящему сервису, бодрый отвечает сам (отчёт 06, раздел 2) |
| `/system/info` | GET | Владелец | Версия сборки бэкенда, время запуска процесса, число записей по сущностям, время последней публикации, число неопубликованных правок |
| `/system/log` | GET | Владелец | Журнал действий (9.7) с фильтрами по пользователю и датам |

**Статусы синхронизаций бэкенд не отдаёт.** Админка читает `data/sync-state.json` из той же сборки, в которой живёт сама, — своим же источником, без межсайтового запроса и без участия Render. Причина: синхронизация с бэкендом не связана (7.1), и состояние источников должно быть видно даже при остановленном Render.

### 8.7. Поведение админки при спящем Render (ожидание до минуты)

1. **Раннее пробуждение.** Страница `/admin` при открытии, до любых действий человека, отправляет `GET /health`. Пока редактор читает форму входа и набирает логин, сервис просыпается: ожидание около минуты (отчёт 06, раздел 2) накладывается на набор пароля, а не следует за ним.
2. **Что видно при ожидании.** Через 3 секунды без ответа — строка «Сервіс прокидається, це займає до хвилини» и индикатор ожидания. Это не ошибка и не предупреждение: сообщение нейтральное, кнопка остаётся активной.
3. **Таймауты.** Клиентский таймаут 90 секунд, затем один автоматический повтор, затем сообщение «Не вдалося з'єднатися. Спробуйте ще раз» с кнопкой повтора. Код ответа в сообщение не выводится (2.3, требование 5).
4. **Ничего не теряется.** При неудачном сохранении форма остаётся заполненной, введённый текст не сбрасывается и не очищается; повтор отправляет те же данные. Сохранения черновиков в браузере нет (бриф, раздел 6).
5. **Будильника нет** (бриф, 5.1, п. 2). Единственное обращение к `/health` — то, что делает открытая админка, и только пока она открыта.
6. **Первая операция после пробуждения** может ждать ещё соединения с Atlas: при 503 `DB_UNAVAILABLE` админка повторяет запрос один раз через 3 секунды, прежде чем показать ошибку.

## 9. Роли и админка

### 9.1. Матрица прав «владелец» / «редактор» по сущностям

Словарь ленты отдан владельцу, а не редактору, по одной причине: он управляет тем, что публикуется на сайте автоматически и без просмотра человеком. Скрыть лишнюю карточку редактор может всегда — это обратимое действие с видимым результатом.

### 9.2. Вход, хэш пароля, смена пароля, выход

1. **Вход** — по 8.2: логин и пароль, cookie сессии, срок 12 часов.
2. **Первый владелец создаётся без интерфейса и без консоли.** Shell на бесплатном Render недоступен (отчёт 06, раздел 2), поэтому при запуске бэкенд проверяет: если учётных записей нет и заданы переменные окружения `BOOTSTRAP_OWNER_LOGIN` и `BOOTSTRAP_OWNER_PASSWORD_HASH`, он создаёт владельца и пишет об этом в журнал. Хэш Заказчик получает локально командой `npm run hash-password`; пароль в открытом виде в переменные окружения не попадает. После создания переменные удаляются из настроек сервиса. `[логин владельца и хэш первичного пароля — Заказчик]`.
3. **Смена своего пароля** — в админке, с вводом текущего. Смена отзывает все остальные сессии этого пользователя.
4. **Сброс пароля редактора** делает владелец: задаёт временный пароль, запись получает `mustChangePassword`. Канала «восстановить по почте» нет и не планируется в версиях 1–3 (8.2, п. 5).
5. **Если владелец потерял свой пароль,** порядок один: разработчик меняет хэш в БД напрямую либо включается повторный `BOOTSTRAP` после удаления записи владельца. Порядок описывается в `docs/runbook-admin-access.md` — вместе с тем, как убедиться, что действие попало в журнал.
6. **Выход** удаляет серверную сессию. Закрытие вкладки сессию не удаляет: срок истекает сам.
7. **Блокировка** (`active: false`) гасит сессии немедленно и сохраняет записи журнала: учётные записи уволившихся не удаляются, а блокируются.

### 9.3. Структура интерфейса: разделы, список, форма, предпросмотр

**Разделы меню админки** (подписи — украинские, как на сайте): Підприємство · Контакти · Керівництво · Послуги · Куди звертатися · Публічна інформація · Вакансії · Зелені зони · Техніка · Блоки сторінок · Новини підприємства · Тематична стрічка · Кошик · *Службове* (только владельцу: Користувачі, Словник стрічки, Стан синхронізацій, Журнал дій, Резервні копії).

**Список записей.** Название, состояние («Чернетка» / «Опубліковано»), дата изменения, кнопки «Редагувати» и «Приховати». Сортировка — по `order`, переключатель «показати чернетки». Поиска по админке нет: записей единицы и десятки.

**Форма.** Один столбец, поля в порядке важности, обязательные помечены, под каждым — короткая подсказка, что это и где появится на сайте. Языковые поля — двумя закладками `Українська / English`; закладка `English` помечена как необязательная, и её незаполненность не мешает сохранению (6.1, п. 4). Кнопки: «Зберегти», «Зберегти й опублікувати», «Скасувати». Уход со страницы при несохранённых правках — с подтверждением.

**Предпросмотр.** Карточка или блок рисуются в админке теми же React-компонентами, что и на сайте (10.2), с данными из формы. Предпросмотра целой страницы со сервера нет: сайт статический, страница появляется только после сборки. Это ограничение называется в подсказке: «Так виглядатиме картка на сайті».

**Полоса публикации** закреплена внизу экрана: число неопубликованных правок, время последней публикации, кнопка «Опублікувати зміни», после нажатия — состояние по `/publish/status`.

### 9.4. Требования UX для нетехнического редактора

1. **Язык.** Все подписи, подсказки, кнопки и сообщения — на украинском. Слов «валидация», «деплой», «API», «JSON», «токен», «слаг» в интерфейсе нет. Технические понятия либо названы по-человечески («адреса сторінки»), либо скрыты от редактора.
2. **Ошибки — действием, а не кодом** (2.3, требование 5), с указанием, что именно сделать. Поле с ошибкой подсвечивается и получает фокус.
3. **Подтверждения** — только у необратимого и у массового: удаление, снятие с публикации, смена порядка целиком. У обратимого (скрыть карточку) подтверждения нет, есть отмена.
4. **«Кошик»** на 30 дней с кнопкой «Відновити»: ошибочное удаление исправляет сам редактор (6.1, п. 7).
5. **Состояние сохранения видно всегда:** «Не збережено» рядом с кнопкой, пока есть правки. Автосохранения нет — и оно не обещается, чтобы редактор не полагался на то, чего нет.
6. **Мобильное и планшетное** использование: админка работает на планшете, тач-цели не меньше 44×44 px, формы в один столбец (11.1). Полноценная правка с телефона не требуется, но вход, скрытие карточки и правка телефона с телефона работают.
7. **Доступность** — те же требования, что к публичным страницам (11.3): работа с клавиатуры, видимый фокус, контраст.
8. **Страница помощи** `/admin/help` с шестью короткими рецептами: исправить телефон · додати вакансію · приховати картку · замінити фото · опублікувати зміни · що робити, якщо адмінка довго відкривається. Рецепт — три-четыре шага, без скриншотов, которые устареют.
9. **Инструкция редактору** (бриф, риск 4) — это и есть `/admin/help` плюс один лист на печать; отдельного документа в базе знаний не создаётся.

### 9.5. Модерация импортированного: скрытие карточки ленты и поста Facebook

1. **Одно действие.** В разделах «Новини підприємства» и «Тематична стрічка» каждая карточка имеет кнопку «Приховати»; скрытая переносится в конец списка с пометкой и кнопкой «Повернути».
2. **Скрытие — только у нас.** В источнике запись не меняется: ни в Facebook, ни на сайте издателя (2.5). Подсказка в интерфейсе говорит это прямым текстом.
3. **Скрытие переживает синхронизацию.** Решение хранится в `Moderation` по естественному ключу записи (6.3, 6.4) и применяется при каждой сборке. Скрытая карточка не возвращается при следующем прогоне (4.8).
4. **Текст чужой публикации не правится.** Редактор не может изменить заголовок, дату, источник и отрывок карточки ленты: это чужой текст, и его правка превратила бы цитату в нашу переделку. Доступно только скрытие и выбор категории (от неё зависит наша иллюстрация).
5. **Посты Facebook** правятся так же: только скрытие. Нужен другой текст — используется ручная новость (6.3).
6. **Скрытие предлагает публикацию** сразу: без неё карточка остаётся на сайте до следующей публикации (8.5).
7. **Все действия модерации** попадают в журнал (9.7): кто скрыл, что и когда.

### 9.6. Резервные копии БД и порядок восстановления

Бесплатных резервных копий у кластера Atlas нет: функция платная, требует карты и находится в закрытом предпросмотре (отчёт 06, раздел 1, п. 3). Поэтому копия делается своими силами.

1. **Что копируется.** Только БД: сущности 6.2 и 6.4. Изображения, документы и JSON-данные лежат в репозитории и уже имеют историю в git — в копию они не входят.
2. **Чем.** `mongodump` из рабочего процесса `backup` (отчёт 06, раздел 7, п. 3), раз в месяц и по кнопке владельца.
3. **Шифрование обязательно.** Дамп содержит хэши паролей и данные сотрудников, а репозиторий и артефакты прогонов публичного репозитория доступны любому. Поэтому дамп шифруется (`age`, открытый ключ — в репозитории, закрытый — только у владельца) и только после этого выкладывается артефактом прогона. **Нешифрованный дамп не попадает ни в репозиторий, ни в артефакт, ни в чат ни при каких условиях.** `[где владелец хранит закрытый ключ шифрования копий — Заказчик]`.
4. **Срок хранения артефактов** в публичном репозитории — **[ПРОВЕРИТЬ]** перед внедрением; владелец скачивает копию и хранит три последние у себя, не полагаясь на срок GitHub.
5. **Когда копия делается обязательно, помимо расписания:** перед изменением схемы данных (повышением `schemaVersion`), перед обновлением зависимостей бэкенда, перед передачей админки редактору.
6. **Порядок восстановления** (в `docs/runbook-restore.md`, проверяется один раз на пустой БД до передачи админки редактору): расшифровать копию → создать пустую БД или очистить текущую → `mongorestore` → войти в админку и сверить число записей по сущностям с `/system/info` → опубликовать изменения и убедиться, что сайт собрался.
7. **Ограничения `mongodump` на бесплатном кластере** известны: база `admin` и часть опций недоступны (отчёт 06, раздел 3) — в порядке восстановления они не используются.
8. **Проверка копии** — не «файл создался», а «из копии поднялась рабочая БД»: прогон восстановления выполняется хотя бы один раз и записывается в журнал решений.

### 9.7. Журнал действий

1. **Что записывается.** Вход и выход, неудачные попытки входа, создание, правка, удаление и восстановление записи, смена состояния публикации, загрузка и удаление файла, скрытие и возврат карточки, запуск публикации, правка словаря, действия с учётными записями, создание и восстановление резервной копии.
2. **Состав записи:** время, кто, действие, сущность и её идентификатор, результат, краткие детали. Паролей, токенов и строк подключения в деталях нет (7.5, п. 6).
3. **Запись только добавляется.** Из интерфейса журнал не правится и не чистится; плановая чистка удаляет записи старше 180 дней.
4. **Кто видит:** владелец (9.1), фильтры по пользователю и датам, вывод постранично.
5. **Чего в журнале нет.** Подтверждения карточек руководства (5.4, п. 2) записываются в журнал решений ТЗ (13.3), а не здесь: это решение по продукту и согласие человека, а не действие в интерфейсе. Журнал действий фиксирует, кто поставил отметку в админке, но доказательством согласия служит запись 13.3.

### 9.8. Вопросы к постройке админки версии 2

Записаны решением Заказчика 18.11.2026 как условия будущей задачи. В версию 1 не входят и сейчас не строятся; матрица прав 9.1 ими не расширяется — она уже покрывает всё наполнение.

1. **Формат текста в полях.** Обычный текст плюс закрытый набор: полужирный, ссылка, список. Набор размечается своей разметкой, а не хранится готовой разметкой страницы. Визуальный редактор с готовой разметкой не применяется: он даёт редактору чужие стили, вставку из Word и разметку, которой нет в дизайн-системе.
2. **Проверка начала адреса ссылок.** Принимаются только `http`, `https`, `tel` и `mailto`. Остальные начала адреса отклоняются с подсказкой на украинском (9.4, п. 2).
3. **Загрузка изображений.** До постройки решить: какие форматы принимаются, какой предел веса, где хранится файл при бюджете 0 грн, как снимаются метаданные снимка. Без ответа на все четыре вопроса загрузка не строится.
4. **Границы правки.** Редактору не даётся управление вёрсткой, цветами, шрифтами и порядком блоков сверх задуманного задачей: это значения дизайн-системы, а не наполнение.

## 10. Стек, структура кода и сборка

### 10.1. Выбор сборщика: Astro с React-компонентами

**Решение: Astro, компоненты на React, TypeScript.** Один вариант рекомендуется, два рассмотренных отброшены.

Причина в одном предложении: публичные страницы обязаны открываться при спящем бэкенде и держать бюджет первого экрана (2.1, требование 3; 11.2), а Astro по умолчанию отдаёт HTML без JavaScript и подключает React только там, где он нужен.

Что при этом получается штатными средствами, а не кодом проекта:

| Требование ТЗ | Чем закрывается в Astro |
|---|---|
| Папка с `index.html` и обязательной завершающей косой чертой (3.2, п. 3) | `build.format: 'directory'`, `trailingSlash: 'always'` |
| Базовый путь, меняемый без правок страниц (3.2, п. 1) | параметр `base` из переменной окружения |
| Префикс `/en/`, `hreflang`, канонические адреса (3.2, пп. 4–6) | маршрутизация по каталогам и штатная i18n-настройка |
| Чтение `data/*.json` при сборке с проверкой схемой (6.6, п. 3) | импорт JSON в коде страницы, проверка Zod, падение сборки при несоответствии |
| `404.html` в корне сборки (3.3) | страница `src/pages/404.astro` |
| Минимум JS на публичных страницах (11.2) | островная модель: `client:*` только на раскрывающемся меню, остальное — HTML |
| Админка в той же сборке по `/admin` (8.0) | одна страница-оболочка с React-приложением |

Отброшено:
1. **Vite с пререндером** (плагин SSG или ручной прогон маршрутов). Всё перечисленное в таблице пришлось бы собирать самостоятельно: маршруты страниц, пререндер, завершающая косая черта, языковые префиксы, разделение бюджета публичных страниц и админки. Это код без выгоды: тот же результат, больше мест для ошибки.
2. **Чистый Vite + React как одностраничное приложение.** Отброшено жёстко: один `index.html` не даёт ни отдельных адресов страниц, ни работающего `404.html`, а первый экран без JavaScript не отображается вовсе — это прямо противоречит 2.1 и 11.7.
3. **Eleventy (11ty).** Отброшено 13.11.2026 при разборе альтернатив с Заказчиком: ноль JS и отдельные адреса он даёт, но React-компонентов у него нет, поэтому требование 9.3 — предпросмотр карточки в админке теми же компонентами, что на сайте — выполняется только дублированием вёрстки.
4. **Next.js со статическим экспортом.** Отброшено там же: требование 9.3 выполняет, но клиентский рантайм React едет на каждую публичную страницу, а бюджет первого экрана — 50 КБ JS (11.2) при требовании работать с выключенным JavaScript (11.7, п. 4).

Бэкенд версии 2 — **Node.js и Fastify** (решение разработчика): проверка тел запросов схемами и структурный лог встроены, что снимает ручную обвязку вокруг правил 8.1 и 7.5, п. 6. Express рассматривался и отброшен только по этой причине; на требования ТЗ выбор не влияет.

**Версии зависимостей в ТЗ не записываются.** Они фиксируются в `package-lock.json` первым PR по актуальным на тот момент выпускам: номер, записанный в ТЗ, устареет раньше, чем будет написана версия 1. Исключение — среда исполнения: Node.js берётся активной LTS-версии, одна и та же в `.nvmrc`, в CI и на Render; номер проверяется по первоисточнику перед первым PR — `[активная LTS-версия Node.js на момент первого PR — проверка разработчиком]`. Нижняя граница известна: Astro требует Node.js не ниже 22.22.0.

### 10.2. Слои `components / domain / gateway / config`, строгий `tsconfig`

**Пакеты рабочего пространства npm** (одно из решений брифа, раздел 6: монорепозиторий):

| Пакет | Что внутри | Где исполняется |
|---|---|---|
| `shared` | Схемы Zod всех сущностей и конвертов файлов, типы, чистые функции формата (обрезка текста, маска телефона, даты, `urlKey`) | Везде |
| `site` | Astro-страницы, React-компоненты, админка | Сборка и браузер |
| `server` | API бэкенда | Render |
| `scripts` | Синхронизация источников и выгрузка для рабочих процессов | Раннеры GitHub Actions |

**Слои внутри `site` и `server`** — перенос из проекта бота (бриф, раздел 6):

| Слой | Что можно | Что запрещено |
|---|---|---|
| `components` | Разметка, стили, вывод переданных данных | Любой ввод-вывод, прямое чтение JSON, обращения к сети |
| `domain` | Чистые функции и типы: правила словаря ленты, три состояния выдачи, обрезка, сортировка, проверка полей публикации | Импорт из `gateway`, `components`, доступ к сети, БД, файлам, времени и случайным числам иначе как параметром |
| `gateway` | Весь ввод-вывод: Mongo, `fetch` к источникам, API GitHub, файловая система, cookie | Бизнес-правила: они живут в `domain` |
| `config` | Единый объект настроек: таймауты, частоты, лимиты, адреса, пределы длин | Секреты в коде; значения, разбросанные по файлам |

1. **Направление зависимостей:** `components → domain`, `gateway → domain`, `routes/pages → gateway + domain`. `domain` не зависит ни от кого. Нарушение ловится правилом линтера (запрет импортов по шаблону пути), а не договорённостью.
2. **Схемы Zod — единственное описание полей** (6.1, п. 8). Их читают: бэкенд при записи, сборка при чтении `data/*.json`, тесты. Второго описания полей (в типах вручную) нет: типы выводятся из схем.
3. **Переменные окружения проверяются при старте** (`fail-fast`): отсутствие обязательной переменной останавливает процесс с внятным сообщением. Это прямой урок отчёта 02, раздел 4: в боте правило было записано, а в коде отсутствовало.
4. **`tsconfig` строгий:** `strict`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, ESM. `any` в сигнатурах экспортируемых функций не допускается; внешние данные входят в код только через схему.
5. **Один файл — одна ответственность.** Файл длиннее 400 строк — повод разделить; вторая похожая возможность делается общим ядром, а не копией первой (урок отчёта 02, 5.3, п. 4).

### 10.3. Структура репозитория и `docs/`

### 10.5. Деплой: GitHub Pages, Render, переменные и секреты

**Сайт.** Публикуется рабочим процессом `deploy` (сборка → артефакт → публикация Pages), а не из ветки: сборка должна проверяться схемами и бюджетом до публикации. Файлы на Pages вручную не заливаются ни разу — иначе на Pages окажется версия, которой нет в истории. Запуск самого рабочего процесса кнопкой (событие `workflow_dispatch`) разрешён и ручной выкладкой не считается: процесс собирает то, что лежит в `main`, и проходит те же проверки (уточнение 19.11.2026, версия 3.14; прежняя формулировка «деплой вручную не выполняется ни разу» запрещала и то и другое вместе). Ограничения Pages по размеру сайта и частоте сборок — заглушка 41.

**Публичность репозитория — условие работоспособности, а не предпочтение.** GitHub Pages на тарифе Free доступен только в публичных репозиториях; защита ветки `main` и наборы правил на Free — тоже только в публичных; минуты Actions для публичных репозиториев не расходуются из включённого объёма. Приватный репозиторий при бюджете 0 грн (1.2) лишает проект деплоя и защиты ветки. Проверено по документации GitHub 13.11.2026; репозиторий сделан публичным в тот же день.

**Бэкенд.** Сервис на Render из каталога `server`, запуск собранного файла, проверка состояния — `GET /health` (8.6). Адрес сервиса — заглушка 34.

**Переменные и секреты.** Репозиторий публичный, поэтому правило одно: ни одного значения секрета в репозитории, в сборке и в чате.

| Где | Что хранится | Почему там |
|---|---|---|
| Переменные окружения Render | `MONGODB_URI`, `GITHUB_TOKEN` (права: запуск рабочих процессов и запись содержимого только этого репозитория), `EXPORT_TOKEN`, `SITE_ORIGIN`, при первом запуске — `BOOTSTRAP_OWNER_LOGIN` и `BOOTSTRAP_OWNER_PASSWORD_HASH` | Нужны только бэкенду; переменные `BOOTSTRAP_*` удаляются после создания владельца (9.2, п. 2) |
| Секреты GitHub Actions | `FB_PAGE_TOKEN`, `FB_PAGE_ID`, `EXPORT_TOKEN`, `MONGODB_URI` (только для `backup`) | Синхронизация и копия идут с раннеров, а не с Render (7.1, следствие 1) |

1. **В собранный фронт не попадает ничего, кроме базового пути и адреса API.** Проверяется шагом `secrets:check`: поиск в сборке имён секретов и характерных образцов значений.
2. **`.env` в `.gitignore`**, в репозитории только `.env.example` без значений.
3. **Список доступа Atlas.** Копия БД делается с раннеров GitHub Actions, адреса которых заранее неизвестны, поэтому список доступа открывается для любого адреса (`0.0.0.0/0`), а защита переносится на пароль длиной не менее 32 знаков и пользователя БД с правами только на одну базу. Диапазоны адресов Render (заглушка 43) этого не меняют: ограничить список только ими нельзя, пока копию делает раннер.
4. **Утечка токена закрывается перевыпуском**, а не правкой кода: порядок — в `docs/runbook-facebook-token.md`.

### 10.6. Ветки, Conventional Commits, один PR на задачу, слияние только владельцем

1. **Ветки:** `main` и рабочие `feat/…`, `fix/…`, `docs/…`, `chore/…`, `ci/…` — обычными словами, без буквенных кодов (бриф, раздел 6: «обычные слова вместо буквенных кодов»). Прямой push в `main` запрещён правилом защиты ветки.
2. **Коммиты:** Conventional Commits с областью, по-английски: `feat(services): add service cards`. Имена файлов и ветвей — английские (инструкции проекта, п. 2).
3. **Один PR на задачу.** Описание PR: что сделано, что намеренно не тронуто, как проверить. Найденное попутно в PR не исправляется — оно записывается и показывается Заказчику (инструкции проекта, п. 4).
4. **Слияние — squash,** один PR превращается в один коммит в `main`: история `main` читается как список выполненных задач. Слияние выполняет только владелец и только при зелёном CI (бриф, раздел 6).
5. **В том же PR обязательно** обновляется `docs/project-context.md`, а при решении по коду — файл в `docs/decisions/`. Это условие закрытия задачи (12.1), а не пожелание: в боте документы отстали от кода на месяц.
6. **Шаблон PR заполняется.** В боте шаблон существовал и не использовался (отчёт 02, 5.2); здесь незаполненный шаблон — причина не сливать PR.
7. **Теги** `v1.0.0`, `v2.0.0`, `v3.0.0` ставятся на коммит, которым Заказчик принял соответствующую версию состава (1.2); запись о содержании — в `CHANGELOG.md`.

## 11. Нефункциональные требования

### 11.1. Мобильная вёрстка первой, точки перелома, размеры тач-целей

1. **Порядок проектирования и правила CSS — от узкого к широкому** (`min-width`). Макет версии для телефона создаётся первым и принимается первым (инструкции проекта, п. 7).
2. **Точки перелома:** 360 px — базовая; 600 px — планшет; 1024 px — десктоп. Ширина содержимого не превышает 1200 px, поля не меньше 16 px на телефоне.
3. **Нижняя граница работоспособности — 320 px:** горизонтальной прокрутки нет, ничего не обрезается.
4. **Тач-цели не меньше 44×44 px**, расстояние между соседними целями не меньше 8 px. Телефон в карточке — цель полной ширины карточки, а не подчёркнутое слово. Это строже уровня AA: 44×44 — критерий 2.5.5 Target Size (Enhanced) уровня AAA, тогда как на AA действует 2.5.8 Target Size (Minimum) с минимумом 24×24. Повышенное требование принято сознательно: главный сценарий жителя (2.1) — нажать телефон с телефона, одной рукой, на улице.
   **Исключение: ссылка внутри текста** (решение Заказчика 19.11.2026). Требование 44×44 относится к управляющим элементам — кнопкам, пунктам меню, ссылке-логотипу, телефону в карточке, заголовку-ссылке и прочим ссылкам, стоящим отдельно от текста. Ссылка внутри предложения, пункта перечня или ячейки таблицы под него не подпадает: её высота равна высоте строки, а растягивание разогнало бы междустрочный интервал в абзаце. То же исключение («Inline») записано в самих критериях 2.5.5 и 2.5.8. Проверяется это так: если ссылку можно поднять до 44 px, не меняя набора окружающего текста, она управляющий элемент и требование к ней применяется.
5. **Текст:** базовый размер 16 px, межстрочный интервал не меньше 1,5, длина строки 60–75 знаков на десктопе. Масштабирование страницы не запрещается: `maximum-scale` и `user-scalable=no` не применяются (это требование доступности, 11.3).
6. **Таблицы на телефоне** (реквизиты предприятия, 4.2) выводятся парами «подпись — значение», а не горизонтальной прокруткой.
7. **Проверка — на трёх размерах:** 360×640, 768×1024, 1366×768, плюс один реальный телефон Заказчика.

### 11.2. Производительность: бюджет первого экрана и целевые метрики

**Бюджет первого экрана главной страницы на телефоне.** Значения — после сжатия при передаче, суммарно по типу файлов:

| Что | Предел |
|---|---|
| HTML | 50 КБ |
| CSS, всего | 30 КБ, из них критический встроенный — не более 14 КБ |
| JavaScript на публичной странице | 50 КБ |
| Изображения первого экрана, суммарно | 250 КБ, главное изображение — не более 150 КБ |
| Шрифты | 120 КБ: подмножество «кириллица + латиница», WOFF2 (дизайн-система 1.0 расходует 65,1 КБ) |
| **Первый экран целиком** | **500 КБ** |
| Число сетевых запросов первого экрана | 20 |
| Сторонних доменов в запросах | 0 |
| Вес любой публичной страницы целиком | 1 МБ |
| JavaScript админки (бюджет первого экрана на неё не распространяется) | 300 КБ |

**Целевые метрики.** Lighthouse, режим телефона с эмуляцией медленной сети, медиана из трёх прогонов на опубликованной версии:

| Метрика | Цель | Порог приёмки |
|---|---|---|
| Largest Contentful Paint | ≤ 2,0 с | 2,5 с |
| Cumulative Layout Shift | ≤ 0,05 | 0,10 |
| Interaction to Next Paint | ≤ 100 мс | 200 мс |
| Total Blocking Time | ≤ 150 мс | 300 мс |
| Time to First Byte | ≤ 0,8 с | 1,2 с |
| Lighthouse Performance | ≥ 95 | 90 |
| Lighthouse Accessibility | ≥ 95 | 90 |
| Lighthouse Best Practices | ≥ 95 | 90 |

Пороги приёмки по LCP, CLS и INP совпадают с границей «хорошо» в Core Web Vitals (LCP ≤2500 мс, INP ≤200 мс, CLS ≤0,1 по 75-му процентилю); цели поставлены строже, чтобы ухудшение съедало запас, а не сразу роняло приёмку. TBT включён в таблицу потому, что Lighthouse работает без пользователя и INP измерить не может, отдавая вместо него Total Blocking Time. Бюджет первого экрана — наше решение, выведенное обратным счётом от LCP на медленном мобильном канале, а не отраслевой стандарт.

Lighthouse SEO не проверяется: сайт закрыт от поисковиков (3.3), оценка будет искажена `noindex`. Проверка возвращается в приёмку при снятии закрытия (11.4).

**Правила, которыми бюджет держится:**
1. Изображения — WebP, в двух плотностях через `srcset`, с обязательными `width` и `height` (иначе сдвиг макета).
2. Главное изображение первого экрана — `fetchpriority="high"`, без отложенной загрузки; всё ниже первого экрана — `loading="lazy"`.
3. Шрифты — локальные файлы, `font-display: swap`, `preload` только для одного начертания. Сторонние шрифтовые сервисы не подключаются (5.3, п. 9).
4. Сторонних скриптов, аналитики, встроенных карт и встраиваемых блоков соцсетей в первом экране нет ни на одной странице (4.6, 7.2, п. 10).
5. Шрифты, CSS и JS отдаются с того же домена, что и страница.
6. Шаг `budget:check` в CI сверяет вес файлов сборки с таблицей бюджета и роняет проверку при превышении: иначе бюджет держится обещаниями. Изображения он считает с 19.11.2026 (решение 020; до этого не считал вовсе, и строка «Изображения первого экрана» в таблице выше не проверялась ничем). Правила счёта: **один элемент — один файл** (у `<img>` и `<picture>` берётся самый тяжёлый кандидат, который элемент может запросить, и считается один раз: браузер скачивает одну ступень `srcset` и одну из двух тем, а не все); **две контрольные ширины** — 360 px, то есть телефон, которому и посвящена таблица бюджета, и 1920 px справочно, причём атрибут `media` у `<source>` читается, поэтому боковые предметы с `media="(min-width: 768px)"` в телефонную строку не попадают; **`loading="lazy"` — не первый экран**, такая картинка выводится отдельной строкой отчёта, чем правило п. 2 и становится проверяемым; **вес — как есть, без gzip**, потому что WebP и PNG уже сжаты. Строка «главное изображение» проверяется строже буквы: шаг берёт самое тяжёлое изображение первого экрана, и если под пределом оно, то под пределом и баннер.
7. Прогон Lighthouse выполняется разработчиком перед сдачей версии и записывается в PR числами, а не словом «быстро».

### 11.3. Доступность: WCAG 2.1 AA

Постановой КМУ № 757 доступность для коммунальных предприятий рекомендована, а не обязательна (`claude/04_vymohy.md`, раздел 3). Уровень AA берётся целью проекта, и его пункты проверяются при приёмке. Там, где ТЗ строже AA, это сказано прямо (11.1, п. 4).

1. **Контраст:** обычный текст — не менее 4,5:1; крупный (от 24 px или от 19 px полужирного) и границы элементов управления — не менее 3:1. Значения берутся из дизайн-системы 1.0 (`claude/11_dyzain-systema.md`, раздел 3, минимальная текстовая пара 5,14:1) и проверяются до вёрстки.
2. **Клавиатура:** все ссылки, кнопки, раскрывающиеся блоки и поля достигаются `Tab`, порядок обхода совпадает с визуальным, видимый контур фокуса не менее 2 px с контрастом не менее 3:1, ловушек фокуса нет. Требование контраста действует на каждой поверхности: на тёмной заливке контур берёт свой цвет (дизайн-система, раздел 3, п. 6).
3. **«Перейти до вмісту»** — первая ссылка на странице, видимая при фокусе.
4. **Семантика:** один `h1`, уровни заголовков без пропусков, `header / nav / main / footer`, перечни — списками, кнопка — `button`, ссылка — `a`. Элемент-«кнопка» из `div` не применяется.
5. **Изображения:** `alt` у каждого, декоративные — с пустым `alt` (5.3, п. 4).
6. **Язык разметки:** `lang="uk"` или `lang="en"` у `html`; вставка на другом языке получает свой `lang` — это прямо нужно карточкам ленты на английском (4.8).
7. **Ссылки понятны вне контекста:** вместо «читати далі» — «читати новину на сайті КМДА» либо доступное имя через `aria-label`.
8. **Мобильное меню:** кнопка сообщает состояние «раскрыто» (при `popover` это делает сам браузер, атрибут `aria-expanded` в разметку не ставится), закрытие `Esc`, кнопкой и нажатием вне меню, возврат фокуса на кнопку при закрытии, `Tab` из кнопки ведёт в меню (3.1).
9. **Формы админки:** `label` связан с полем, сообщение об ошибке привязано через `aria-describedby`, результат сохранения объявляется областью `aria-live`, обязательность отмечена не только цветом.
10. **Информация не передаётся одним цветом:** состояние «Чернетка» и «Опубліковано» — словом, а не только цветом метки. Само слово в метке — короткое, не длиннее 24 знаков, и метка переносится по словам: предложение в метке с запретом переноса расширяет карточку и даёт горизонтальную прокрутку на узком экране (решение 017, 18.11.2026). Длинная формулировка идёт в текст или в таблицу.
11. **Самодвижения нет:** анимаций, карусели и автопрокрутки на публичных страницах нет (4.1). Движение в ответ на действие пользователя под этот запрет не подпадает — переход цвета при наведении разрешён (решение Заказчика 18.11.2026). Сдвиг слоёв баннера при прокрутке и параллакс отложены в конец очереди (решение Заказчика 19.11.2026): в версии 1 баннер неподвижен. Любое такое движение подчиняется `prefers-reduced-motion`: при `reduce` оно отключается само, без участия пользователя, а не прячется за переключателем.
12. **Проверка:** автоматическая (axe или Lighthouse, 0 нарушений уровня AA) плюс ручная — обход клавиатурой по чек-листу 12.2. Автоматическая проверка не заменяет ручную: порядок обхода и осмысленность `alt` она не видит.

### 11.5. Безопасность: секреты вне репозитория, защита админки, заголовки

1. **Секреты** — только там, где указано в 10.5. Шаг `secrets:check` в CI; `.env` в `.gitignore`; значение секрета не попадает ни в лог прогона, ни в `sync-state.json` (7.5, п. 6).
2. **Если секрет всё же попал в историю git**, он считается утратившим силу: порядок — перевыпуск токена и смена пароля БД, а не правка истории. Публичный репозиторий означает, что коммит уже прочитан.
3. **Админка:** сессия в cookie `HttpOnly; Secure; SameSite=Lax` (8.2), пароль только хэшем bcrypt cost 12 (6.4), ограничение частоты входа (8.1, п. 6), заголовок `X-Requested-With` на изменяющих запросах, CORS с единственным разрешённым источником, журнал действий (9.7).
4. **Заголовки ответов API** (`helmet` или их явная установка): `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, минимальная `Permissions-Policy`.
5. **Политика содержимого публичных страниц.** Задать заголовки ответа на GitHub Pages нельзя — `[можно ли задать заголовки ответа (CSP, HSTS) на GitHub Pages — проверка разработчиком]`; поэтому политика объявляется через `<meta http-equiv="Content-Security-Policy">`: `default-src 'self'`, `img-src 'self' data:`, `script-src 'self'`, `style-src 'self'`, `font-src 'self'`, `connect-src 'self'` плюс адрес бэкенда, `frame-src 'none'`, `base-uri 'none'`, `form-action 'none'`. Встроенных скриптов и стилей, требующих ослабления политики, на публичных страницах нет.
6. **Загрузка файлов:** проверка по сигнатуре, удаление EXIF, имя задаёт сервер, SVG — только владельцу и только после очистки разметки (8.4, пп. 1–5).
7. **Внешние ссылки:** `rel="noopener noreferrer"` на всех (4.0, общее правило).
8. **Зависимости:** `npm audit` в CI, Dependabot, `ignore-scripts=true`.
9. **Резервная копия** выкладывается только шифрованной (9.6, п. 3). Нешифрованный дамп в репозиторий, артефакт и чат не попадает ни при каких условиях.
10. **Чего нет и не появляется без отдельного решения:** аналитики, сторонних скриптов, cookie на публичных страницах (5.4, п. 8). Из этого следует, что баннер о cookie не нужен: нечего согласовывать.

### 11.6. Надёжность: публичные страницы при спящем бэкенде, деградация блоков по отдельности

1. **Публичные страницы не зависят ни от Render, ни от Atlas, ни от внешних источников:** все данные лежат в сборке (6.6, 7.1). Остановленный бэкенд, приостановленный кластер и отказ любого источника не влияют на доступность страниц.
2. **Главный сценарий жителя не зависит от сети вовсе:** телефоны сценариев и услуг — редактируемые данные в сборке, а не внешний источник (2.1).
3. **Блоки деградируют по отдельности** (7.5, п. 7): отказ ленты не влияет на блок Facebook, отказ Prozorro — на новости. Общего «аварийного режима сайта» нет.
4. **Сломанные данные не публикуются:** не прошедший схему файл роняет сборку, на Pages остаётся прежняя версия (6.6, п. 3; код `SCHEMA_MISMATCH`).
5. **Откат** выполняется повторным запуском последнего успешного деплоя либо коммитом-возвратом; выполняет владелец. Порядок — в `docs/runbook-restore.md`, рядом с восстановлением БД.
6. **Внешнего мониторинга в версиях 1–3 нет.** Будильник отброшен (бриф, 5.1, п. 2), а бодрость бэкенда ни на что публичное не влияет; сбой синхронизации виден письмом GitHub о падении прогона (7.2, п. 8) и служебным разделом админки (8.6). Отдельные учётные записи сервисов мониторинга не создаются.
7. **Своего соглашения о доступности сайта нет:** доступность определяется GitHub Pages, измерений и обещаний в ТЗ не делается.

1. **Поддерживаются:** две последние версии Chrome, Firefox, Edge и Safari (macOS и iOS), последняя версия Samsung Internet, Chrome на Android. `[устройства и браузеры руководства для внутреннего показа — Заказчик]`: если в ответе окажется что-то старше, перечень расширяется решением Заказчика.

## 12. Приёмка

### 12.1. Критерий закрытия задачи

Задача закрыта, когда выполнены все шесть условий:
1. Результат проверен разработчиком самостоятельно: тесты, сборка, открытие страницы или вызов эндпоинта. Заказчику отдаётся только недоступное разработчику (чужие кабинеты, секреты, подтверждения людей) — 12.6.
2. `npm run ci` зелёный, PR зелёный.
3. `docs/project-context.md` обновлён в том же PR; решение по коду, если оно было, записано в `docs/decisions/` там же.
4. Найденное попутно записано и показано Заказчику, но не сделано (инструкции проекта, п. 4).
5. Заглушка, которая закрылась в ходе задачи, убрана из текста ТЗ и из реестра 13.2 тем же PR или той же правкой ТЗ.
6. Заказчик сказал «принято».

Не является закрытием: «собралось», «тесты зелёные», «выложено». Версия состава закрыта, когда пройден её чек-лист целиком и каждый непройденный пункт либо исправлен, либо перенесён решением Заказчика с записью в 13.3.
