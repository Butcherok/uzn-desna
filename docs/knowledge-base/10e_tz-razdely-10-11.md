## 10. Стек, структура кода и сборка

### 10.1. Выбор сборщика: Astro с React-компонентами

**Решение: Astro, компоненты на React, TypeScript.** Один вариант рекомендуется, два рассмотренных отброшены.

Причина в одном предложении: публичные страницы обязаны открываться при спящем бэкенде и держать бюджет первого экрана (2.1, требование 3; 11.2), а Astro по умолчанию отдаёт HTML без JavaScript и подключает React только там, где он нужен.

Что при этом получается штатными средствами, а не кодом проекта:

| Требование ТЗ | Чем закрывается в Astro |
|---|---|
| Папка с `index.html` и обязательной завершающей косой чертой (3.2, п. 3) | `build.format: 'directory'`, `trailingSlash: 'always'` |
| Базовый путь, меняемый без правок страниц (3.2, п. 1) | параметр `base` из переменной окружения |
| Префикс `/en/`, `hreflang`, канонические адреса (3.2, пп. 4–6) | маршрутизация по каталогам и штатная i18n-настройка |
| Чтение `data/*.json` при сборке с проверкой схемой (6.6, п. 3) | импорт JSON в коде страницы, проверка Zod, падение сборки при несоответствии |
| `404.html` в корне сборки (3.3) | страница `src/pages/404.astro` |
| Минимум JS на публичных страницах (11.2) | островная модель: `client:*` только на раскрывающемся меню, остальное — HTML |
| Страница-будильник `/admin` (8.7); сама админка отдаётся с Render (8, вступление) | одна статическая страница в сборке сайта; интерфейс админки собирается отдельно и отдаётся сервером |

Отброшено:
1. **Vite с пререндером** (плагин SSG или ручной прогон маршрутов). Всё перечисленное в таблице пришлось бы собирать самостоятельно: маршруты страниц, пререндер, завершающая косая черта, языковые префиксы, разделение бюджета публичных страниц и админки. Это код без выгоды: тот же результат, больше мест для ошибки.
2. **Чистый Vite + React как одностраничное приложение.** Отброшено жёстко: один `index.html` не даёт ни отдельных адресов страниц, ни работающего `404.html`, а первый экран без JavaScript не отображается вовсе — это прямо противоречит 2.1 и 11.7.
3. **Eleventy (11ty).** Отброшено 13.11.2026 при разборе альтернатив с Заказчиком: ноль JS и отдельные адреса он даёт, но React-компонентов у него нет, поэтому требование 9.3 — предпросмотр карточки в админке теми же компонентами, что на сайте — выполняется только дублированием вёрстки.
4. **Next.js со статическим экспортом.** Отброшено там же: требование 9.3 выполняет, но клиентский рантайм React едет на каждую публичную страницу, а бюджет первого экрана — 50 КБ JS (11.2) при требовании работать с выключенным JavaScript (11.7, п. 4).

Бэкенд версии 2 — **Node.js и Fastify** (решение разработчика): проверка тел запросов схемами и структурный лог встроены, что снимает ручную обвязку вокруг правил 8.1 и 7.5, п. 6. Express рассматривался и отброшен только по этой причине; на требования ТЗ выбор не влияет.

**Версии зависимостей в ТЗ не записываются.** Они фиксируются в `package-lock.json` первым PR по актуальным на тот момент выпускам: номер, записанный в ТЗ, устареет раньше, чем будет написана версия 1. Исключение — среда исполнения: Node.js берётся активной LTS-версии, одна и та же в `.nvmrc`, в CI и на Render; номер проверяется по первоисточнику перед первым PR — `[активная LTS-версия Node.js на момент первого PR — проверка разработчиком]`. Нижняя граница известна: Astro требует Node.js не ниже 22.22.0.

### 10.2. Слои `components / domain / gateway / config`, строгий `tsconfig`

**Пакеты рабочего пространства npm** (одно из решений брифа, раздел 6: монорепозиторий):

| Пакет | Что внутри | Где исполняется |
|---|---|---|
| `shared` | Схемы Zod всех сущностей и конвертов файлов, типы, чистые функции формата (обрезка текста, маска телефона, даты, `urlKey`) | Везде |
| `site` | Astro-страницы, React-компоненты, страница-будильник `/admin` | Сборка и браузер |
| `admin` | Интерфейс админки: Vite, React; типы — из `shared` (решение 040) | Собирается на Render командой сборки сервиса, отдаётся сервером по `/admin/` |
| `server` | API бэкенда | Render |
| `scripts` | Синхронизация источников и выгрузка для рабочих процессов | Раннеры GitHub Actions |

**Слои внутри `site` и `server`** — перенос из проекта бота (бриф, раздел 6):

| Слой | Что можно | Что запрещено |
|---|---|---|
| `components` | Разметка, стили, вывод переданных данных | Любой ввод-вывод, прямое чтение JSON, обращения к сети |
| `domain` | Чистые функции и типы: правила словаря ленты, три состояния выдачи, обрезка, сортировка, проверка полей публикации | Импорт из `gateway`, `components`, доступ к сети, БД, файлам, времени и случайным числам иначе как параметром |
| `gateway` | Весь ввод-вывод: Mongo, `fetch` к источникам, API GitHub, файловая система, cookie | Бизнес-правила: они живут в `domain` |
| `config` | Единый объект настроек: таймауты, частоты, лимиты, адреса, пределы длин | Секреты в коде; значения, разбросанные по файлам |

1. **Направление зависимостей:** `components → domain`, `gateway → domain`, `routes/pages → gateway + domain`. `domain` не зависит ни от кого. Нарушение ловится правилом линтера (запрет импортов по шаблону пути), а не договорённостью.
2. **Схемы Zod — единственное описание полей** (6.1, п. 8). Их читают: бэкенд при записи, сборка при чтении `data/*.json`, тесты. Второго описания полей (в типах вручную) нет: типы выводятся из схем.
3. **Переменные окружения проверяются при старте** (`fail-fast`): отсутствие обязательной переменной останавливает процесс с внятным сообщением. Это прямой урок отчёта 02, раздел 4: в боте правило было записано, а в коде отсутствовало.
4. **`tsconfig` строгий:** `strict`, `noUnusedLocals`, `noUnusedParameters`, `noFallthroughCasesInSwitch`, `noUncheckedIndexedAccess`, `exactOptionalPropertyTypes`, ESM. `any` в сигнатурах экспортируемых функций не допускается; внешние данные входят в код только через схему.
5. **Один файл — одна ответственность.** Файл длиннее 400 строк — повод разделить; вторая похожая возможность делается общим ядром, а не копией первой (урок отчёта 02, 5.3, п. 4).

1. **Состояние разработки — только `docs/project-context.md`** (1.1). ТЗ его не дублирует, чат не является его заменой.
2. **Решение по коду — отдельный файл в `docs/decisions/`** в том же PR, что и код. Шаблон: тема, дата, статус, что решено, что отброшено и почему, чем проверено.
3. **Три runbook'а обязательны к версии 2** и пишутся в задачах соответствующих интеграций, а не «потом»: каждый из них нужен при первом же сбое.
4. **`docs/` не разрастается в опросник.** Урок отчёта 02, 5.2: документ о процессе на 2680 строк не читается ни человеком, ни агентом. Предел: `CLAUDE.md` до 80 строк, `project-context.md` до 100 строк и 8 КБ (байтовый предел — правка 3.51: при 98 строках файл дорос до 39 КБ, из них 27,5 КБ — отчёты о проверках). **Предел держит шаг `docs:check` в `npm run ci`, а не обещание** (правка 19.11.2026, версия 3.15): до его появления предел не проверялся ничем, и `project-context.md` дорос до 133 строк и 44 КБ, которые уходили в переписку при каждом старте сессии. Исторические разделы вынесены в `done.md` и `findings.md`: при старте читаются только `CLAUDE.md` и `project-context.md`. Отчёт о проверках задачи пишется в `docs/checks/<дата>-<ветка>.md`, в `project-context.md` остаётся ссылка на последний.
5. **Крупный документ базы знаний хранится частями и читается срезом** (правка 3.51). ТЗ и дизайн-система разделены на оглавление и части до 80 КБ по границам разделов; правка меняет одну часть — документ базы знаний не дописывается построчно, а заменяется целиком, поэтому меньшая часть — меньше переписки. Номера строк разделов внутри частей — в `docs/kb-map.md`, он пересобирается шагом `docs:check` и в CI проверяется на свежесть.
5. **Файлы дизайн-системы** (`tokens.css`, `components.css`, шрифты) лежат в `site/src/styles` и `site/public/fonts`; значения и правила — `claude/11_dyzain-systema.md`, раздел 1.
6. **Копии документов базы знаний — `docs/knowledge-base/`.** Везутся: оглавления и части ТЗ и дизайн-системы, бриф, требования, содержание ТЗ, SEO-аудит. Закрытые документы (эксперименты 05–08, замечания 14, исследование 15) убраны из базы знаний 27.11.2026 и лежат в `docs/archive/`. Паспорт предприятия и отчёт по торговому боту в репозиторий не копируются: первый содержит непроверенные телефоны и сведения о людях при публичном репозитории (5.4), второй к этому проекту не относится (из базы знаний убран 27.11.2026; всё взятое из него — бриф, раздел 6). Копия не мастер: при расхождении прав документ базы знаний (1.1). Копия обновляется той же задачей, которой меняется сам документ (решение Заказчика 15.11.2026).

### 10.4. ESLint, Prettier, Vitest, pre-commit, `npm run ci` — с первого PR

Подключается в первом PR, до первой страницы. Основание: в проекте бота эти инструменты отложили и получили отдельный пакет из четырёх PR на 190-м PR (отчёт 02, 5.1, п. 5).

**`npm run ci` — одна команда, она же в CI** (девять шагов; `docs:check` добавлен 19.11.2026)**:**

| Шаг | Что делает |
|---|---|
| `typecheck` | `tsc --noEmit` по всем пакетам |
| `lint` | ESLint, в том числе запрет импортов между слоями (10.2, п. 1) |
| `format:check` | Prettier в режиме проверки |
| `test` | Vitest |
| `data:check` | Проверка каждого файла `data/*.json` схемой и конвертом (6.6) |
| `build` | Сборка сайта; падение сборки — падение CI |
| `budget:check` | Сверка веса файлов первого экрана с бюджетом 11.2 |
| `secrets:check` | Поиск в сборке имён и образцов секретов из списка (10.5) |
| `docs:check` | Пределы длины файлов старта сессии и свежесть `docs/kb-map.md` (10.3, пп. 4–5) |

**Обязательные тесты** (без них задача не закрывается, 12.1):

| Что проверяется | Почему именно это |
|---|---|
| Обрезка текста до 200 символов и заголовка до 90 по границе слова | 5.2, пп. 1–2; обрезка посреди слова или ссылки — дефект |
| Словарь и стоп-слова ленты на украинских строках | 7.4, п. 3: `\w` не покрывает кириллицу, ошибка не видна на латинице |
| Нормализация `urlKey` и устранение дублей | 6.1, п. 2; без этого одна публикация выводится дважды |
| Разбор даты публикации из номера `UA-ГГГГ-ММ-ДД-…` | 7.3, п. 2: даты в выдаче нет |
| Три состояния выдачи: `unknown` не очищает `items` | 6.5; главное правило отказоустойчивости |
| Проверка схемами всех файлов `data/` | 6.6, п. 3 |
| Формат телефона `+380XXXXXXXXX` и вывод по маске | 5.1, п. 6 |
| Матрица прав: редактор не получает действий владельца | 9.1 |

Тесты проверяют поведение чистых функций и ответы API на поднятом в памяти приложении. Проверок наличия подстроки в тексте исходников (как в боте) не делается: они пропускали дефекты (отчёт 02, 5.1, п. 7).

**Остальное:**
1. **pre-commit** (`husky` + `lint-staged`): Prettier и ESLint на изменённые файлы, затем `typecheck`. Полный `npm run ci` на коммите не гоняется — он в CI.
2. **CI обязателен для слияния.** Репозиторий публичный, поэтому правило защиты ветки `main` с требованием зелёной проверки доступно (отчёт 02, 2.3) и включается в первом PR вместе с запретом прямого push в `main`.
3. **Зависимости:** `npm audit` шагом CI, Dependabot на недельное обновление, `ignore-scripts=true` в `.npmrc` (перенос из бота как есть).
4. **Самописные `check-*` скрипты не создаются** (бриф, раздел 6, «не берём»).

### 10.5. Деплой: GitHub Pages, Render, переменные и секреты

**Сайт.** Публикуется рабочим процессом `deploy` (сборка → артефакт → публикация Pages), а не из ветки: сборка должна проверяться схемами и бюджетом до публикации. Файлы на Pages вручную не заливаются ни разу — иначе на Pages окажется версия, которой нет в истории. Запуск самого рабочего процесса кнопкой (событие `workflow_dispatch`) разрешён и ручной выкладкой не считается: процесс собирает то, что лежит в `main`, и проходит те же проверки (уточнение 19.11.2026, версия 3.14; прежняя формулировка «деплой вручную не выполняется ни разу» запрещала и то и другое вместе). Ограничения Pages по размеру сайта и частоте сборок — заглушка 41.

**Публичность репозитория — условие работоспособности, а не предпочтение.** GitHub Pages на тарифе Free доступен только в публичных репозиториях; защита ветки `main` и наборы правил на Free — тоже только в публичных; минуты Actions для публичных репозиториев не расходуются из включённого объёма. Приватный репозиторий при бюджете 0 грн (1.2) лишает проект деплоя и защиты ветки. Проверено по документации GitHub 13.11.2026; репозиторий сделан публичным в тот же день.

**Бэкенд.** Сервис на Render из каталога `server`, запуск собранного файла, проверка состояния — `GET /health` (8.6). Тот же сервис отдаёт интерфейс админки (8, вступление). Настройки сервиса — в `render.yaml` в корне репозитория (`docs/decisions/037-render-atlas-live.md`). Адрес сервиса — заглушка 34.

**Переменные и секреты.** Репозиторий публичный, поэтому правило одно: ни одного значения секрета в репозитории, в сборке и в чате.

| Где | Что хранится | Почему там |
|---|---|---|
| Переменные окружения Render | `MONGODB_URI`, `GITHUB_TOKEN` (права: запуск рабочих процессов и запись содержимого только этого репозитория), `EXPORT_TOKEN`, `SITE_ORIGIN`, при первом запуске — `BOOTSTRAP_OWNER_LOGIN` и `BOOTSTRAP_OWNER_PASSWORD_HASH` | Нужны только бэкенду; переменные `BOOTSTRAP_*` удаляются после создания владельца (9.2, п. 2) |
| Секреты GitHub Actions | `EXPORT_TOKEN`, `MONGODB_URI` (только для `backup`) | Синхронизация и копия идут с раннеров, а не с Render (7.1, следствие 1) |
| Репозиторий открытым текстом | Базовый путь и адрес API (переменные с префиксом `PUBLIC_`), открытый ключ `age` для шифрования копий (9.6, п. 3) | Это не секреты: открытый ключ шифрует, но не расшифровывает |
| Нигде в проекте | Закрытый ключ `age`, пароли в открытом виде | Закрытый ключ хранит владелец (заглушка 45) |

1. **В собранный фронт не попадает ничего, кроме базового пути и адреса API.** Проверяется шагом `secrets:check`: поиск в сборке имён секретов и характерных образцов значений.
2. **`.env` в `.gitignore`**, в репозитории только `.env.example` без значений.
3. **Список доступа Atlas.** Копия БД делается с раннеров GitHub Actions, адреса которых заранее неизвестны, поэтому список доступа открывается для любого адреса (`0.0.0.0/0`), а защита переносится на пароль длиной не менее 32 знаков и пользователя БД с правами только на одну базу. Диапазоны адресов Render (заглушка 43) этого не меняют: ограничить список только ими нельзя, пока копию делает раннер.
4. **Утечка токена Facebook** — исключено (решение 029).

### 10.6. Ветки, Conventional Commits, один PR на задачу, слияние только владельцем

1. **Ветки:** `main` и рабочие `feat/…`, `fix/…`, `docs/…`, `chore/…`, `ci/…` — обычными словами, без буквенных кодов (бриф, раздел 6: «обычные слова вместо буквенных кодов»). Прямой push в `main` запрещён правилом защиты ветки.
2. **Коммиты:** Conventional Commits с областью, по-английски: `feat(services): add service cards`. Имена файлов и ветвей — английские (инструкции проекта, п. 2).
3. **Один PR на задачу.** Описание PR: что сделано, что намеренно не тронуто, как проверить. Найденное попутно в PR не исправляется — оно записывается и показывается Заказчику (инструкции проекта, п. 4).
4. **Слияние — squash,** один PR превращается в один коммит в `main`: история `main` читается как список выполненных задач. Слияние выполняет только владелец и только при зелёном CI (бриф, раздел 6).
5. **В том же PR обязательно** обновляется `docs/project-context.md`, а при решении по коду — файл в `docs/decisions/`. Это условие закрытия задачи (12.1), а не пожелание: в боте документы отстали от кода на месяц.
6. **Шаблон PR заполняется.** В боте шаблон существовал и не использовался (отчёт 02, 5.2); здесь незаполненный шаблон — причина не сливать PR.
7. **Теги** `v1.0.0`, `v2.0.0`, `v3.0.0` ставятся на коммит, которым Заказчик принял соответствующую версию состава (1.2); запись о содержании — в `CHANGELOG.md`.

## 11. Нефункциональные требования

### 11.1. Мобильная вёрстка первой, точки перелома, размеры тач-целей

1. **Порядок проектирования и правила CSS — от узкого к широкому** (`min-width`). Макет версии для телефона создаётся первым и принимается первым (инструкции проекта, п. 7).
2. **Точки перелома:** 360 px — базовая; 600 px — планшет; 1024 px — десктоп. Ширина содержимого не превышает 1200 px, поля не меньше 16 px на телефоне.
3. **Нижняя граница работоспособности — 320 px:** горизонтальной прокрутки нет, ничего не обрезается.
4. **Тач-цели не меньше 44×44 px**, расстояние между соседними целями не меньше 8 px. Телефон в карточке — цель полной ширины карточки, а не подчёркнутое слово. Это строже уровня AA: 44×44 — критерий 2.5.5 Target Size (Enhanced) уровня AAA, тогда как на AA действует 2.5.8 Target Size (Minimum) с минимумом 24×24. Повышенное требование принято сознательно: главный сценарий жителя (2.1) — нажать телефон с телефона, одной рукой, на улице.
   **Исключение: ссылка внутри текста** (решение Заказчика 19.11.2026). Требование 44×44 относится к управляющим элементам — кнопкам, пунктам меню, ссылке-логотипу, телефону в карточке, заголовку-ссылке и прочим ссылкам, стоящим отдельно от текста. Ссылка внутри предложения, пункта перечня или ячейки таблицы под него не подпадает: её высота равна высоте строки, а растягивание разогнало бы междустрочный интервал в абзаце. То же исключение («Inline») записано в самих критериях 2.5.5 и 2.5.8. Проверяется это так: если ссылку можно поднять до 44 px, не меняя набора окружающего текста, она управляющий элемент и требование к ней применяется.
5. **Текст:** базовый размер 16 px, межстрочный интервал не меньше 1,5, длина строки 60–75 знаков на десктопе. Масштабирование страницы не запрещается: `maximum-scale` и `user-scalable=no` не применяются (это требование доступности, 11.3).
6. **Таблицы на телефоне** (реквизиты предприятия, 4.2) выводятся парами «подпись — значение», а не горизонтальной прокруткой.
7. **Проверка — на трёх размерах:** 360×640, 768×1024, 1366×768, плюс один реальный телефон Заказчика.

### 11.2. Производительность: бюджет первого экрана и целевые метрики

**Бюджет первого экрана главной страницы на телефоне.** Значения — после сжатия при передаче, суммарно по типу файлов:

| Что | Предел |
|---|---|
| HTML | 50 КБ |
| CSS, всего | 30 КБ, из них критический встроенный — не более 14 КБ |
| JavaScript на публичной странице | 50 КБ; фактически с версии 3 — только встроенный скрипт переключателя темы, до 2 КБ (решение Заказчика 27.11.2026, В1; до версии 3 — 0 КБ, журнал 19.11.2026) |
| Изображения первого экрана, суммарно | 250 КБ, главное изображение — не более 150 КБ |
| Шрифты | 120 КБ: подмножество «кириллица + латиница», WOFF2 (дизайн-система 1.0 расходует 65,1 КБ) |
| **Первый экран целиком** | **500 КБ** |
| Число сетевых запросов первого экрана | 20 |
| Сторонних доменов в запросах | 0 |
| Вес любой публичной страницы целиком | 1 МБ |
| JavaScript админки (бюджет первого экрана на неё не распространяется) | 300 КБ |

**Целевые метрики.** Lighthouse, режим телефона с эмуляцией медленной сети, медиана из трёх прогонов на опубликованной версии:

| Метрика | Цель | Порог приёмки |
|---|---|---|
| Largest Contentful Paint | ≤ 2,0 с | 2,5 с |
| Cumulative Layout Shift | ≤ 0,05 | 0,10 |
| Interaction to Next Paint | ≤ 100 мс | 200 мс |
| Total Blocking Time | ≤ 150 мс | 300 мс |
| Time to First Byte | ≤ 0,8 с | 1,2 с |
| Lighthouse Performance | ≥ 95 | 90 |
| Lighthouse Accessibility | ≥ 95 | 90 |
| Lighthouse Best Practices | ≥ 95 | 90 |

Пороги приёмки по LCP, CLS и INP совпадают с границей «хорошо» в Core Web Vitals (LCP ≤2500 мс, INP ≤200 мс, CLS ≤0,1 по 75-му процентилю); цели поставлены строже, чтобы ухудшение съедало запас, а не сразу роняло приёмку. TBT включён в таблицу потому, что Lighthouse работает без пользователя и INP измерить не может, отдавая вместо него Total Blocking Time. Бюджет первого экрана — наше решение, выведенное обратным счётом от LCP на медленном мобильном канале, а не отраслевой стандарт.

Lighthouse SEO не проверяется: сайт закрыт от поисковиков (3.3), оценка будет искажена `noindex`. Проверка возвращается в приёмку при снятии закрытия (11.4).

**Правила, которыми бюджет держится:**
1. Изображения — WebP, в двух плотностях через `srcset`, с обязательными `width` и `height` (иначе сдвиг макета).
2. Главное изображение первого экрана — `fetchpriority="high"`, без отложенной загрузки; всё ниже первого экрана — `loading="lazy"`.
3. Шрифты — локальные файлы, `font-display: swap`, `preload` только для одного начертания. Сторонние шрифтовые сервисы не подключаются (5.3, п. 9).
4. Сторонних скриптов, аналитики, встроенных карт и встраиваемых блоков соцсетей в первом экране нет ни на одной странице (4.6, 7.2, п. 10).
5. Шрифты, CSS и JS отдаются с того же домена, что и страница.
6. Шаг `budget:check` в CI сверяет вес файлов сборки с таблицей бюджета и роняет проверку при превышении: иначе бюджет держится обещаниями. Изображения он считает с 19.11.2026 (решение 020; до этого не считал вовсе, и строка «Изображения первого экрана» в таблице выше не проверялась ничем). Правила счёта: **один элемент — один файл** (у `<img>` и `<picture>` берётся самый тяжёлый кандидат, который элемент может запросить, и считается один раз: браузер скачивает одну ступень `srcset` и одну из двух тем, а не все); **две контрольные ширины** — 360 px, то есть телефон, которому и посвящена таблица бюджета, и 1920 px справочно, причём атрибут `media` у `<source>` читается, поэтому боковые предметы с `media="(min-width: 768px)"` в телефонную строку не попадают; **`loading="lazy"` — не первый экран**, такая картинка выводится отдельной строкой отчёта, чем правило п. 2 и становится проверяемым; **вес — как есть, без gzip**, потому что WebP и PNG уже сжаты. Строка «главное изображение» проверяется строже буквы: шаг берёт самое тяжёлое изображение первого экрана, и если под пределом оно, то под пределом и баннер.
7. Прогон Lighthouse выполняется разработчиком перед сдачей версии и записывается в PR числами, а не словом «быстро».

### 11.3. Доступность: WCAG 2.2 AA

Постановой КМУ № 757 доступность для коммунальных предприятий рекомендована, а не обязательна (`claude/04_vymohy.md`, раздел 3). Уровень AA берётся целью проекта, и его пункты проверяются при приёмке. С 26.11.2026 цель — **WCAG 2.2 AA** вместо 2.1 (решение Заказчика 26.11.2026): из новых критериев сайта касаются 2.4.11 (элемент в фокусе не уходит под липкую шапку, 3.1), 2.5.8 (размер цели — у нас 44 px, 11.1) и 3.3.8 (вход в админку без запоминания: вставка пароля и менеджер паролей не запрещены, `autocomplete` у полей). Виджета «версія для слабозорих» нет и не будет: такие надстройки перебивают настройки браузера и программ чтения с экрана (`claude/14_zamechaniia-v2.md`, раздел 6). Там, где ТЗ строже AA, это сказано прямо (11.1, п. 4).

1. **Контраст:** обычный текст — не менее 4,5:1; крупный (от 24 px или от 19 px полужирного) и границы элементов управления — не менее 3:1. Значения берутся из дизайн-системы 1.0 (`claude/11_dyzain-systema.md`, раздел 3, минимальная текстовая пара 5,14:1) и проверяются до вёрстки.
2. **Клавиатура:** все ссылки, кнопки, раскрывающиеся блоки и поля достигаются `Tab`, порядок обхода совпадает с визуальным, видимый контур фокуса не менее 2 px с контрастом не менее 3:1, ловушек фокуса нет. Требование контраста действует на каждой поверхности: на тёмной заливке контур берёт свой цвет (дизайн-система, раздел 3, п. 6).
3. **«Перейти до вмісту»** — первая ссылка на странице, видимая при фокусе.
4. **Семантика:** один `h1`, уровни заголовков без пропусков, `header / nav / main / footer`, перечни — списками, кнопка — `button`, ссылка — `a`. Элемент-«кнопка» из `div` не применяется.
5. **Изображения:** `alt` у каждого, декоративные — с пустым `alt` (5.3, п. 4).
6. **Язык разметки:** `lang="uk"` или `lang="en"` у `html`; вставка на другом языке получает свой `lang` — это прямо нужно карточкам ленты на английском (4.8).
7. **Ссылки понятны вне контекста:** вместо «читати далі» — текст с назвой цели либо доступное имя через `aria-label`, которое начинается с видимого текста: «Детальніше» → «Детальніше: <заголовок публикации>» (4.8).
8. **Мобильное меню:** кнопка сообщает состояние «раскрыто» (при `popover` это делает сам браузер, атрибут `aria-expanded` в разметку не ставится), закрытие `Esc`, кнопкой и нажатием вне меню, возврат фокуса на кнопку при закрытии, `Tab` из кнопки ведёт в меню (3.1).
9. **Формы админки:** `label` связан с полем, сообщение об ошибке привязано через `aria-describedby`, результат сохранения объявляется областью `aria-live`, обязательность отмечена не только цветом.
10. **Информация не передаётся одним цветом:** состояние «Чернетка» и «Опубліковано» — словом, а не только цветом метки. Само слово в метке — короткое, не длиннее 24 знаков, и метка переносится по словам: предложение в метке с запретом переноса расширяет карточку и даёт горизонтальную прокрутку на узком экране (решение 017, 18.11.2026). Длинная формулировка идёт в текст или в таблицу.
11. **Самодвижения нет:** анимаций, карусели и автопрокрутки на публичных страницах нет (4.1). Движение в ответ на действие пользователя под этот запрет не подпадает — переход цвета при наведении разрешён (решение Заказчика 18.11.2026). Так же разрешено движение подложки переключателя языка при переходе на страницу другого языка — без JavaScript, переходом между страницами (`@view-transition`), 200 мс; браузер без поддержки показывает новое состояние сразу (решение Заказчика 27.11.2026, дизайн-система, раздел 10). Сдвиг слоёв баннера при прокрутке и параллакс отложены в конец очереди (решение Заказчика 19.11.2026): в версии 1 баннер неподвижен. Любое такое движение подчиняется `prefers-reduced-motion`: при `reduce` оно отключается само, без участия пользователя, а не прячется за переключателем.
12. **Проверка:** автоматическая (axe-core по правилам WCAG 2.0–2.2 уровней A и AA или Lighthouse, 0 нарушений) плюс ручная — обход клавиатурой по чек-листу 12.2. Автоматическая проверка не заменяет ручную: порядок обхода и осмысленность `alt` она не видит. С 26.11.2026 в проверку входят: все страницы × ширины 320–1920 × светлая, тёмная, повышенный контраст (обе), системные цвета Windows — без горизонтальной прокрутки при видимой полосе прокрутки; увеличение браузера 200 и 400 % (1280 px → 640 и 320 CSS px), текст 200 % (1.4.4) и интервалы 1.4.12 — без прокрутки вбок и обрезанного текста. В системных цветах Windows axe читает цвета автора и даёт ложные нарушения контраста: этот режим проверяется снимком и вычисленными цветами.
13. **Повышенный контраст** (решение Заказчика 26.11.2026) — по настройке системы посетителя (`prefers-contrast: more`: «Збільшити контраст» на iPhone, iPad и Mac), без переключателя и без JavaScript, как тёмная тема. Отдельный набор значений тех же токенов, светлый и тёмный: текст не ниже 7:1, границы и иконки не ниже 4,5:1, контур фокуса 4 px (дизайн-система, раздел 3). Кнопки на сайте нет: она требует JavaScript на всех страницах (11.2) и по сути повторяет виджет. Передача этой настройки браузером на Android не подтверждена — там помогают увеличение текста и тёмная тема.
14. **Системные цвета Windows** («Контрастні теми», `forced-colors: active`): всё, что держится заливкой, получает прозрачную рамку, метка текущего пункта меню остаётся единственной, иконки — цвета ссылки, знак в шапке — своих цветов с обводкой (дизайн-система, раздел 3).
15. **Увеличение и длина строки:** масштаб не запрещается (11.1, п. 5); при увеличении до 400 % содержимое перестраивается в одну колонку без прокрутки вбок (WCAG 1.4.10). Строка абзаца — 60–75 знаков: мера `60ch` (на кириллице `68ch` давали ~80 знаков; замер 26.11.2026).
16. **«Заява про доступність»** — страница `/accessibility/`, ссылка в нижней полосе подвала (3.1). Содержание (решение Заказчика 26.11.2026, вариант «частково відповідає»): стан відповідності — «частково відповідає WCAG 2.2 AA» с причиной (самостоятельная проверка без независимого аудита, часть содержимого от нас не зависит); что сделано; что может быть недоступно (программами чтения с экрана сайт не проверялся; документы на других сайтах; PDF без структуры; «Новини» — чужие публикации, машинный перевод; английской версии нет); как увеличить текст и включить контраст — названиями настроек, без путей по меню; куда сообщить о проблеме — почта и приймальня из данных; как составлена заява и дата проверки (`A11Y_REVIEWED_AT` в `site/src/config/site.ts`, меняется с повторной проверкой). Только украинский.

### 11.4. Индексация: `noindex` до решения руководства, порядок снятия, `sitemap`, метаданные

**Сейчас** действует 3.3: `noindex, nofollow` на каждой странице, `robots.txt` с `Disallow: /`, `sitemap.xml` не публикуется, бэкенд отдаёт свой `robots.txt` с запретом (8.6).

**Порядок снятия — одним PR,** после решения руководства, записанного в журнал решений 13.3:
1. Переключить настройку `INDEXING_ENABLED` в `site/src/config/site.ts`: `<meta name="robots">` снимается со всех страниц, кроме 404 и «Новини» — у них остаётся `noindex, follow`. «Новини» — чужие публикации: политики спама Google относят перепубликацию чужого содержания без добавленной ценности к нарушениям (решение Заказчика 20.11.2026).
2. Заменить `robots.txt` сайта на разрешающий обход со ссылкой на `sitemap.xml`.
3. Включить создание `sitemap.xml` при сборке: только индексируемые канонические адреса (без 404 и «Новини»), абсолютные, обе языковые версии, с `lastmod` по дате значимой правки данных; `priority` и `changefreq` не выводятся — Google их не использует. На адресе в подкаталоге файл подаётся через Search Console: строка `Sitemap:` в чужом корневом `robots.txt` невозможна.
4. Проверить, что канонические адреса и `hreflang` (3.2, пп. 5–6) указывают на окончательный адрес сайта, а не на старый базовый путь.
5. `robots.txt` бэкенда разрешает обход, из индекса сервис убирает заголовок `X-Robots-Tag: noindex, nofollow` (8.6). Google видит `noindex` только у страницы, которую ему разрешено обойти; запрещённый к обходу адрес со ссылкой на него (страница `/admin`) мог бы попасть в индекс без содержимого. Сделано с версии 2 (решение Заказчика 20.11.2026).
6. Записать решение в `docs/decisions/` и в журнал решений ТЗ.
7. Заявку в Google Search Console и Bing подаёт владелец после публикации (12.6): ресурс «Префікс URL» с подтверждением мета-тегом, подача `sitemap.xml`, «Перевірка URL» главной, импорт в Bing Webmaster Tools из Search Console — по шагам `claude/13_seo-audyt.md`, раздел 5.

### 11.5. Безопасность: секреты вне репозитория, защита админки, заголовки

1. **Секреты** — только там, где указано в 10.5. Шаг `secrets:check` в CI; `.env` в `.gitignore`; значение секрета не попадает ни в лог прогона, ни в `sync-state.json` (7.5, п. 6).
2. **Если секрет всё же попал в историю git**, он считается утратившим силу: порядок — перевыпуск токена и смена пароля БД, а не правка истории. Публичный репозиторий означает, что коммит уже прочитан.
3. **Админка:** сессия в cookie `HttpOnly; Secure; SameSite=Lax` (8.2), пароль только хэшем bcrypt cost 12 (6.4), ограничение частоты входа (8.1, п. 6), заголовок `X-Requested-With` на изменяющих запросах, CORS с единственным разрешённым источником, журнал действий (9.7).
4. **Заголовки ответов API** (`helmet` или их явная установка): `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, минимальная `Permissions-Policy`.
5. **Политика содержимого публичных страниц.** Задать заголовки ответа на GitHub Pages нельзя — `[можно ли задать заголовки ответа (CSP, HSTS) на GitHub Pages — проверка разработчиком]`; поэтому политика объявляется через `<meta http-equiv="Content-Security-Policy">`: `default-src 'self'`, `img-src 'self' data:`, `script-src 'self'`, `style-src 'self'`, `font-src 'self'`, `connect-src 'self'` плюс адрес бэкенда, `frame-src 'none'`, `base-uri 'none'`, `form-action 'none'`. Встроенных стилей на публичных страницах нет. Встроенный скрипт один — скрипт темы (11.2, В1; решение 058): `script-src` пропускает его по хэшу (`'sha256-…'`, считается при сборке), без `'unsafe-inline'`; `<meta>` политики стоит в `<head>` до него. Совпадение хэша, размер до 2 КБ и то, что скрипт один, проверяет `budget:check` по собранным страницам.
6. **Загрузка файлов:** проверка по сигнатуре, удаление EXIF, имя задаёт сервер, SVG — только владельцу и только после очистки разметки (8.4, пп. 1–5).
7. **Внешние ссылки:** `rel="noopener noreferrer"` на всех (4.0, общее правило).
8. **Зависимости:** `npm audit` в CI, Dependabot, `ignore-scripts=true`.
9. **Резервная копия** выкладывается только шифрованной (9.6, п. 3). Нешифрованный дамп в репозиторий, артефакт и чат не попадает ни при каких условиях.
10. **Чего нет и не появляется без отдельного решения:** аналитики, сторонних скриптов, cookie на публичных страницах (5.4, п. 8). Из этого следует, что баннер о cookie не нужен: нечего согласовывать.

### 11.6. Надёжность: публичные страницы при спящем бэкенде, деградация блоков по отдельности

1. **Публичные страницы не зависят ни от Render, ни от Atlas, ни от внешних источников:** все данные лежат в сборке (6.6, 7.1). Остановленный бэкенд, приостановленный кластер и отказ любого источника не влияют на доступность страниц.
2. **Главный сценарий жителя не зависит от сети вовсе:** телефоны «Контактів» и услуг — редактируемые данные в сборке, а не внешний источник (2.1).
3. **Блоки деградируют по отдельности** (7.5, п. 7): отказ ленты не влияет на закупки, отказ Prozorro — на новости. Общего «аварийного режима сайта» нет.
4. **Сломанные данные не публикуются:** не прошедший схему файл роняет сборку, на Pages остаётся прежняя версия (6.6, п. 3; код `SCHEMA_MISMATCH`).
5. **Откат** выполняется повторным запуском последнего успешного деплоя либо коммитом-возвратом; выполняет владелец. Порядок — в `docs/runbook-restore.md`, рядом с восстановлением БД.
6. **Внешнего мониторинга в версиях 1–3 нет.** Будильник отброшен (бриф, 5.1, п. 2), а бодрость бэкенда ни на что публичное не влияет; сбой синхронизации виден письмом GitHub о падении прогона (7.2, п. 8) и служебным разделом админки (8.6). Отдельные учётные записи сервисов мониторинга не создаются.
7. **Своего соглашения о доступности сайта нет:** доступность определяется GitHub Pages, измерений и обещаний в ТЗ не делается.

### 11.7. Браузеры и устройства

1. **Поддерживаются:** две последние версии Chrome, Firefox, Edge и Safari (macOS и iOS), последняя версия Samsung Internet, Chrome на Android. `[устройства и браузеры руководства для внутреннего показа — Заказчик]`: если в ответе окажется что-то старше, перечень расширяется решением Заказчика.
2. **Не поддерживаются:** Internet Explorer, Opera Mini в экономном режиме.
3. **Возможности платформы** применяются только те, что поддержаны во всех перечисленных браузерах не менее двух лет. Новая возможность, не прошедшая это условие, применяется только с запасным путём.
4. **Публичные страницы полностью работоспособны при отключённом JavaScript:** меню строится на `popover`, раскрывающаяся биография руководителя — на `details`, телефоны — обычными ссылками. Это требование, а не побочный результат: оно же держит бюджет 11.2. Переключатель темы (версия 3) — надстройка: без JavaScript его кнопки нет, а страница показывается в теме системы посетителя (решение 024).
5. **Админка требует JavaScript** и это допустимо: у неё один-два пользователя и известные устройства.
6. **Разрешения:** от 320 до 1920 px по ширине.
7. **Печать:** «Контакти» имеет стили печати — телефоны и адрес видны, меню и декоративные изображения скрыты. Это же даёт лист на печать для редактора (9.4, п. 9).
