# Эксперимент: связка Render Free + MongoDB Atlas + пингер

Версия 1.0 от 13.11.2026. Результат этапа 3 дорожной карты (`00_brief-sait-kp-uzn.md`, разделы 5.1, 7, 9). Закрывает пометки **[ПРОВЕРИТЬ]** в разделе 5 брифа (лимиты БД) и в разделе 5.1, п. 2 (лимиты сервисов) — кроме перечисленного ниже в «Что не проверено».
Пометка **[ПРОВЕРИТЬ]** = не подтверждено по первоисточнику.

**Как проверялось.** Только документация, открыта 12.11.2026: Render (free, outbound-bandwidth, outbound-ip-addresses), MongoDB Atlas (free cluster limits, free cluster backups), UptimeRobot (условия, политика добросовестного использования, справка по бесплатному тарифу), cron-job.org (FAQ), Healthchecks.io (pricing, FAQ). Объём согласован с Заказчиком: без живого прогона.

**Что не проверено.**
- Живое поведение: реальное время засыпания и пробуждения, держит ли пингер сервис бодрым сутками.
- Условия использования Render: разрешён ли «будильник». В документации он не упомянут — ни запрета, ни разрешения.
- GitHub Actions: актуальная страница документации не открылась. «Минимум 5 минут» подтверждён по старой версии страницы docs.github.com; задержки, пропуски запусков и отключение расписания через 60 дней без активности в публичном репозитории — по цитатам из документации во вторичных источниках **[ПРОВЕРИТЬ]**.
- UptimeRobot: метод запроса (HEAD или GET), таймаут, можно ли на бесплатном тарифе поставить интервал 10 минут вместо 5, отключает ли он монитор после серии сбоев, каналы уведомлений — **[ПРОВЕРИТЬ]** в интерфейсе.
- Память и процессор бесплатного экземпляра Render: на странице free не указаны **[ПРОВЕРИТЬ]**.
- Лимиты Telegram Bot API и интеграция Healthchecks.io → Telegram: не открывались.

## 1. Главное

1. Факты раздела 5.1 брифа подтверждены все четыре: сон через 15 минут, пробуждение около минуты, 750 часов в месяц на рабочее пространство, `/robots.txt` спящий сервис не будит.
2. Схема «будильник раз в 10 минут» по документации рабочая и укладывается в лимит, но впритык: месяц из 31 дня — 744 часа из 750. Запас 6 часов. Часы общие на всё рабочее пространство Render: второй бесплатный веб-сервис (например, тестовый для эксперимента с Facebook) съест запас, и Render остановит **все** бесплатные сервисы до начала следующего месяца.
3. Резервные копии Atlas для бесплатного кластера платные: 0,10 $ в день, до 3 $ в месяц, нужна карта, функция в закрытом предпросмотре. В бюджет 0 грн не входит. Копия по расписанию (бриф, раздел 7, п. 4) — только своими силами через `mongodump`.
4. GitHub Actions как будильник не подходит; как запуск синхронизации и резервной копии по расписанию — подходит.
5. С бесплатного сервиса Render нельзя отправлять почту по SMTP: исходящие порты 25, 465, 587 закрыты. Уведомления и, в будущем, восстановление пароля админки — только через HTTP-API (Telegram или почтовый сервис с API).

## 2. Render Free (веб-сервис)

| Параметр | Значение по документации |
|---|---|
| Сон | Через 15 минут без входящего трафика (HTTP-запросы и сообщения WebSocket) |
| Пробуждение | Около минуты; браузеру показывается страница загрузки Render |
| Часы | 750 в календарный месяц на рабочее пространство; спящий сервис часы не тратит; при исчерпании все бесплатные веб-сервисы останавливаются до 1-го числа; остаток не переносится |
| Исходящий трафик | 5 ГБ в месяц на тарифе Hobby; без привязанной карты при превышении сервисы останавливаются до конца месяца |
| Минуты сборки | Входят в месячный лимит; при исчерпании без карты новые сборки отключаются, сервис работает на старой |
| Файловая система | Теряется при каждом сне, перезапуске и деплое; постоянный диск недоступен |
| Перезапуск | Render может перезапустить бесплатный сервис в любой момент |
| `/robots.txt` | Спящему сервису Render сам отвечает «disallow all», запрос сервис не будит; бодрому — запрос идёт в сервис |
| Исходящий трафик сервиса | Render может остановить сервис за «необычно большой» объём обращений наружу (в примерах — внешняя БД и внешние API); чисел нет |
| Исходящие адреса | Диапазоны IP общие для всех сервисов региона; список — в панели: сервис → Connect → Outbound |
| Недоступно | Масштабирование, shell/SSH, разовые задания, кэш на границе сети, SMTP-порты |
| Назначение | Прямо написано: не использовать для продакшена |

Следствия:
- Бэкенд должен сам отдавать `robots.txt` с запретом: когда сервис бодр, автоответа Render нет.
- `noindex` для адреса бэкенда во сне обеспечивает Render, наяву — мы.

## 3. MongoDB Atlas, бесплатный кластер

| Параметр | Значение по документации |
|---|---|
| Хранилище | 0,5 ГБ: несжатые документы плюс индексы |
| Соединения | До 500 |
| Операции | 100 в секунду; при превышении — замедление и очередь |
| Передача данных | 10 ГБ на вход и 10 ГБ на выход за скользящие 7 дней |
| Базы и коллекции | До 100 баз и 500 коллекций |
| Кластеров | Один бесплатный на проект Atlas |
| Версия | MongoDB 8.0; обновляет Atlas, выбрать нельзя |
| Пауза | Автоматически после 30 дней без единого соединения; возобновление вручную |
| Резервные копии | Платная подписка (см. раздел 1, п. 3) |
| `mongodump` / `mongorestore` | Работают, кроме базы `admin` и нескольких опций (`--oplog`, `--dumpDbUsersAndRoles` и др.) |
| Логи, советник по производительности | Недоступны |

Для сайта-визитки лимиты с большим запасом, если фото не хранить в БД (в брифе фото — Cloudinary или репозиторий).

Доступ по сети: Atlas пускает только адреса из списка доступа. Варианты — диапазоны региона Render из панели или «любой адрес» (`0.0.0.0/0`) с длинным паролем. Показывает ли панель диапазоны для бесплатного сервиса — **[ПРОВЕРИТЬ]** на живом сервисе; документация исключения не делает.

## 4. Будильник: три варианта

| | UptimeRobot | cron-job.org | GitHub Actions по расписанию |
|---|---|---|---|
| Цена и лимит | Бесплатно: 50 мониторов, проверка раз в 5 минут | Бесплатно, число заданий не ограничено («добросовестное использование») | Бесплатно в публичном репозитории |
| Минимальный интервал | 5 минут | 1 минута | 5 минут, но запуск не гарантирован вовремя |
| Таймаут | **[ПРОВЕРИТЬ]** | 30 секунд, читает до 64 КБ ответа | — |
| Что при сбоях цели | Автоотключение монитора в прочитанных документах не упомянуто **[ПРОВЕРИТЬ]** | Отключает задание после более чем 25 сбоев подряд | — |
| Ограничения использования | Разрешено любое, включая коммерческое (условия и справка от 28.09.2026); действует политика добросовестного использования | Аккаунт могут удалить за «чрезмерное» использование | Расписание отключается после 60 дней без активности в репозитории **[ПРОВЕРИТЬ]** |
| Новый аккаунт | Нужен | Нужен | Не нужен |

**Рекомендация: UptimeRobot, монитор на `GET /health` раз в 10 минут (или 5, если 10 выставить нельзя).** Причина: это сервис мониторинга — недоступность цели для него штатный случай, о котором он уведомляет; у cron-job.org серия сбоев ведёт к отключению задания. У cron-job.org при 10-минутном интервале 25 сбоев подряд набираются за 4 с небольшим часа простоя Render, после чего задание отключено и сервис спит до ручного включения. GitHub Actions отпадает: задержка запуска больше 15 минут — и сервис уснул.

Ловушка для обоих внешних сервисов: пробуждение Render длится около минуты, таймаут cron-job.org — 30 секунд. Запрос, который будит сервис, будет записан как сбой, хотя сервис проснётся. Поэтому синхронизацию нельзя запускать тем же запросом, которым будим.

## 5. Healthchecks.io и Telegram

- Бесплатный тариф Hobbyist: 20 проверок, 100 записей журнала на проверку. При heartbeat раз в час 100 записей — около четырёх суток истории.
- Тариф «для частных лиц»; коммерческое использование «терпят», но ждут перехода на платный. В существующем аккаунте Заказчика сайт делит лимит 20 с проверками торгового бота. FAQ разрешает отдельный аккаунт со своим лимитом для отдельного юридического лица; подходит ли под это сайт как личная инициатива — решать Заказчику.
- Сервис ведёт один человек; в FAQ прямо сказано, что возможны простои на часы и дни. Как единственный канал тревоги ненадёжен — UptimeRobot его частично дублирует.
- Аккаунт без входов больше года удаляют после письма-предупреждения.

## 7. Найдено попутно (не делалось)

1. **Нужен ли будильник вообще.** Если синхронизацию новостей и закупок выполняет GitHub Actions по расписанию (сам ходит во внешние API или дёргает бэкенд и пересобирает страницы), бэкенд нужен только админке, и сон стоит редактору одной минуты ожидания при входе. Тогда будильник, лимит 744 из 750 и зависимость от пингера исчезают. Цена: токен Facebook в секретах GitHub, а не Render; отвечает ли Prozorro серверам GitHub — та же непроверенная оговорка, что в `claude/05_eksperyment-prozorro.md`, раздел 3. Решение — в ТЗ.
2. Без будильника и без входов в админку 30 дней Atlas поставит кластер на паузу. Любой регулярный запрос к БД (синхронизация, резервная копия) это снимает.
3. Резервная копия: `mongodump` по расписанию из GitHub Actions. Куда класть дамп — вопрос ТЗ: в нём хэши паролей и данные сотрудников, публичный репозиторий без шифрования не подходит.
4. Тестовые сервисы следующих экспериментов (Facebook) в Render нельзя оставлять работающими: часы общие.
5. В брифе можно заменить пометки **[ПРОВЕРИТЬ]** ссылкой на этот отчёт: раздел 5, строка «БД»; раздел 5.1, п. 2. Строка «Фото» (Cloudinary) остаётся непроверенной.

## 8. План живого прогона (после «да» Заказчика)

Цель — закрыть раздел «Что не проверено», пп. 1 и 4. Аккаунты Render и Atlas у Заказчика есть.
1. Минимальный сервис на Node.js: `GET /health` (проверка соединения с Atlas, время старта процесса), `GET /robots.txt`.
2. Заказчик: бесплатный кластер Atlas, веб-сервис Render из репозитория, монитор UptimeRobot — по пошаговому чеклисту.
3. Замеры: время пробуждения без будильника (3 раза), непрерывность работы с будильником за 24 часа по времени старта процесса, видимость диапазонов IP в панели, расход часов в Billing.
4. После замеров сервис удалить, чтобы не тратил часы.
