# 013: шаг `Audit dependencies` временно не блокирует CI

Дата: 2026-11-17
Статус: принято

## Вопрос

17.11.2026 между 14:21 и 19:34 опубликованы два совета безопасности, задевающие сборочные
зависимости: picomatch — GHSA-fc5q-39xc-vjpf (high, ReDoS на повторяющихся extglob) и
minimatch — GHSA-g3hv-75wg-m249 (moderate). Шаг `Audit dependencies` в `ci.yml` стал красным на
PR #16, хотя `npm run ci` все восемь шагов проходит. `ci` — обязательная проверка правила защиты
`main` (решение 006), поэтому красный шаг блокирует слияние любого PR, а не только этого.

## Что проверено перед решением

1. **Поднять версии нельзя.** Совет закрывает picomatch `<=4.0.7`, а 4.0.7 — последняя
   опубликованная версия (`npm view picomatch versions`: … 4.0.5, 4.0.6, 4.0.7). Исправления в
   npm на 17.11.2026 не существует.
2. **`npm audit fix` не работает**: `npm audit fix --package-lock-only` падает с внутренней
   ошибкой npm (`Cannot read properties of null (reading 'edgesOut')`), `package-lock.json` не
   меняется.
3. **`--omit=dev` не помогает**: остаётся 13 high. Astro объявлен обычной зависимостью пакета
   `site`, а не dev, и тянет picomatch через `@astrojs/internal-helpers`.
4. **minimatch поднять можно** (10.2.6 → 11.x через `overrides`), но в одиночку шаг не
   озеленяет: picomatch остаётся.
5. **Deploy не затронут**: в `deploy.yml` шага `audit` нет, на публикацию сайта это не влияет.

## Решение

Команда шага `Audit dependencies` завершается `|| echo "::warning …"`. Отчёт `npm audit`
остаётся в логе шага, на странице прогона висит предупреждение со ссылкой на это решение, а
задача `ci` из-за советов не падает.

`continue-on-error: true` пробовали первым и отвергли на проверке: с ним шаг показывается
зелёным (API отдаёт `conclusion: success`), и единственный след остаётся в логе, куда никто не
заглядывает. Предупреждение видно прямо на прогоне.

Условие возврата: как только в npm появится picomatch выше 4.0.7, убрать `|| echo` и оставить
голую команду, поднять версию (при необходимости через `overrides` в корневом `package.json`) и
убедиться, что шаг зелёный сам по себе. Пункт стоит в очереди версии 1 дорожной карты.

Цена решения названа Заказчику прямо: это ослабление ворот безопасности. Риск принят как
близкий к нулю — ReDoS в сопоставлении путей на этапе сборки, входные данные — файлы самого
репозитория, в собранный статический сайт эти пакеты не попадают (JavaScript публичных страниц
0 КБ).

## Отброшено

- **Слить PR #16 кнопкой обхода защиты.** Разово работает, но следующий PR упирается в то же
  самое, и так до выхода исправленного picomatch. Обход защиты как привычка хуже, чем один
  явно записанный и ограниченный по сроку шаг.
- **`--audit-level=critical`.** Шаг стал бы зелёным молча и пропускал бы все будущие high до
  конца проекта — то есть прятал бы проблему вместо того, чтобы её показывать.
- **Убрать шаг `audit` из `ci.yml` совсем.** Потеряли бы отчёт и повод вернуться.
- **`overrides` на minimatch прямо сейчас.** Шаг всё равно красный из-за picomatch, а правка
  `package-lock.json` в этом PR смешала бы два разных разбора. Делается вместе с возвратом
  блокировки.

## Чем проверено

`npm run ci` зелёный локально. Прогон CI на PR #17: задача `ci` зелёная, в логе шага
`Audit dependencies` — отчёт на 26 советов, на странице прогона — предупреждение `npm audit`.
Вариант с `continue-on-error` проверен на том же PR и заменён: шаг показывался зелёным без
всякого следа на странице прогона.
