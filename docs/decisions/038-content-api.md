# 038: Эндпоинты контента (пункт 5в)

Дата: 2026-11-20
Статус: принято

## Вопрос

Как устроить эндпоинты контента ТЗ 8.3 на каркасе 5а (решение 035): где хранить
записи, как проверять их схемами из `shared/`, когда у схемы есть `refine`, как
считать `pendingChanges`, откуда взять начальные данные и что делать с
расхождением ТЗ 8.3, п. 3 с 5.4, п. 3 и 4.5.

## Решение

Ответы Заказчика 20.11.2026 и правка ТЗ 3.29 (раздел 8.3):

- **Запреты публикации 8.3, п. 3 сняты.** Руководитель без `confirmedAt`
  публикуется по 5.4, п. 3 (решение 011), телефона в сценарии нет по 4.5. В
  `published` переводится запись, прошедшая схему и проверку ссылок.
- **Начальные данные — однократная загрузка при старте.** Файлы `data/*.json`
  вшиваются в сборку сервера (`esbuild` собирает JSON в `dist/index.js`) и
  проверяются схемами файлов. Отметка загрузки — служебная запись в БД:
  повторной загрузки нет, даже если записи удалены. Время загрузки считается
  последней публикацией.
- **`green-zones` и `equipment` — с версией 3:** схем в `shared/` нет, данных о
  предприятии для них нет.
- **Окончательное удаление** — `DELETE /{сущность}/{id}?permanent=1`, только
  владелец и только из «Кошика». Автоочистка через 30 дней — задача 5ж.
- **`/moderation`** — задача 5ж по дорожной карте.

Решения разработчика:

- **Одна коллекция `content`** с полем `kind` и уникальным индексом
  `{ kind, key }`, где `key` — `slug`, `blockKey` или `singleton`. Записей
  меньше сотни; одна коллекция даёт `pendingChanges` одним `countDocuments` и
  одну пару методов хранилища на все сущности. Корзина держит свой `key`:
  возврат из неё не упирается в занятый `slug`.
- **Запись = служебные поля + `data`.** `data` — ровно поля схемы `shared/`,
  служебные (`status`, `deletedAt`, `createdAt`, `updatedAt`,
  `firstPublishedAt`) — рядом, а не внутри. Выгрузка 5д берёт `data` как есть.
- **Проверяется вся запись, не тело.** `PATCH` накладывает присланные поля на
  текущую `data` и проверяет результат полной схемой. `.partial()` и `.omit()`
  в Zod 4 на схемах с `refine` бросают исключение (проверено:
  `leaderSchema`, `publicDocSchema`), а частичная схема пропустила бы запись,
  ломающую `refine` в сочетании со старыми полями.
- **Реестр сущностей** (`domain/content-kinds.ts`): схема, поле ключа, поле
  названия для `slug`, есть ли порядок и черновик, синглтон ли, кто правит.
  Маршруты строятся по реестру одним модулем; новая сущность версии 3 — одна
  строка реестра и схема.
- **`slug`** — транслитерация по таблице постанови КМУ № 55 від 27.01.2010
  (https://zakon.rada.gov.ua/laws/show/55-2010-%D0%BF), до 60 знаков, занятый —
  с суффиксом. Задаёт и меняет только владелец (8.3, п. 2 строже 9.1 —
  выбрано строгое).
- **`pendingChanges`** = записи с `updatedAt` позже последней публикации +
  счётчик окончательно удалённых, чьё удаление не опубликовано. Счётчик правок
  (каждое сохранение +1) отброшен: пять правок одной карточки — это одна
  карточка, ждущая публикации.
- **`If-Match` с `updatedAt`** — защита от перезаписи из второй вкладки;
  необязательна, чтобы не усложнять админку там, где она не нужна.
- **Ссылки `contactId`** проверяются при записи; контакт, на который ссылаются,
  не удаляется и не меняет `slug`. Иначе сборка упадёт на битой ссылке
  (`site/src/domain/vacancies.ts`) уже после публикации.

## Отброшено

- **Исполнять 8.3, п. 3 как написано** — ни одна карточка руководства и ни один
  сценарий версии 1 не публикуются.
- **Команда загрузки на машине Заказчика** — строка подключения к БД оказалась
  бы у него на диске; у Render Free нет shell.
- **Чтение `data/*.json` с диска при старте** — зависит от рабочего каталога
  Render; вшитые в сборку файлы от него не зависят.
- **Коллекция на сущность** — девять коллекций и девять запросов на каждый
  `pendingChanges` без выигрыша при сотне записей.

## Последствия

- 5г (админка) получает готовый формат записи и сообщения ошибок на украинском.
- 5д (публикация) сбрасывает `pendingChanges`: пишет время публикации в
  служебную запись `content_meta` и обнуляет счётчик удалённых.
- Схема, изменённая после загрузки, может не принять старые записи: тогда
  `PATCH` отдаст 422 по полям — запись правится, а не теряется.
