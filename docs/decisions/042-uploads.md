# 042: загрузка файлов — до публикации в БД, в репозиторий через `publish-content`

Дата: 2026-11-21
Статус: принято Заказчиком 21.11.2026 (ответы на вопросы 2–6 при старте задачи 5е — по рекомендациям)

## Вопрос

ТЗ 8.4, п. 6 предполагал, что бэкенд пишет файл в репозиторий через API GitHub
тем же токеном, что запускает публикацию. Это значило бы три проблемы:
токену `GITHUB_DISPATCH_TOKEN` нужно право Contents: write, а владелец обходит
защиту `main` (решение 006, п. 3), поэтому утёкший с Render токен писал бы
прямо в `main`; коммит сервера в `content-data` через API ломал бы `git push`
рабочего процесса `publish-content` (та же причина, по которой отброшена
`sync-data`); файл становился бы публичным в репозитории до «Опублікувати
зміни», а после удаления навсегда оставался бы в истории git. Ещё нужно было
решить объём задачи, SVG, формат Word и способ снять метаданные без тяжёлой
обработки на Render (ТЗ 8.4, п. 7).

## Решение

1. **Файл ждёт публикации в БД.** `POST /uploads` проверяет тип по сигнатуре,
   вырезает метаданные, задаёт имя `media/{entity}/{slug}-{8 знаков SHA-256}.{ext}`
   и кладёт файл в коллекцию `uploads` (`_id` — путь). Тот же файл второй раз
   даёт тот же путь, копии нет.
2. **В репозиторий его кладёт `publish-content`.** `GET /export` отдаёт
   перечень `media` (путь, SHA-256, размер); рабочий процесс скачивает
   недостающие файлы с `GET /export/media` по токену выгрузки, сверяет хэш,
   лишние файлы `media/leaders/` и `media/public-docs/` в ветке удаляет и
   коммитит всё одним коммитом с `data/*.json`. `Deploy` берёт `media/` из
   `content-data` поверх `main`.
3. **В перечень идут** опубликованные файлы и неопубликованные, на которые
   ссылается опубликованная запись. Брошенный файл не уходит ни на сайт, ни в
   публичный репозиторий. Неопубликованные файлы выгрузки записываются в
   прогон (`lastRun.uploadPaths`); при успехе прогона они становятся
   опубликованными и их содержимое убирается из БД — один раз, тем же условным
   завершением прогона, что и счётчик правок (решение 041).
4. **Удаление — только владелец** (ТЗ 9.1), только неиспользуемого файла
   (используемый — 409 с перечнем записей, включая «Кошик»). Неопубликованный
   удаляется сразу; опубликованный помечается и уходит из ветки со следующей
   публикацией.
5. **Проверка перед публикацией:** запись, чей файл не найден ни среди
   загруженных, ни среди файлов начальных данных в `main`, останавливает
   публикацию с перечнем (ТЗ 8.5, п. 2).
6. **Объём 5е:** фото руководителя (`Leader.photoPath`: JPEG, PNG, WebP до
   2 МБ) и файл пункта `PublicDoc` с `publishedWhere: own` (`filePath`,
   `docUpdatedAt`: PDF и `.docx` до 10 МБ). У `own` вместо адреса — файл.
   На странице «Публічна інформація» файл — обычной ссылкой с типом и датой
   обновления; адрес даёт сборка (`?no-inline`, иначе маленький файл Vite
   встроил бы в разметку строкой `data:`).
7. **SVG отложен:** поля под SVG нет ни у одной сущности, надёжная очистка
   разметки — тяжёлая библиотека на Render. **Word — только `.docx`**: ZIP с
   `word/document.xml`; старый `.doc` по сигнатуре не отличить от `.xls`.
8. **Метаданные — вырезкой блоков без перекодирования** (свой разбор,
   без библиотек): JPEG — APP1 (Exif, XMP), APP13 (IPTC), прочие APPn кроме
   JFIF, ICC и Adobe, комментарии; PNG — `eXIf`, `tEXt`, `iTXt`, `zTXt`,
   `tIME`; WebP — `EXIF`, `XMP ` и их флаги в `VP8X`. От JPEG остаётся блок
   Exif из одного тега ориентации (36 байт): сборка Astro поворачивает по нему
   (`sharp().rotate()`). Ориентация PNG и WebP не сохраняется — с телефонов
   такие снимки приходят редко.
9. **Просмотр в админке:** `GET /uploads/{path}` — неопубликованный файл из
   БД, опубликованный — переадресация на `raw.githubusercontent.com` ветки
   `content-data`, файл начальных данных — на `main`. В политику содержимого
   админки добавлен `img-src https://raw.githubusercontent.com`.
10. **Админка:** поле «Фото» у руководителя и «Файл документа» у пункта
    публичной информации (файл уходит сразу после выбора, путь записывается
    в поле, запись сохраняется обычной кнопкой; до первого сохранения записи
    поле просит сохранить); раздел «Файли» со списком, состоянием и местами
    использования; два рецепта в «Допомога».

## Отброшено

- **Запись через API GitHub в `content-data` или отдельную ветку** — право
  Contents: write токену на Render и обход защиты `main` при утечке; гонка с
  `git push` рабочего процесса; файл публичен до публикации.
- **Все неопубликованные файлы в выгрузку по времени** — брошенный файл
  (например, фото не того человека) попадал бы в публичный репозиторий.
- **Перечень `media` необязательным** — его отсутствие означало бы «удалить
  все файлы ветки»; нет перечня — `SCHEMA_MISMATCH`.
- **`sharp` на Render для очистки метаданных** — перекодирование на
  бесплатном экземпляре, чего ТЗ 8.4, п. 7 и избегает.

## Последствия

- Токены и шаги владельца не меняются: `GITHUB_DISPATCH_TOKEN` остаётся с
  одним правом Actions.
- Неопубликованные файлы занимают место в Atlas (0,5 ГБ) до публикации;
  предел документа MongoDB 16 МБ, файл до 10 МБ влезает без GridFS.
- Новая зависимость сервера — `@fastify/multipart` (поток обрезается на
  10 МБ, `throwFileSizeLimit: false`, отказ формулирует домен).
- Если ветку `content-data` удалить, опубликованные файлы восстановить из БД
  нельзя: в ней их уже нет. Выгрузка тогда упадёт с `EXPORT_UNAVAILABLE` и
  именем файла; лечится новой загрузкой файла в карточке.
- Живой прогон (загрузка на Render, публикация, файл на сайте) — шаг
  Заказчика после выкладки.

## Правка после живого прогона (21.11.2026)

Живой прогон на Render 21.11.2026 (Заказчик поручил агенту): фото руководителя
и PDF пункта `own` загружены, опубликованы и видны на сайте; брошенный файл в
выгрузку не попал; после успеха файлы стали «На сайті», содержимое из БД
убрано; 409 для используемого файла и для файла записи в «Кошику»; удалённые
опубликованные файлы ушли из `content-data` следующей публикацией. Тестовые
записи и файлы убраны, данные `content-data` совпадают с `main`.

Найдено и исправлено (ветка `fix/5e-live`, ТЗ 3.34):

1. **Новый пункт `own` нельзя было сохранить:** схема требует файл, а поле
   файла принимало его только после первого сохранения. Теперь у несохранённой
   записи `slug` имени файла — `provisionalSlug(название)`, транслитерация
   перенесена из сервера в `shared` (`shared/src/format/translit.ts`), поле
   названия для каждой сущности — `UPLOAD_TARGETS[...].titleField`, тест
   сверяет его с `titleField` сервера. Пока названия нет, поле просит его
   заполнить.
2. **Публикация падала при живом `Deploy`:** `gh run watch` сразу после
   запуска получал 404 — номер прогона из ответа API становится виден не
   сразу. Одна из трёх публикаций прогона показала неудачу, хотя сайт
   обновился. Теперь шаг до минуты ждёт `gh run view` и только потом следит.
   Ошибка шага 5д, в его живом прогоне не проявилась.

**Повторный прогон 21–22.11.2026** (после PR #51, `c6387ce`): новый пункт `own`
с PDF сохранён одним действием до первого сохранения записи; публикация прошла,
файл на сайте открывается как PDF; уборка — файл ушёл из `content-data`, данные
совпадают с `main`. Уборочная публикация 22.11.2026 снова показала неудачу при
успешном `Deploy`: `gh run watch` получил HTTP 500 посреди слежения. Исправлено
в корне (ветка `fix/publish-watch`): вместо `gh run watch` — свой опрос
`gh run view` раз в 15 с; сбой API — повтор, 12 сбоев подряд или 25 минут без
итога — неудача с понятной ошибкой `DEPLOY`. Сценарии (404 в начале, 500 в
середине, провал `Deploy`, молчание API, нет итога) прогнаны с подставным `gh`.
