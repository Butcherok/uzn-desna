# 023: данные синхронизации в ветке `sync-data`, шаг Prozorro

Дата: 2026-11-19
Статус: принято Заказчиком 19.11.2026 (ветка `sync-data`; подписи статусов из документации Prozorro; текст «Закупівель поки немає»)

## Вопрос

ТЗ 7.1 предполагает, что `sync-external` коммитит JSON в репозиторий, а `deploy`
собирает сайт на любой коммит в `main`. Оба звена не работают при нынешних
настройках:

1. Прямой push в `main` запрещён правилом защиты (решение 006), обязательна
   проверка `ci`. Push из рабочего процесса с `GITHUB_TOKEN` отклоняется.
2. События, вызванные `GITHUB_TOKEN`, кроме `workflow_dispatch` и
   `repository_dispatch`, не создают новых прогонов (документация GitHub,
   «Triggering a workflow from a workflow»). Коммит синхронизации не запустил бы
   `deploy`, даже если бы push прошёл.

Второй вопрос задачи: отвечает ли поиск портала Prozorro раннерам GitHub
Actions (ТЗ 7.3, п. 5; заглушка 36).

## Решение

**Ветка `sync-data`.** `sync-external` пишет `data/sync/tenders.json` и
`data/sync/sync-state.json` в незащищённую ветку `sync-data` (одна папка, без
кода). Если изменились данные, которые выводит сайт, процесс запускает `deploy`
командой `gh workflow run deploy.yml --ref main`. `deploy` собирает `main` и
перед сборкой берёт `data/sync/` из `sync-data`. В `main` лежит заготовка
`data/sync/tenders.json` с `state: unknown`: ветки ещё нет — страница честно
пишет «Дані тимчасово недоступні».

**Коммит только при изменении содержимого (ТЗ 12.3).** Время прогона и счётчики
записей одного прогона изменением не считаются; результат, код ошибки и счётчик
сбоев подряд считаются. Следствие: при прогонах без изменений `lastRunAt` в
`sync-state.json` отстаёт; время каждого прогона видно в журнале Actions.

**Падение на сбоях (ТЗ 7.5, п. 3).** У `tenders.json` один источник, поэтому
правило «все источники файла недоступны» к нему не применяется — иначе первый
же сбой Prozorro слал бы письмо и правило «третий сбой подряд» не имело бы
смысла. Действует «третий неудачный прогон подряд». Правило «все источники
файла» остаётся для ленты, где источников несколько.

**Prozorro с раннера — работает.** Пробный прогон 19.11.2026 (прогон
44574493875): POST без браузерных заголовков — 200, 20 записей, 30 281 байт,
`x-ratelimit-limit: 60`. Полный прогон `sync-external` с ветки задачи (прогон 44575831879) записал 20 закупок в `sync-data`. Заглушка 36 закрыта.

**Подписи статусов** — из документации API Prozorro, раздел «Tender», поле
`status`, украинская версия; основная часть названия без пояснения в скобках.
Статус без украинского названия в документации не выдумывается: «Статус — на
сторінці закупівлі».

## Отброшено

- **GitHub App или личный токен в списке обхода защиты `main`.** Новый секрет с
  правом записи в `main`; правило 006 перестаёт защищать ветку для автомата,
  который пишет туда каждый день.
- **Синхронизация через PR с автослиянием.** PR от `GITHUB_TOKEN` не запускает
  `ci` без ручного одобрения, обязательная проверка не придёт — PR повиснет.
- **Снять защиту `main`.** Теряется проверка `ci` перед слиянием (ТЗ 10.4, п. 2).
- **Вариант Б отчёта 05 (официальная лента).** Не нужен: поиск портала раннерам
  отвечает.

## Последствия

- ТЗ 7.1, 7.3, 7.5, 4.9 и 13.2 поправлены в версии 3.17; заглушка 36 убрана из реестра.
- Ветку `sync-data` руками не правят. Удалить её можно: следующий прогон
  создаст её заново, а до него сайт соберётся на заготовке (`state: unknown`).
- Расписание `sync-external` — в UTC: 05:10, 11:10, 17:10. По Киеву зимой 07:10,
  13:10, 19:10, летом на час позже. Prozorro — только в 05:10 UTC.
- **[ПРОВЕРИТЬ]** (ТЗ 7.1, п. 5): считаются ли коммиты в `sync-data` активностью,
  которая не даёт GitHub отключить расписание после 60 дней. Страховка — ручной
  запуск владельцем.
- Строки чек-листа 12.3, которые требуют `main` (запуск по расписанию, письмо
  GitHub на третьем сбое), проверяются после слияния; порядок — в
  `docs/project-context.md`.
