# 032: Lighthouse в Actions, результаты в ветке `metrics`

Дата: 2026-11-20
Статус: принято

## Вопрос

Как мерить Lighthouse (ТЗ 11.2, прежде всего CLS) без ручного прогона
Заказчика и без доступа агента к его браузеру.

## Решение

Рабочий процесс `Lighthouse` (решение Заказчика 20.11.2026: «автоматически с
записью результатов в файл»; ветка `metrics` — «подходит»):

- **Когда:** после каждой удачной публикации `Deploy` на `main` (через 60 с —
  GitHub Pages отдаёт новую версию не мгновенно) и по кнопке, с выбором страниц.
- **Как:** `scripts/bin/lighthouse-run.mjs`, Lighthouse 13.6.0 через `npx`
  (в зависимости проекта не входит), Chrome раннера, режим телефона по
  умолчанию, три прогона на страницу, медиана по каждой метрике — метод
  `docs/checklists/v1-12-2.md`, раздел 1. Девять страниц, 404 не меряется.
- **Куда:** ветка `metrics` — `lighthouse/latest.md` (таблица с отметкой порогов
  ТЗ 11.2) и `lighthouse/history.csv` (дописывается, страница × замер); та же
  таблица — в отчёт запуска. Ветка без общей истории с `main`, создаётся первым
  запуском.
- **Порог не роняет запуск:** лабораторный замер даёт разброс, красный запуск
  слал бы ложные письма. Нарушение видно словами «не пройдено» в таблице.

## Отброшено

- **Ручной прогон Заказчика** — то, от чего уходим.
- **Запись в `main`** — защищена правилом (решение 006), коммит от
  `GITHUB_TOKEN` туда не пройдёт; та же причина, что у `sync-data` (решение 023).
- **PageSpeed Insights API** — ключ и квота; полевых данных у закрытого от
  индексации сайта всё равно нет.
- **Lighthouse CI (`@lhci/cli`) с сервером** — свой сервер для бюджета 0 грн лишний.

## Последствия

- Цифры раннера — лабораторные и не обязаны совпадать с замером Заказчика в
  PageSpeed: первый замер сверить с его прогоном.
- Есть ли Chrome на раннере `ubuntu-latest`, проверяется шагом `Find Chrome`:
  нет — запуск падает с понятной строкой.
- Каждая публикация, в том числе ежедневная по расписанию и запущенная
  синхронизацией, добавляет 9 строк в `history.csv`.
