# 041: публикация — ветка `content-data`, сброс счётчика по успеху прогона

Дата: 2026-11-21
Статус: принято Заказчиком 21.11.2026 (ответы на вопросы 1–4 при старте задачи 5д — по рекомендациям)

## Вопрос

ТЗ 8.5, п. 4 предполагал, что `publish-content` коммитит `data/` и тем самым
запускает `deploy`. Это не работает по той же причине, что у синхронизации
(решение 023): `main` защищена, а коммит `GITHUB_TOKEN` не запускает рабочие
процессы по `push`. Ещё нужно было решить, когда сбрасывать счётчик
неопубликованных правок, какой токен держит Render и оставлять ли запуск по
расписанию (ТЗ 7.1).

## Решение

1. **Ветка `content-data`.** `publish-content` пишет девять редактируемых
   файлов `data/*.json` в незащищённую ветку `content-data` (одна папка, без
   кода) и запускает `Deploy` через API (`workflow_dispatch` создаёт прогон и
   от `GITHUB_TOKEN`). `Deploy` перед сборкой берёт `data/sync/` из `sync-data`
   и `data/*.json` из `content-data`. Нет ветки — сборка на `data/` из `main`.
2. **Итог публикации — итог одного прогона.** `publish-content` дожидается
   `Deploy` (`gh run watch --exit-status`): «успех» значит «новая версия на
   сайте». Изменений нет — коммита и сборки нет, прогон успешен.
3. **Счётчик правок.** `GET /export?runId=` записывает время выгрузки в
   прогон (`content_meta.lastRun.snapshotAt`) и число окончательно удалённых на
   этот момент. Когда GitHub говорит, что прогон закончился успехом, время
   выгрузки становится временем последней публикации, а удалённые до неё
   вычитаются из счётчика. Правки во время прогона остаются в счётчике. Успех
   без выгрузки — неудача (`EXPORT_UNAVAILABLE`).
4. **Состояние прогона читается у GitHub при запросе** `/publish/status` и
   `POST /publish`, с кэшем 60 секунд и общим Promise (ТЗ 7.5, п. 4). Ответа
   нет — отдаётся сохранённое состояние. Итог записывается одним условным
   обновлением: два опроса не завершат прогон дважды.
5. **Вторая публикация** — 409 `PUBLISH_IN_PROGRESS`, пока прогон не
   закончен по GitHub. Прогон без итога дольше часа считается зависшим.
6. **Номер прогона** — из ответа `workflow_dispatch` с `return_run_details`
   (GitHub, 19.02.2026). На старый ответ 204 номер ищется в списке прогонов.
   Прогон по расписанию сервер впервые видит на выгрузке и заводит сам, без
   автора.
7. **Проверка перед запуском**: схемы записей `published`, синглтон ровно
   один, ссылка на опубликованный контакт. Непрошедшее — 422 с перечнем
   `problems` (раздел, название, ссылка на запись в админке).
8. **Токены.** `GITHUB_DISPATCH_TOKEN` — fine-grained, только этот
   репозиторий, Actions: Read and write, без срока действия; только в Render.
   `EXPORT_TOKEN` — не меньше 32 знаков, в Render и в секретах Actions;
   сравнивается за постоянное время. Нет токена GitHub — кнопки нет, полоса
   пишет «Публікацію ще не налаштовано».
9. **Расписание** 1-го числа, 06:37 UTC, сохранено (ТЗ 7.1). Выгрузка ждёт
   `/health` с `dbConnected: true` до 3 минут.
10. **Сравнение без времени выгрузки.** Файл, у которого не изменились
    записи, не переписывается; порядок ключей при сравнении не важен (файлы
    версии 1 написаны руками), порядок записей важен.

## Отброшено

- **Коммит в `main`** — защищена; токен в списке обхода ослабил бы правило 006.
- **Ветка `sync-data`** — два рабочих процесса толкались бы при push.
- **PR в `main`** — каждая публикация ждала бы слияния владельцем.
- **`Deploy` как переиспользуемый рабочий процесс** — `github.event_name`
  вызывающего попадал бы в `Deploy`: при запуске по расписанию сработал бы шаг
  `kick-sync`, которому нужны права, не выданные `publish-content`.
- **Сброс счётчика при выгрузке** — при упавшей сборке админка показала бы
  «0 змін» при старом сайте.
- **Замок публикации в БД** — второй источник правды рядом с GitHub.
- **Токен со сроком 366 дней** — истёкший токен молча остановил бы публикацию.

## Последствия

- После первой публикации `data/*.json` в `main` — только начальные данные
  бэкенда; правка их руками в PR на сайт не попадает.
- Первая публикация перепишет `static-blocks.json`: сервер упорядочивает
  блоки по ключу, файл версии 1 — в другом порядке. Содержимое то же.
- Если пока идёт `Deploy` публикации, в очередь `pages` встанет ещё один
  запуск, GitHub может отменить ожидающий: публикация покажет неудачу, хотя
  данные уйдут следующей сборкой. Повтор кнопкой исправляет.
- Шаги владельца: токен GitHub, `GITHUB_DISPATCH_TOKEN` и `EXPORT_TOKEN` в
  Render, `EXPORT_TOKEN` в секретах Actions — `docs/runbook-backend-deploy.md`,
  раздел 10.
- Живой прогон с GitHub и Render — после слияния; здесь проверено на
  `MemoryStore` с подставным `WorkflowRunner`.
