# 006: правило защиты ветки `main`

Дата: 2026-11-15
Статус: принято; пункт 4 отменён Заказчиком 16.11.2026 (см. «Пересмотрено 16.11.2026»)

## Вопрос

После слияния PR #1 Заказчик включил правило защиты `main` и запретил прямой push.
Две настройки правила остались неопределёнными: обязательны ли проверки перед слиянием
и отзывается ли одобрение PR при новых коммитах. ТЗ 10.4, п. 2 требует, чтобы слияние
было возможно только при зелёной проверке, а чек-лист 12.2 проверяет это отдельной
строкой. Заказчик работает над проектом один и попросил решить за него.

## Решение

Правило защиты `main` состоит из четырёх частей:

1. Прямой push в `main` запрещён — уже включено.
2. «Require a pull request before merging» включено, число обязательных одобрений — 0.
   Владелец сливает собственный PR сам, не одобряя его; запрет прямого push при этом
   сохраняется, и каждое изменение проходит через PR с описанием и историей.
3. «Require status checks to pass before merging» включено, обязательная проверка — `ci`
   (рабочий процесс `.github/workflows/ci.yml`, имя проверки совпадает с именем задачи).
4. Список обхода (bypass) пустой. Владелец в него не добавляется: иначе правило
   перестаёт действовать для единственного человека, который пишет код.

Отзыв одобрения при новых коммитах («Dismiss stale pull request approvals when new
commits are pushed») выключен: при нуле обязательных одобрений он ни на что не влияет.

## Отброшено

- **Обязательное одобрение PR (1 и больше).** При одном человеке в проекте это
  самоодобрение: ритуал без проверяющего, зато блокирует слияние, если GitHub
  запретит одобрять собственный PR.
- **«Require branches to be up to date before merging».** Заставляет переносить ветку
  на свежий `main` перед каждым слиянием. При одном авторе и последовательных задачах
  параллельных веток не бывает, а трение появляется сразу.
- **Оставить правило без обязательных проверок.** Это и есть нынешнее состояние: красный
  CI не мешает слиянию, и строка чек-листа 12.2 о зелёном CI не выполняется.

## Последствия

- Задача закрывается только при зелёном `ci`: красная проверка физически не даёт слить PR.
- Проверка `ci` появляется в списке выбора только после того, как она хотя бы раз
  выполнялась в репозитории. У нас она выполнялась в PR #1 и #8, поэтому доступна.
- Настройку применяет Заказчик: доступа к настройкам репозитория у разработчика нет.
  Порядок — в `docs/project-context.md`, раздел «Следующий шаг».

## Пересмотрено 16.11.2026

Правило применено Заказчиком 16.11.2026. Проверено по API GitHub в тот же день; состав
правила отличается от принятого решения.

1. Правило классическое — `Settings` → `Branches` → `Branch protection rules`, а не рулсет.
   Рулсетов в репозитории нет. На состав решения это не влияет, но порядок включения был
   записан в `docs/project-context.md` через `Settings` → `Rules` → `Rulesets` и
   действительности не соответствовал.
2. Пункты 1–3 действуют. Обязательная проверка одна — `ci`
   (`required_status_checks.contexts`: `ci`), источник проверки — GitHub Actions
   (`app_id` 15368). Прямой push запрещён, слияние только через PR, обязательных
   одобрений 0.
3. Пункт 4 отменён решением Заказчика. Галочка «Do not allow bypassing the above settings»
   не включена, уровень применения правила — `non_admins`: на владельца репозитория
   правило не распространяется. Причина — Заказчик работает над проектом один и не хочет
   оставлять себя без доступа к `main`.

Следствие: первый пункт «Последствий» больше не верен. При красной или незаконченной `ci`
владелец может слить PR кнопкой «Merge without waiting for requirements to be met».
Требование ТЗ 10.4, п. 2 (слияние только при зелёной проверке) держится на порядке работы
владельца, а не на настройке репозитория. Строка чек-листа 12.2 о зелёном CI проверяется
вручную: перед слиянием убедиться, что проверка `ci` в PR закончилась и она зелёная.
