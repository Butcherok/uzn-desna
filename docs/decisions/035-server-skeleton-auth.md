# 035: Каркас бэкенда и вход (пункт 5а очереди версии 2)

Дата: 2026-11-20
Статус: принято

## Вопрос

Очередь версии 2 после «Новин» не была расписана. Каталог `server/` был
пустым. Нужно было решить, в каком порядке строить бэкенд и админку, на
чём собрать сервер, как хранить пароли и сессии и как проверять работу с
БД, если у агента нет MongoDB.

## Решение

- **Очередь пункта 5** (утверждена Заказчиком 20.11.2026): 5а каркас и вход →
  5б живой запуск Render и Atlas → 5в эндпоинты контента → 5г интерфейс
  `/admin` → 5д публикация и `/export` → 5е загрузка файлов → 5ж модерация,
  журнал, резервные копии.
- **Сервер:** Fastify 5, `@fastify/cookie`, `@fastify/cors`,
  `@fastify/rate-limit`, официальный драйвер `mongodb` 7, схемы Zod. Без
  Mongoose: проверка формы данных уже делается Zod (ТЗ 8.3, п. 1), вторая
  модель данных дала бы второе место, где правила расходятся.
- **Слои** (ТЗ 10.2): `domain` (правила паролей, сессий, первого
  владельца, порт хранилища `Store`), `gateway` (`MongoStore`,
  `MemoryStore`), `routes`, `config`. `domain` не импортирует `gateway`.
- **Пароли:** `bcryptjs`, cost 12. Чистый JavaScript, сборки под машину не
  требует. Замер в контейнере агента: одна проверка пароля — 0,3 с. Новый
  пароль длиннее 72 байт не принимается: bcrypt учитывает только 72 байта.
- **Сессии:** токен — 32 случайных байта в cookie `HttpOnly`, в БД — только
  SHA-256. В production cookie `Secure` с префиксом `__Host-`. Срок 12 часов,
  продление при активности не чаще раза в 5 минут, не больше 5 сессий,
  просроченные удаляет индекс TTL. Новый вход из того же браузера закрывает
  прежнюю сессию.
- **Защита изменяющих запросов:** заголовок `X-Requested-With: uzn-admin`
  обязателен; запрос с `Origin` не из списка CORS отклоняется.
- **Ограничение частоты:** 60 в минуту на сессию (без сессии — на адрес),
  10 попыток входа за 15 минут на пару «логин + адрес», тот же предел на
  смену пароля. Счётчики в памяти процесса.
- **Первый владелец** — из `BOOTSTRAP_OWNER_LOGIN` и
  `BOOTSTRAP_OWNER_PASSWORD_HASH`. Хэш — командой `npm run hash-password`.
  Порядок — `docs/runbook-admin-access.md`.
- **Проверка БД:** `MemoryStore` и `MongoStore` проходят один и тот же набор
  `store-contract.ts`. Локально — только на `MemoryStore`: `fastdl.mongodb.org`
  из контейнера агента недоступен. В CI — на настоящей MongoDB 8 в сервисном
  контейнере. `REQUIRE_MONGO_TESTS=1` превращает отсутствие БД в ошибку,
  а не в пропуск.
- **Сборка:** `esbuild` собирает `server/dist/index.js`, зависимости внешние.
  Шаг `server:build` входит в `npm run ci`.

## Отброшено

- **Обычный `bcrypt`** с нативным модулем: быстрее, но установка на Render не
  проверена. Можно вернуться, если вход на Render окажется медленным (замер — 5б).
- **argon2id** — ТЗ 6.4: память бесплатного экземпляра не проверена.
- **`mongodb-memory-server`** — качает MongoDB с недоступного агенту сайта.
  Тесты либо падали бы у агента, либо молча пропускались бы.
- **Mongoose** — см. выше.
- **Счётчики ограничения частоты в БД** — лишняя запись на каждый запрос.
  Цена счётчиков в памяти: они обнуляются, когда Render засыпает. Пока идёт
  перебор, сервис не засыпает, поэтому предел держится.

## Последствия

- `/health` отвечает не дольше 2 с и при недоступной БД. Без своего срока
  проверка связи держалась 7 с (замер на сборке): админка будит сервис этим
  запросом (ТЗ 8.7).
- Порт открывается до подключения к БД; индексы и первый владелец
  создаются в фоне с повтором (2, 5, 10, 30, 60 с).
- Значение `TRUST_PROXY` для Render и версия MongoDB у Atlas сверяются в 5б.
  До этого адрес клиента в ограничении частоты — адрес прокси.
- `COOKIE_SAME_SITE` вынесен в настройку: при админке на Pages и API на
  Render запросы межсайтовые, и cookie `Lax` браузер не отправит
  (`docs/findings.md`). Решение — до задачи 5г.
